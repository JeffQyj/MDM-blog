# 文章创作风格

## 1. 内容风格

### 1.1 基础维度

| 维度      | 规范                                                       |
| ------- | -------------------------------------------------------- |
| **语言**  | 统一使用简体中文（zh\_CN），变量/函数名保持英文                              |
| **语气**  | 第一视角、亲切、简洁、严谨、结构化、风趣幽默；撰写技术文章时要保证不枯燥，引经据典地比喻；优先使用分点/表格呈现 |
| **排版**  | 中文与英文/数字之间留空格；标点符号使用全角（除代码内、Markdown 语法、URL 外）           |
| **标题**  | 采用 Markdown 标准标题层级（`#` / `##` / `###`），避免跳级              |
| **代码块** | 必须标注语言标签；代码示例一定要有注释；**禁止**纯注释代码块                         |

### 1.2 段落与章节

| 项目     | 建议                                |
| ------ | --------------------------------- |
| 标题层级深度 | 建议最多到 `####`，超过需拆分章节或重组为列表        |
| 章节字数   | 单章建议 300-800 字；超过 1500 字应主动拆分为子章节 |
| 段落长度   | 单段不超过 5 行；超过需用列表/表格/分段            |
| 章节开头   | 避免"接下来讲一下 X"；建议以场景/问题/回顾切入        |

### 1.3 关键术语处理

- **首次出现**：使用 **加粗** + 简短解释段（不超过 1 行）
- **后续出现**：可直接使用术语，无需重复解释
- **建立术语表**：同系列文章保持术语一致，跨文章不随意更换
- **专有名词**：英文专有名词保持原文（如 React、TypeScript），不译为中文

## 2. 文章结构模板

项目支持 5 种 admonition 类型，分别适用于不同场景，**确保一篇文章五个类型都有用到**，并且在合理的基础上尽可能多地使用：

| 类型          | 使用场景           | 语义强度 |
| ----------- | -------------- | ---- |
| `tip`       | 技巧提示、最佳实践      | 轻量提示 |
| `note`      | 补充说明、一般注意事项    | 中性   |
| `important` | 重要内容、需要强调的信息   | 重要   |
| `caution`   | 警告、需要小心处理的事项   | 警示   |
| `warning`   | 严重警告、可能导致问题的事项 | 最高警示 |

```markdown
:::tip
文章开篇说明或核心要点提示
:::

## 章节标题

正文内容...

:::note
补充说明或注意事项
:::

## 下一章节

:::important
需要重点强调的内容
:::

:::caution
需要注意避免的坑或警示事项
:::

:::warning
严重警告或可能导致问题的内容
:::

---

*文章结尾，可添加延伸阅读*
```

## 3. 独立项目系列文章风格

独立项目系列文章需采用「技术叙事 + 深度讲解」的创作风格，既要有真实项目经历的故事性，又要有技术干货的实用性。

章节过渡要顺滑，且文章内容不允许完全一致的重复。

**文章字数无封顶**，并且需要联网搜索相关资料确保项目内容无误的同时，做到全面详细丰富，避免文章内容单薄。

需要与发布时间在此之前的系列文章进行联动。

### 3.1 风格要素

| 风格要素     | 具体要求                                             |
| -------- | ------------------------------------------------ |
| **生动比喻** | 每个技术概念都要有通俗易懂的类比，如将注册中心比作物业管理处、网关比作门神            |
| **架构图示** | 简单流程用 ASCII；复杂架构用 mermaid；多对象对比用 HTML 表格（展示效果优先） |
| **代码示例** | 核心技术点必须提供真实可运行的代码片段，附加完整注释，注释一定要丰富               |
| **概念详解** | 专业术语首次出现时必须解释，不能只堆砌名词                            |
| **表格对照** | 优先使用表格进行概念对比，如家庭类比 vs 技术概念对照表                    |

### 3.2 ASCII 流程图示例

适合描述算法流程、业务逻辑、状态转换等场景，**所有 ASCII 码示例图都不要使用线框包围**。

```text
用户输入任务
    ↓
初始化消息列表(系统提示+用户任务)
    ↓
初始化工具定义与注册表
    ↓
循环开始(条件：未停止 && 未超过最大步数)
    ├─ 构建包含当前状态和历史上下文的提示词
    ├─ 调用大语言模型
    ├─ 解析模型响应，提取工具调用指令
    ├─ 执行所有工具调用
    ├─ 将工具执行结果添加到消息列表
    ├─ 检查是否得到最终答案或达到最大步数
    └─ 如需继续，进入下一轮循环
    ↓
循环结束，返回最终结果
```

### 3.3 内容结构

````markdown
:::tip
项目开篇说明，包含时间背景、技术选型概述
:::

## 项目背景
- 项目定位与业务场景
- 核心功能模块介绍（表格形式）
- 与其他同类项目的差异化

## 技术架构
### 技术栈一览表（包含通俗比喻）
| 技术 | 类比 | 说明 |
|------|------|------|
| Redis | 快递柜 | 存取快但空间有限 |

### 核心组件详解
每个核心组件都需要包含：
1. **为什么需要它？** - 问题背景 + 通俗比喻
2. **它是什么？** - 技术原理解释
3. **怎么用？** - 核心配置或代码示例
4. **注意事项** - 常见问题和最佳实践

## 业务模块实战
### 模块选择
从项目所有微服务中，选择 2-6 个最具代表性的模块进行深入讲解。

### 每个模块的内容结构

### 模块名称：功能名称

**业务场景**：描述这个模块解决什么问题

**核心代码**：

​```java
// 关键业务代码
​```

**技术要点**：解释代码中的核心设计思路

### 模块类型参考
| 模块类型 | 示例 | 展示内容 |
|----------|------|----------|
| CRUD 型 | 文章、问答、吐槽 | 基本增删改查、关联查询 |
| 认证型 | 用户、登录 | JWT、密码加密、第三方登录 |
| 关系型 | 交友、粉丝 | 关注关系、推荐算法、黑名单 |
| 文件型 | 文章配图、头像 | FastDFS、文件类型校验 |
| 搜索型 | 全站搜索 | ES 索引构建、全文检索、高亮 |
| 状态机型 | 活动、订单 | 状态流转、状态机模式 |

## 项目亮点与踩坑实录
### 问题解决类
每个问题采用以下结构：
- **问题现象**：实际遇到的问题描述
- **根因分析**：为什么会出现这个问题
- **解决方案**：具体配置或代码（必须包含）
- **经验总结**：从这个坑里学到了什么

### 技术对比类
- 方案 A vs 方案 B 的优劣对比（表格形式）
- 为什么最终选择了当前方案

---

*文章结尾感悟，从工程视角总结项目价值*
````

## 4. 禁止事项

| 禁止      | 说明                    |
| ------- | --------------------- |
| 堆砌技术名词  | 每个技术名词都要有解释或比喻        |
| 只有配置无代码 | 核心功能必须展示关键代码          |
| 只有代码无解释 | 代码必须有注释和上下文说明         |
| 干瘪的章节衔接 | 必须使用承上启下的过渡句          |
| 标题中滥用标点 | 禁止使用书名号、感叹号、问号以外的强调标点 |
