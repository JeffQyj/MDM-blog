:::tip
Odoo评论区的那句话还在我脑子里回响——"不对接第三方平台就是个玩具，对接了才有用。"

这句话像一把钥匙，打开了我对"技术接续"本质的新认知。当然，它针对的是需要生态协同的业务系统，并非所有软件。但它在提醒我们：**当系统本应互联时，孤立就是一种价值折损。**
:::

## 一、从Odoo说起：一次认知的涟漪

### 1.1 中间件方案的启示

五月初，我在B站刷到了一个开源项目盘点视频，其中一个叫 **Odoo** 的开源ERP系统吸引了我的注意。

深入了解后，我发现Odoo对接第三方平台有三种方式：

| 方式        | 说明          | 认知难度       |
| --------- | ----------- | ---------- |
| HTTP原生请求  | 直接调用第三方API  | 基础，能想到     |
| 第三方SDK    | 官方封装的调用库    | 常识，能想到     |
| **中间件方案** | 统一中间件对接所有平台 | 陌生，第一时间没想到 |

那个让我"第一时间没想到"的中间件方案，后来成了我理解"技术接续"的钥匙。

:::note
Odoo的中间件方案本质是：Odoo只需要和中间件对接一次，由中间件适配所有OTA平台（携程、飞猪、美团）的差异。这不就是胶水编程的雏形吗？
:::

### 1.2 从"没想到"到"系统化"

在《认知先行的落地——技术接续》中，我写过这样一段话：

> 不是能力差距，而是认知差距。我懂技术，但不懂这个行业；我能写出对接代码，但不知道行业里已经有成熟的解决方案。

这种"不知道自己不知道"的状态，正是认知先行要打破的。

而"胶水编程"（Glue Coding），正是从方法论层面给出了系统化的答案。

> 胶水编程 = 识别成熟能力 + 设计连接边界 + 编写精炼代码

这不是偷懒，而是更高维度的价值创造。

:::important
技术接续者的核心工作不是"发明"，而是"连接"。你不需要创造轮子，你只需要知道轮子在哪里，然后用最少的胶水把它装到你的车上。
:::

## 二、道：胶水编程的哲学根基

### 2.1 技术接续者的本质

在《自我丰容与认知先行》中，我提到过AI时代的两大特征：

- **信息极大丰富，但认知极度稀缺**
- **行动成本降低，但决策成本上升**

胶水编程正是对这两个特征的回应。

| 角色    | 核心动作     | 价值产出     |
| ----- | -------- | -------- |
| 技术发明者 | 从0到1创造   | 新技术的诞生   |
| 技术接续者 | 理解→连接→优化 | 技术的落地与流转 |
| 技术消费者 | 被动使用     | 功能的使用    |

:::note
我不是技术的发明者，但我可以是技术的接续者。把成熟的技术连接起来、优化落地，这本身就是极高的能力。
:::

### 2.2 胶水编程的三重应对策略

AI辅助开发有三个慢性顽疾，胶水编程提供了相应的应对思路：

| 顽疾        | 症状          | 胶水编程的应对策略             |
| --------- | ----------- | --------------------- |
| **AI幻觉**  | 凭空创造不存在的API | 验证优先，先找成熟能力，将幻觉影响降到最低 |
| **复杂度爆炸** | 从零构建导致无尽调试  | 站在生态肩膀上，复用已验证的方案      |
| **门槛虚高**  | 需要从底层学起     | 聚焦业务，而非底层实现细节         |

:::caution
当你想在AI的帮助下"从零构建"一个认证系统、一个支付系统、一个搜索系统时，请停下来问自己：行业里有没有成熟的解决方案？
:::

## 三、法：胶水编程的方法论体系

### 3.1 五层决策序列

哲学原则需要落地为可执行的决策序列：

| 优先级    | 行动         | 认知要求 | 决策成本 | 何时适用     |
| ------ | ---------- | ---- | ---- | -------- |
| **P1** | 官方/平台/内部能力 | 认知广度 | 极低   | 永远优先     |
| **P2** | 成熟开源/托管服务  | 评估能力 | 中    | P1不满足时   |
| **P3** | 配置/插件/适配层  | 设计能力 | 较高   | 需桥接时     |
| **P4** | 胶水代码       | 编码能力 | 高    | P1-P3不足时 |
| **P5** | 自研核心       | 判断能力 | 极高   | 成熟方案不可用时 |

:::note
决策成本从上到下递增。P1是"直接用，无需评估"；P5意味着"长期维护成本全自担"。这就是为什么P5应该是最后选项——不是因为它不好，而是因为它最贵。
:::

:::warning
P5是慎重决策后的战略选项，不应是图方便的习惯性动作。在非核心区习惯性自研，才是本末倒置；但在核心差异化领域，自研是不可或缺的战略选择。

**权衡思维**：既不盲目自研，也不盲目引入外部依赖。选择的标准永远是——这是不是我的核心竞争力？
:::

### 3.2 能力分层模型

决策序列需要映射为具体的工程分层。

:::note
此处借用分层思想来组织胶水编程的工程实践，非传统DDD架构术语。为避免与领域驱动设计中的"Entity"概念混淆，使用"Capability"表示成熟能力单元。
:::

| 层级             | 职责     | 胶水代码角色   | 示例                   |
| -------------- | ------ | -------- | -------------------- |
| **Capability** | 成熟能力载体 | 零代码，直接引用 | Redis、Auth0、Supabase |
| **Connection** | 连接与转换  | 轻量胶水     | Adapter、Transformer  |
| **Boundary**   | 隔离与防腐  | 边界定义     | 接口包装层、DTO            |
| **Gate**       | 质量门禁   | 验证规则     | 测试、类型检查、CI           |
| **Goal**       | 业务目标   | 编排逻辑     | 可运行的业务流              |

```
Capability (成熟能力)
    ↓ 连接
Connection (胶水代码)
    ↓ 隔离
Boundary (防腐层)
    ↓ 验证
Gate (质量门禁)
    ↓ 达成
Goal (业务目标)
```

### 3.3 与全端认知的呼应

在《AI时代下，全端认知》中，我整理过一张技术地图：

```
全端技术地图
├── Web端：Next.js / Nuxt / Astro
├── PC端：Electron / Tauri / Qt
├── 小程序端：uni-app / Taro / Flutter
├── 移动端：Flutter / React Native / KMP
└── CLI端：Bun / Node.js / oclif
```

胶水编程回答的问题是：**这些技术之间如何连接？**

| 场景       | 连接方案                    | 胶水代码职责 |
| -------- | ----------------------- | ------ |
| Web + 后端 | REST / GraphQL          | 接口适配   |
| 前端 + 搜索  | Meilisearch             | 索引映射   |
| 后端 + AI  | Spring AI / LangChain4J | 模型编排   |
| 多服务协同    | 消息队列                    | 事件流转   |

## 四、术：胶水编程的工程实践

### 4.1 标准流程

方法论需要转化为可执行的流程：

```
需求表达 → 能力发现 → 方案评估 → 边界设计 → 胶水实现 → 验证交付
```

| 阶段   | 关键问题          | 产出物  |
| ---- | ------------- | ---- |
| 需求表达 | 我要解决什么问题？     | 需求文档 |
| 能力发现 | 行业里有什么成熟方案？   | 方案清单 |
| 方案评估 | 哪个方案最适合我的场景？  | 选型报告 |
| 边界设计 | 第三方和我系统的边界在哪？ | 接口契约 |
| 胶水实现 | 如何精准地连接？      | 胶水代码 |
| 验证交付 | 胶水层是否可靠？      | 测试报告 |

### 4.2 质量门禁

:::note
质量门禁是胶水代码的保护网——当第三方能力发生变更时，质量门禁能第一时间发现问题，防止缺陷扩散到整个系统。
:::

| 门禁类型     | 工具示例              | 作用        | 检出能力 |
| -------- | ----------------- | --------- | ---- |
| 单元测试     | pytest / JUnit    | 验证胶水逻辑正确性 | 逻辑错误 |
| 类型检查     | TypeScript / MyPy | 接口契约约束    | 类型错误 |
| Schema验证 | JSON Schema / Zod | 数据格式校验    | 输入污染 |
| CI流水线    | GitHub Actions    | 自动化质量把关   | 集成失败 |

## 五、器：胶水编程的工具箱

### 5.1 成熟能力库

好工具的价值在于放大上层能力：

| 场景   | 推荐方案             | 提效对比（传统 → 胶水）\* |
| ---- | ---------------- | --------------- |
| 身份认证 | Supabase Auth    | 数天 → 数小时        |
| 后台管理 | Refine           | 一周 → 两三天        |
| 文件存储 | MinIO + Imgproxy | 数天 → 半天         |
| 实时通信 | PocketBase       | 数天 → 一天         |
| 搜索引擎 | Meilisearch      | 数天 → 半天         |
| 监控告警 | Uptime Kuma      | 数天 → 数小时        |
| 部署基建 | Coolify          | 数天 → 一小时        |

\*以上为基于小型项目/原型的经验估计，实际效果因项目复杂度、团队熟悉度、业务定制需求而异。

### 5.2 选型三原则

:::important
选型能力是"认知先行"的工程落地。你需要知道行业里有什么成熟方案，并能够评估它们的成熟度。
:::

| 原则        | 问自己                  | 答案                      |
| --------- | -------------------- | ----------------------- |
| **许可证安全** | 这个方案的许可证会不会给我带来法律风险？ | MIT/Apache 2.0优先，AGPL谨慎 |
| **维护活跃度** | 这个项目还在被维护吗？          | 近三月有commit，issue有响应     |
| **依赖深度**  | 这个方案引入多少间接依赖？        | 越少越好，零依赖最佳              |

## 六、陷阱与边界：胶水编程不是银弹

### 6.1 什么时候不该用胶水

:::caution
胶水编程是方法论，不是教条。知道什么时候不用，比知道什么时候用更重要。

| 场景      | 原因            | 替代方案 |
| ------- | ------------- | ---- |
| 核心差异化能力 | 是竞争壁垒，决定生死    | 自研   |
| 性能极致敏感  | 胶水层有开销，可能成为瓶颈 | 原生优化 |
| 合规强制要求  | 安全审计/政策要求必须自研 | 内部框架 |

### 6.2 常见陷阱

| 陷阱        | 症状             | 解药          |
| --------- | -------------- | ----------- |
| **胶水层过厚** | 胶水代码比业务代码还多    | 重新评估P1-P5序列 |
| **边界不清**  | 业务逻辑渗透到胶水层     | 强化防腐层设计     |
| **过度依赖**  | 第三方API变更导致全局地震 | 接口隔离+降级方案   |
| **供应商锁定** | 替换成本高到无法动弹     | 抽象层+替换预案    |

:::warning
有一种错误的"胶水思维"：把所有东西都当成第三方能力，连核心业务逻辑都往外包。这种做法是另一种形式的懒惰，不是胶水编程。
:::

## 七、成为胶水编程时代的架构师

### 7.1 能力模型转变

```
过去：精通语言 → 精通框架 → 精通业务
        ↓
现在：认知广度 → 选型能力 → 架构设计 → 业务洞察
```

在《AI时代的学习方法论》中，我提到过"Agent架构师"的概念：

> 你不是执行者，你是指挥官。你不需要亲自上战场，你需要的是排兵布阵的能力。

胶水编程架构师 = Agent架构师在系统设计领域的映射

| Agent架构师 | 胶水编程架构师  |
| -------- | -------- |
| 设计AI如何工作 | 设计系统如何连接 |
| 下达精准指令   | 设计精准边界   |
| 评估AI产出   | 评估方案选型   |

### 7.2 从"写代码的人"到"连接系统的人"

:::important
写代码的人的价值在于代码行数，连接系统的人的价值在于系统效率。
:::

| 维度   | 写代码的人  | 连接系统的人      |
| ---- | ------ | ----------- |
| 核心问题 | 如何实现功能 | 如何选择+连接     |
| 价值衡量 | 代码质量   | 业务流转效率      |
| 能力重心 | 实现细节   | 架构设计        |
| 时间分配 | 80%写代码 | 80%选型+20%胶水 |

## 八、写在最后

回到文章开头的那句话——"不对接第三方平台就是个玩具，对接了才有用。"

当然，我们已知道这并非绝对真理——孤立的核潜艇系统不是玩具，封闭的金融清算系统也不是玩具。但**对你正在构建的那个本应融入生态的业务系统而言**，这句话依然是一盏警示灯。

> **不连接成熟能力的系统就是玩具，连接了才有用。**

而你，作为技术接续者，你的价值不是创造那些成熟能力——那是别人的工作。你的价值是：**发现它们，评估它们，连接它们，让它们在你的系统中为你的业务目标服务。**

这，就是胶水编程。
