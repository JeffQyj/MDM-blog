## 一、索引调优实战：给查询装上「目录」

### 造 100 万行数据，先看「没索引」的惨状

```sql
-- 建演示表
CREATE TABLE documents (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    doc_name TEXT NOT NULL,
    doc_type VARCHAR(20),
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 快速插入 100 万条模拟数据
-- 知识点：generate_series 是 PG 的行生成神器
INSERT INTO documents (doc_name, doc_type)
SELECT
    'doc_' || i || '.pdf',                                        -- 生成 doc_1.pdf 到 doc_1000000.pdf
    (ARRAY['video', 'image', 'doc'])[floor(random()*3)+1]         -- 随机类型
FROM generate_series(1, 1000000) s(i);

-- 未加索引前：查询耗时（EXPLAIN ANALYZE 会真实执行 SQL）
EXPLAIN ANALYZE SELECT * FROM documents WHERE doc_name = 'doc_999999.pdf';
-- 你会看到 Seq Scan（全表扫描），扫描 100 万行
```

### 加 B-Tree 索引，立竿见影

```sql
-- 创建 B-Tree 索引（最常用的平衡树索引，默认类型）
CREATE INDEX idx_doc_name ON documents(doc_name);

-- 再次查询：变成 Index Scan，速度提升几百倍
EXPLAIN ANALYZE SELECT * FROM documents WHERE doc_name = 'doc_999999.pdf';
```

### 索引的底层：为什么 B-Tree 这么快

`CREATE INDEX` 默认建的是 **B-Tree（平衡多路查找树）**：

- 全表扫描是 O(n)——看 100 万次
- B-Tree 索引是 O(log n)——树的高度只有 3\~4 层
- **哪怕数据量翻 10 倍到 1 亿行，树高可能只增加 1 层，查询耗时几乎不变**

### 其他索引类型一览

```sql
-- Hash 索引：仅适用于 = 等值查询
CREATE INDEX idx_doc_hash ON documents USING hash (doc_name);

-- 复合索引：注意字段顺序，遵循最左匹配原则
CREATE INDEX idx_doc_type_created ON documents (doc_type, created_at);

-- GIN 索引：数组/JSONB/全文搜索的神器
CREATE INDEX idx_doc_tags ON documents USING gin (tags);
CREATE INDEX idx_doc_meta ON documents USING gin (metadata jsonb_path_ops);

-- 唯一索引：保证字段值不重复
CREATE UNIQUE INDEX idx_doc_md5 ON documents (doc_md5);
```

### 索引的「代价」：天下没有免费的午餐

| 代价   | 说明                                     |
| ---- | -------------------------------------- |
| 磁盘空间 | 索引本身是一棵树，占用额外存储                        |
| 写入变慢 | INSERT/UPDATE/DELETE 时要同步维护索引树，索引越多写越慢 |
| 维护成本 | 数据频繁变动会产生碎片，偶尔需要 REINDEX               |

:::important
**不是所有字段都要建索引。** 判断标准：查询频率远高于写入频率的列才值得建。频繁写入的表（如日志、流水）索引过多反而是灾难。
:::

### 四大索引失效场景：加了索引还是慢的原因

| 场景    | 错误示例（导致全表扫描）                        | 正确姿势                                |
| ----- | ----------------------------------- | ----------------------------------- |
| 模糊查询  | `LIKE '%doc_999%'`（左通配符）            | 前缀匹配 `LIKE 'doc_999%'` 才能走索引        |
| 函数操作  | `WHERE UPPER(doc_name) = 'DOC.PDF'` | 建函数索引 `ON (UPPER(doc_name))` 或查询前处理 |
| 类型不匹配 | `WHERE id = '123'`（数字列传字符串）         | 保持类型一致                              |
| 最左匹配  | 复合索引 `(a, b)` 只查 `b`                | 复合索引必须从最左侧字段开始                      |

:::note
**索引失效的规律是跨数据库通用的**，因为它们都是「破坏索引有序性」的行为。
:::

## 二、事务与 ACID：要么全做，要么不做

### 事务：立下「生死状」

```sql
-- 准备表
CREATE TABLE accounts (
    username TEXT PRIMARY KEY,
    balance DECIMAL(10, 2)
);
CREATE TABLE members (
    username TEXT PRIMARY KEY,
    expire_date DATE
);
INSERT INTO accounts VALUES ('jeff', 150.00);
INSERT INTO members VALUES ('jeff', '2026-01-01');

-- 开启事务，立下「生死状」
BEGIN;

-- 1. 扣钱
UPDATE accounts SET balance = balance - 100 WHERE username = 'jeff';

-- 2. 开通一年会员（假设这里 SQL 写错了或网络断了）
UPDATE members SET expire_date = expire_date + INTERVAL '1 year' WHERE username = 'jeff';

-- 检查无误后，正式写入硬盘
COMMIT;

-- 如果中途发现问题，直接反悔
ROLLBACK;  -- 刚才的操作全部撤销，钱回到 jeff 账上
```

### SAVEPOINT：事务里的「存档点」

事务还可以设置存档点，像单机游戏存档一样局部回滚：

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE username = 'jeff';

SAVEPOINT step1_done;     -- 存档点：类似游戏存档

UPDATE members SET expire_date = NULL WHERE username = 'jeff';  -- 这里出错了
ROLLBACK TO step1_done;   -- 只回滚到存档点，扣钱那步保留

COMMIT;                   -- 最终提交
```

### ACID：事务的四条铁律

| 特性                    | 含义           | 通俗理解         |
| --------------------- | ------------ | ------------ |
| **A**（Atomicity）原子性   | 要么全做，要么全不做   | 扣钱和加会员必须同生共死 |
| **C**（Consistency）一致性 | 数据从合法状态到合法状态 | 余额不能变负数      |
| **I**（Isolation）隔离性   | 并发事务互不干扰     | 两人同时转账不会乱账   |
| **D**（Durability）持久性  | COMMIT 后永久生效 | 断电也不丢        |

:::note
关于 ACID 的实现原理——原子性和持久性靠 redo/undo 日志，隔离性靠 MVCC——我在 [数据库学习之路](../编程生涯数据库学习之路/) 里已经详细拆解过 MySQL 的实现，PG 的思路与之相通但细节不同（PG 用 WAL 日志 + 多版本元组，见 [数据库天花板——PostgreSQL](../编程生涯数据库天花板postgresql/)）。这里不重复，重点讲事务的**用法**。
:::

## 三、锁机制：并发安全的「交通规则」

事务保证了单条业务正确，但**多个用户同时操作同一条数据**时，还需要锁来维持秩序。

### 表级锁：PG 自动加的四档锁

| 锁模式                  | 何时触发                      | 阻塞什么                   |
| -------------------- | ------------------------- | ---------------------- |
| Access Share         | SELECT 时自动获取              | 不阻塞读写，只阻塞改表结构          |
| Row Exclusive        | INSERT/UPDATE/DELETE 自动获取 | 允许并发读写同表不同行            |
| Share                | 创建索引时                     | 允许读，禁止改                |
| **Access Exclusive** | ALTER/DROP/TRUNCATE       | **最强锁，阻塞一切（含 SELECT）** |

### 行级锁：FOR UPDATE 解决「超卖」

只剩最后一个名额，两个用户同时下单怎么办？用 `FOR UPDATE` 锁定行：

```sql
BEGIN;
-- 锁定 id=100 的文档行：别人必须等我处理完（其他事务只能 SELECT，不能 UPDATE/DELETE）
SELECT * FROM documents WHERE id = 100 FOR UPDATE;

-- 检查剩余名额并扣减
UPDATE documents SET remaining = remaining - 1 WHERE id = 100;
COMMIT;   -- 释放锁
```

:::caution
不加 `FOR UPDATE` 的「先查后改」在高并发下必然翻车：两个事务同时读到 `remaining = 1`，各自减一，结果名额变成 -1。**`SELECT ... FOR UPDATE`** **是防超卖的标准写法，它在读取时就锁住行，别人改不了。**
:::

### 建议锁：PG 独有的「程序员的锁」

表锁、行锁都是数据库自动管理的。**建议锁（Advisory Lock）** 则是由程序员定义的一种逻辑锁——不锁表、不锁行，只是在内存里占一个「标识位」：

```sql
-- 获取一个编号为 12345 的逻辑锁
SELECT pg_advisory_lock(12345);
-- 执行你的业务逻辑...

-- 释放锁
SELECT pg_advisory_unlock(12345);
```

### 如何排查「数据库卡住」？

如果发现查询全部阻塞，用这张表查「谁在锁谁」：

```sql
SELECT *
FROM pg_locks l
JOIN pg_stat_activity a ON l.pid = a.pid;
```

## 四、用户与权限：告别「裸奔」

到目前为止，我们一直用超级管理员 `postgres` 在操作——这在生产环境里等于「开着 root 裸奔」。

### Role 与 GRANT 基础

```sql
-- 1. 创建一个组角色（默认不能登录）
CREATE ROLE managers;

-- 2. 创建一个登录用户
CREATE USER jeff_app WITH PASSWORD 'jeff_app_2026';

-- 3. 让用户加入组角色
GRANT managers TO jeff_app;
```

### 场景一：给「只读」的运营同学开账号

```sql
-- 1. 创建用户
CREATE USER reader_user WITH PASSWORD 'readonly_2026';

-- 2. 基础「进门权」：能连库、能进模式
GRANT CONNECT ON DATABASE jeff_kb TO reader_user;
GRANT USAGE ON SCHEMA public TO reader_user;

-- 3. 核心只读权：现有表 + 序列只读
GRANT SELECT ON ALL TABLES IN SCHEMA public TO reader_user;
GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO reader_user;

-- 4. 自动化：未来新建的表自动授予只读（关键！否则新表又没权限）
ALTER DEFAULT PRIVILEGES IN SCHEMA public
GRANT SELECT ON TABLES TO reader_user;
```

### 场景二：给「增删改查」的后端开发开账号

```sql
CREATE USER jeff_app WITH PASSWORD 'jeff_app_2026';

GRANT CONNECT ON DATABASE jeff_kb TO jeff_app;
GRANT USAGE ON SCHEMA public TO jeff_app;

-- 表的增删改查
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO jeff_app;

-- 【重点】序列必须给权限！否则无法执行自增 ID 的插入
GRANT USAGE, SELECT, UPDATE ON ALL SEQUENCES IN SCHEMA public TO jeff_app;

-- 新表自动授权
ALTER DEFAULT PRIVILEGES IN SCHEMA public
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO jeff_app;

ALTER DEFAULT PRIVILEGES IN SCHEMA public
GRANT USAGE, SELECT, UPDATE ON SEQUENCES TO jeff_app;
```

:::warning
**给应用账号授权时，序列（SEQUENCE）权限是最大的隐形坑。** 很多开发者只给表授权，结果应用一执行 INSERT 就报 `permission denied for sequence`——因为自增 ID 的生成依赖序列。一次 `GRANT USAGE, SELECT, UPDATE ON ALL SEQUENCES` 就能治好。
:::

## 五、备份与恢复：数据库的「保险单」

### pg\_dump：单库逻辑备份

`pg_dump` 把数据库的表结构、数据、序列、权限全部导成 SQL 脚本：

```bash
# 格式：pg_dump -U 用户名 -d 数据库名 > 备份文件.sql
pg_dump -U postgres -d jeff_kb > jeff_kb_0729.sql

# -t：只备份某张表    -n：只备份某个模式
pg_dump -U postgres -d jeff_kb -t documents > documents.sql
pg_dump -U postgres -d jeff_kb -n storage > storage_schema.sql

# -Fc：压缩二进制格式，体积小、支持并行恢复（推荐！）
pg_dump -U postgres -F c -d jeff_kb > jeff_kb_0729.bak
```

### pg\_restore：恢复二进制备份

```bash
# 恢复 .sql 纯文本备份：直接用 psql 执行
psql -U postgres -d jeff_kb < jeff_kb_0729.sql
# 注意：目标数据库要先创建好

# 恢复 .bak 压缩备份：必须用 pg_restore
pg_restore -U postgres -d jeff_kb -c jeff_kb_0729.bak
# -c：先清理旧对象再恢复，防止冲突
```

### pg\_dumpall：全库备份

想一次性带走**所有数据库 + 所有用户和权限**，用 pg\_dumpall：

```bash
# 设置环境变量避免每库输一次密码
set PGPASSWORD=root

pg_dumpall -U postgres > all_backup.sql

# 恢复：-f 指定脚本文件，先连默认库 postgres，脚本内部会建库切换
psql -U postgres -f all_backup.sql postgres
```

### 数据库安全铁律

**数据库安全，七分在习惯，三分在工具**。

1. **云服务器上的数据库绝不对外开放端口**，只允许内网/本机连接
2. **绝不用弱密码**，越复杂越好
3. **改掉服务器默认的 22 端口**（SSH），换成 10022 等非常规端口，防止端口扫描
4. **备份要养成习惯，且备份要放在别处**（异地/对象存储），防止连备份一起被删

:::important
`pg_dump` 是**逻辑备份**（导出 SQL），好处是易读、跨版本兼容；缺点是速度慢、不适合超大库。超大规模场景要用**物理备份**（直接拷贝数据目录，或使用 pg\_basebackup）。**备份的频率取决于你能接受丢失多少数据**——日备是底线，核心系统建议实时 PITR（时间点恢复）。
:::

## 六、扩展：全文搜索——不用 ES 也能搜

### 核心概念：tsvector 与 tsquery

```sql
-- tsvector：把文本分词并转换成「搜索向量」
-- 会自动：去标点、去停用词（the/is）、词干化（guides → guide）
SELECT to_tsvector('english', 'This is a comprehensive guide to PostgreSQL.');

-- tsquery：你的搜索关键词（| 表示 OR，& 表示 AND，! 表示 NOT）
SELECT to_tsquery('english', 'PostgreSQL | Guide');
```

### 一条完整的搜索

```sql
-- 建文章表
CREATE TABLE docs (
    id SERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    content TEXT
);

-- 搜索标题或正文包含 PostgreSQL 或 Guide 的文章
SELECT title, content
FROM docs
WHERE to_tsvector('english', title || ' ' || content) @@ to_tsquery('english', 'PostgreSQL | Guide');
```

### 预分词：性能的关键

上面那条 SQL 有个致命问题：**每次查询都在现场分词**，无法走索引，必然全表扫描。正确做法是「预分词」——插入时就算好向量存起来：

```sql
-- 1. 建表时加一个自动生成的向量列
-- 知识点：STORED 表示结果物理存储在硬盘上，而非查询时才计算
CREATE TABLE docs2 (
    id SERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    content TEXT,
    searchable_index_col tsvector
        GENERATED ALWAYS AS (to_tsvector('english', title || ' ' || content)) STORED
);

-- 2. 在这个列上建 GIN 索引（关键！没有索引 STORED 列也白搭）
CREATE INDEX idx_docs_search ON docs2 USING GIN (searchable_index_col);

-- 3. 插入时不用管向量列，数据库自动生成
INSERT INTO docs2 (title, content)
VALUES ('PostgreSQL Guide', 'This is a post about full-text search index.');

-- 4. 查询直接走索引
SELECT title, content
FROM docs2
WHERE searchable_index_col @@ to_tsquery('english', 'PostgreSQL');
```

### 中文分词：zhparser 扩展

PG 默认只支持英文分词，中文需要分词插件。最省事的方式是用社区预集成好的 Docker 镜像：

```bash
docker pull zhparser/zhparser:alpine-16
docker run -d --name pg-chinese -p 5432:5432 -e POSTGRES_PASSWORD=root zhparser/zhparser:alpine-16
```

```sql
-- 初始化配置（只需执行一次）
CREATE EXTENSION IF NOT EXISTS zhparser;
CREATE TEXT SEARCH CONFIGURATION chinese (PARSER = zhparser);
ALTER TEXT SEARCH CONFIGURATION chinese ADD MAPPING FOR n,v,a,i,e,l WITH simple;

-- 验证：能把「枫枫老师的 Go 语言教程」拆成词
SELECT to_tsvector('chinese', 'jeff 的 PostgreSQL 学习教程');
```

:::tip
**什么时候用 PG 全文搜索，什么时候上 ES？** 判断标准很简单：**数据量几百万以内、单机部署、事务一致性要求高**（数据更新后搜索立刻生效）——用 PG。需要分布式分片、大规模日志聚合分析——上 ES。我在 [数据库大盘点](../编程生涯数据库大盘点/) 里也强调过：中小规模搜索用 PG + GIN 完全够用。
:::

## 七、扩展：地理位置——用 SQL 算距离

### earthdistance：轻量距离计算

```sql
-- 1. 开启扩展（earthdistance 依赖 cube）
CREATE EXTENSION cube;
CREATE EXTENSION earthdistance;

-- 2. 计算两个经纬度坐标的距离（单位：米）
SELECT earth_distance(
    ll_to_earth(28.228, 112.937),   -- 岳麓山 (纬度, 经度)
    ll_to_earth(28.191, 112.971)    -- 五一广场
) AS distance_meters;
```

### 查「5 公里内的场地」

```sql
-- 假设用户当前位置 (28.23, 112.94)
SELECT
    venue_name,
    earth_distance(ll_to_earth(28.23, 112.94), ll_to_earth(lat, lng)) / 1000 AS distance_km
FROM venues
WHERE earth_box(ll_to_earth(28.23, 112.94), 5000) @> ll_to_earth(lat, lng)   -- 5000 米范围
ORDER BY distance_km ASC;
```

### PostGIS：专业级的「卫星测绘系统」

如果说 `earthdistance` 是只能算距离的「皮尺」，那 **PostGIS** 就是一套完整的「卫星测绘系统」——它让数据库真正理解空间几何关系，而不仅是存两个数字：

| 超能力    | 代表函数                                           | 应用                  |
| ------ | ---------------------------------------------- | ------------------- |
| 空间关系判断 | `ST_Contains` / `ST_Intersects` / `ST_Touches` | 判断坐标在多边形内、两航线是否交叉   |
| 几何计算加工 | `ST_Buffer` / `ST_Union`                       | 生成 500 米缓冲区、合并校区多边形 |
| 坐标系转换  | `ST_Transform(geometry, 4326)`                 | 解决 GPS/高德/百度的坐标偏移   |

:::note
地理场景的选型：只需要「算两点距离 + 圈范围」用 `earthdistance` 够了；要做区域判断、复杂几何运算，用 PostGIS。
:::

## 八、扩展：向量数据库——知识库接入 RAG

### 安装与基础使用

```bash
# 用官方预集成镜像，免去编译痛苦
docker pull pgvector/pgvector:pg16
docker run -d --name pg-vector -e POSTGRES_PASSWORD=root -p 15432:5432 pgvector/pgvector:pg16
```

```sql
-- 1. 开启扩展
CREATE EXTENSION IF NOT EXISTS vector;

-- 2. 创建向量字段（3 维示例）
CREATE TABLE test_vector (
    id serial PRIMARY KEY,
    embedding vector(3)
);

-- 3. 插入向量数据
INSERT INTO test_vector (embedding) VALUES ('[1, 2, 3]'), ('[4, 5, 6]');

-- 4. 余弦相似度查询（相似度越高排越前）
SELECT
    id,
    embedding,
    1 - (embedding <=> '[0, 2, 1]') AS similarity_score
FROM test_vector
ORDER BY similarity_score DESC;
```

### 三大距离操作符

| 操作符   | 计算方式              | 适用场景                            |
| ----- | ----------------- | ------------------------------- |
| `<=>` | 余弦距离（Cosine）      | **RAG 最常用**：只关注方向不关注长度，适合文本语义匹配 |
| `<->` | L2 距离（欧氏距离）       | 图像检索、需要数值绝对大小的场景                |
| `<#>` | 内积（Inner Product） | 推荐系统、Embedding 已归一化的场景          |

### RAG 的完整链路

```text
用户上传资料
    ↓
程序把资料切成文本块
    ↓
嵌入模型（如 BGE-M3）把文本块向量化
    ↓
向量 + 原文存入 PG（pgvector）
    ↓
用户提问 → 问题向量化 → 与库中向量相似度匹配
    ↓
取出最相关的几个文本片段
    ↓
原文片段 + 问题一起发给大模型 → 生成回答
```

:::tip
向量数据库的选型铁律我在 [数据库大盘点](../编程生涯数据库大盘点/) 说过：**你在哪个数据库生态里，先用它的向量能力**。用 PG 就上 pgvector，用 ES 就上 dense\_vector，用 Redis 就上 RediSearch。这些方案都扛不住了，才考虑单独的 Milvus 或 Pinecone。
:::

## 附录：疑惑深挖

### 深挖① EXPLAIN ANALYZE：查询优化的「终极测谎仪」

`EXPLAIN` 只给你看优化器的**猜测**（预估成本），`EXPLAIN ANALYZE` 会**真实执行一遍 SQL**，告诉你实际发生了什么。

| 维度       | EXPLAIN     | EXPLAIN ANALYZE |
| -------- | ----------- | --------------- |
| 是否执行 SQL | ❌ 不执行，只生成计划 | ✅ 真正执行          |
| 耗时       | 预估成本（抽象单位）  | **实际耗时**（毫秒）    |
| 行数       | 预估（可能偏差巨大）  | **真实行数**        |
| 适用场景     | 快速看是否走索引    | 精准定位慢 SQL 环节    |

#### 读执行计划的三要素

```sql
EXPLAIN ANALYZE SELECT * FROM documents WHERE doc_name = 'doc_999999.pdf';
```

```text
Index Scan using idx_doc_name on documents
  (cost=0.42..8.44 rows=1 width=106) (actual time=0.025..0.027 rows=1 loops=1)
  Index Cond: (doc_name = 'doc_999999.pdf'::text)
Planning Time: 0.085 ms
Execution Time: 15.712 ms
```

- **`actual time=0.025..0.027`**：第一个数是启动耗时（拿到第一条数据），第二个是总耗时
- **`rows=1`** **vs** **`rows=1`**：真实行数 vs 预估行数。**如果预估 1 行、实际 10000 行，说明统计信息过期，执行** **`ANALYZE documents;`**
- **`loops=1`**：节点执行次数。Nested Loop 里 loops 巨大通常是性能灾难

#### 常见「死刑判决书」：看到这些必死

- **`Seq Scan`（全表扫描）**：百万行数据没走索引，查一次扫一遍
- **`Filter`** **出现在** **`Seq Scan`** **下方**：说明索引没生效（操作符写错或类型不匹配）

#### BUFFERS：分清是 CPU 慢还是磁盘 IO 慢

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM documents WHERE doc_name LIKE '%手机%';
```

```text
Buffers: shared hit=2 read=5
```

- `hit=2`：数据在内存缓存中，极快
- `read=5`：数据在磁盘，需要读盘。`read` 数量巨大说明内存太小或索引不对

#### 致命陷阱：EXPLAIN ANALYZE 真的会改数据！

如果你对 INSERT/UPDATE/DELETE 执行 `EXPLAIN ANALYZE`，**数据会被真实修改且不会自动回滚**！正确做法是包在事务里：

```sql
BEGIN;
EXPLAIN ANALYZE DELETE FROM documents WHERE id = 1;
ROLLBACK;   -- 记得回滚，否则数据没了！
```

:::warning
**调优铁律**：只看 `Execution Time`，不要纠结 `Planning Time`；以**第一次冷查询**为准（第二次查询数据进了内存会虚快）；`EXPLAIN ANALYZE` 只对 SELECT 单独执行是安全的。
:::

### 深挖② 全文搜索 SQL 逐段拆解 + STORED 生成列

#### 逐段拆解那条搜索 SQL

```sql
WHERE to_tsvector('english', title || ' ' || content) @@ to_tsquery('english', 'PostgreSQL | Guide')
```

| 片段                                                    | 作用                                                                     |
| ----------------------------------------------------- | ---------------------------------------------------------------------- |
| `to_tsvector('english', title \|\| ' ' \|\| content)` | 把标题+正文拼成一个长字符串，转成「词汇倒排索引向量」                                            |
| `@@`                                                  | 全文搜索的匹配操作符：判断左边的向量是否包含右边的搜索条件                                          |
| `to_tsquery('english', 'PostgreSQL \| Guide')`        | 把搜索词转成标准语法，`\|` 是 OR，`&` 是 AND                                         |
| 词干化                                                   | `guides` 变成 `guide`，`running` 变成 `run`——搜 Guide 能命中 "I am guiding you" |

#### to\_tsquery 的「娇气」

`to_tsquery` 要求输入语法极其严格——`PostgreSQL Guide`（中间没运算符）会**直接报错**。用户搜索框场景要用更友好的函数：

| 函数                     | 行为                 | 适用        |
| ---------------------- | ------------------ | --------- |
| `plainto_tsquery`      | 自动把空格变 `&`，永不报错    | 用户输入一句话搜索 |
| `phraseto_tsquery`     | 匹配整个短语             | 精确短语搜索    |
| `websearch_to_tsquery` | 支持 `or`、`-` 等类百度语法 | 类搜索引擎体验   |

#### STORED 生成列的底层机制与代价

**写入时**：INSERT/UPDATE 立即执行 `to_tsvector`，把分词结果压缩写入硬盘（紧挨该行其他列）。**查询时**：直接读已存好的向量，不再读原文、不再现场分词。

但它是**空间换时间**，有三个代价：

| 代价   | 说明                                                 |
| ---- | -------------------------------------------------- |
| 磁盘翻倍 | 全文索引比原始文本大得多，`title + content` 10MB 可能膨胀到 30\~50MB |
| 写入变慢 | 每次插入/更新都要额外分词计算                                    |
| 语言写死 | `'english'` 写死后，要支持中文得加列或重建                        |

**STORED 生成列 vs 函数索引怎么选？**

| 对比 | STORED 生成列 + GIN          | 直接函数索引                 |
| -- | ------------------------- | ---------------------- |
| 优点 | 查询 SQL 简洁；可 SELECT 出向量做高亮 | 不占表行存储空间               |
| 缺点 | 表变胖，VACUUM/ANALYZE 压力大    | 查询必须原样复写函数表达式，写漏参数索引失效 |
| 推荐 | 复杂多字段联合搜索、查多写少（新闻/电商）     | 临时需求、对表大小敏感            |

### 深挖③ VACUUM：数据库的「清洁工」

#### 为什么需要 VACUUM：MVCC 的代价

PG 的 UPDATE/DELETE 不会立即物理删除旧数据，而是标记为**死元组（Dead Tuple）**——这就是 MVCC 实现「读写互不阻塞」的代价。放任不管会带来：

- **表膨胀（Bloat）**：磁盘文件持续变大
- **性能下降**：查询要扫描大量无用数据
- **事务 ID 回卷**：严重时数据库强制关闭（必须重启）

#### VACUUM vs VACUUM FULL

| 特性   | 标准 VACUUM                | VACUUM FULL     |
| ---- | ------------------------ | --------------- |
| 工作方式 | 标记死元组空间为**可复用**          | **重写整个表**，彻底压缩  |
| 锁表级别 | 非阻塞，可并发读写                | **排他锁**，期间表不可用  |
| 磁盘空间 | 不归还操作系统                  | 归还操作系统，文件物理缩小   |
| 执行速度 | 快                        | 极慢，且需要额外磁盘空间    |
| 使用场景 | **日常维护**（autovacuum 自动做） | **最后手段**（极端膨胀时） |

#### autovacuum：自动清洁工的触发公式

PG 从 8.1 起默认开启 autovacuum 守护进程，触发条件是：

```text
autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × 表大小
= 50 + 0.2 × 表行数（默认配置）
```

**当死元组数量超过这个值，autovacuum 就会清理该表。** 注意默认 `scale_factor = 0.2` 对大表太保守——1000 万行的表要攒 200 万死元组才触发。

```sql
-- 手动清理并更新统计信息（推荐定期执行）
VACUUM ANALYZE documents;

-- 查看详细清理过程（用于诊断）
VACUUM VERBOSE documents;
```

**调优建议**：对频繁更新的热表，单独调低 `scale_factor`（如 0.01），避免死元组堆积；SSD 上可调低 `autovacuum_vacuum_cost_delay` 让清理更快。

:::caution
**VACUUM FULL 是重型操作，会长时间锁表，应视为最后手段。** 需要更优雅地回收空间时，考虑 `pg_repack` 等第三方工具（在线重写表，不阻塞读写）。
:::
