## 第一章：设计模式入门——开启面向对象设计的大门

### 1.1 这篇文章不是"目录式"的罗列

说实话，市面上讲设计模式的文章一抓一大把，但大多数都是把23种模式挨个介绍一遍，配上UML图和代码示例就完事了。看完之后，脑子里还是一片混沌——知道了个名字，却不知道什么时候该用它。

这篇文章不同。它的定位是**个人学习总结与感悟**，核心是"用自己的话讲自己的理解"。我会结合《大话设计模式》书中的案例，用生活化的类比来解释抽象的概念，力求让"单例"、"工厂"、"策略"这些名词变得接地气。

:::note
如果你想系统学习设计模式的完整内容，推荐直接阅读程杰的《大话设计模式》。这本书通过"小菜"和"大鸟"的情景对话，把23种模式讲得深入浅出，是入门设计模式的绝佳选择。
:::

### 1.2 从"烂代码"说起——为什么需要设计模式？

在聊设计模式之前，先说说"烂代码"长什么样。我自己写业务代码时，最容易写出三种坏味道：

**重复代码**——这是最常见的"坏味道"。两个类有相似的代码逻辑，我懒得重构，直接复制粘贴。结果呢？当这个逻辑需要修改时，我得在五个地方改，改漏一个就出bug。这不是危言耸听，是我真实踩过的坑。

**僵硬代码**——代码改一处动全身。业务逻辑有个小变化，我得改一堆相关类，还要小心翼翼测试，生怕蝴蝶效应。这说明我的类之间耦合太紧，一个类的变化会牵连太多其他类。

**脆弱代码**——稍微加点新功能，整个架构就要推倒重来。说明我的设计没有考虑"扩展性"，每次需求变更都是灾难。

设计模式就是来解决这些问题的。它不是银弹，但它是前辈们踩过无数坑之后总结的最佳实践。遵循这些套路，我的代码就能更健壮、更易维护。

### 1.3 设计模式的诞生与体系

1994年，四位作者（GoF：Erich Gamma、Richard Helm、Ralph Johnson、John Vlissides）合著了一本书《Design Patterns: Elements of Reusable Object-Oriented Software》，首次系统性地总结了23种设计模式。

:::important
这23种模式按照解决的问题类型，分为三大类：

| 分类        | 核心目标            | 模式数量 |
| --------- | --------------- | ---- |
| **创建型模式** | 解决"对象如何创建"的问题   | 5种   |
| **结构型模式** | 解决"类/对象如何组合"的问题 | 7种   |
| **行为型模式** | 解决"对象如何交互"的问题   | 11种  |

:::

理解这个分类很重要。它不是随意划分的，而是按照"变化的点"来分类的——创建型模式封装的是"对象创建的变化"，结构型模式封装的是"对象组合的变化"，行为型模式封装的是"对象行为的变化"。

## 第二章：七大设计原则——模式的"内功心法"

在进入具体模式之前，必须先理解设计原则。这些原则是设计模式的"内功心法"，掌握它们才能真正理解模式的意图。

### 2.1 七大原则表格

| 原则 | 英文全称 | 一句话总结 | 核心思想 |
| --- | --- | --- | --- |
| **单一职责原则（SRP）** | Single Responsibility Principle | 一个类只做一件事 | 类的职责要单一 |
| **开闭原则（OCP）** | Open-Closed Principle | 对扩展开放，对修改关闭 | 宁可多写代码，不改原有代码 |
| **里氏替换原则（LSP）** | Liskov Substitution Principle | 子类可以透明替换父类 | is-a关系要纯粹 |
| **依赖倒置原则（DIP）** | Dependency Inversion Principle | 针对接口编程，而非实现 | 依赖抽象，不依赖具体 |
| **接口隔离原则（ISP）** | Interface Segregation Principle | 大接口拆成小接口 | 保持接口精简 |
| **迪米特法则（LoD）** | Law of Demeter | 只与直接朋友通信 | 减少不必要的依赖 |
| **合成复用原则（CRP）** | Composite Reuse Principle | 优先使用组合，而非继承 | has-a优于is-a |

### 2.2 原则解读

#### 单一职责原则（SRP）：每个类只做一件事

一个类应该只有一个引起它变化的原因。听起来简单，但实际写代码时很容易违背。比如：

```java
// 违反单一职责：一个类干了三件事
public class User {
    private String name;
    private String email;

    public void save() { /* 保存到数据库 */ }
    public void sendEmail() { /* 发送邮件 */ }
    public void exportReport() { /* 导出报表 */ }
}

// 符合单一职责：每个类只做一件事
public class User { /* 只管用户属性 */ }
public class UserRepository { /* 只管数据库操作 */ }
public class EmailService { /* 只管发邮件 */ }
public class ReportExporter { /* 只管导出 */ }
```

为什么要这么分？因为三个功能的需求变化频率可能不同——今天要改邮件格式，明天要换报表模板，后天要优化数据库。如果都写在一个类里，改一处可能影响另外两处。

#### 开闭原则（OCP）：对扩展开放，对修改关闭

这是设计模式的核心原则。想象一下，你写了一个计算器类，能做加减乘除。某天产品说"加个开平方功能"，你是直接改计算器类，还是写一个新类？

正确的做法是写新类。因为"修改原有代码"意味着可能引入新bug，而"添加新代码"是最安全的。

```java
// 修改前：每次加功能都要改这个类
public class Calculator {
    public int add(int a, int b) { return a + b; }
    // 产品：加个开平方
    public double sqrt(int a) { return Math.sqrt(a); } // 改了这个类！
}

// 修改后：扩展新功能，不动原有代码
public interface Operation {
    double execute(int a, int b);
}

public class AddOperation implements Operation {
    public double execute(int a, int b) { return a + b; }
}

// 加开平方？写一个新类，不动Calculator
public class SqrtOperation implements Operation {
    public double execute(int a, int b) { return Math.sqrt(a); }
}
```

#### 里氏替换原则（LSP）：子类可以替换父类

里氏替换原则的核心是：**子类必须能够替换父类**，而不破坏程序的正确性。听起来很理所当然，但实际很容易出问题。

```java
// 父类：正方形是特殊的矩形
public class Rectangle {
    protected int width;
    protected int height;

    public void setWidth(int w) { this.width = w; }
    public void setHeight(int h) { this.height = h; }
    public int getArea() { return width * height; }
}

// 子类：正方形
public class Square extends Rectangle {
    // 正方形的宽高必须相等
    @Override
    public void setWidth(int w) {
        this.width = w;
        this.height = w;  // 同时设置宽高
    }

    @Override
    public void setHeight(int h) {
        this.width = h;
        this.height = h;  // 同时设置宽高
    }
}
```

问题来了：如果有个方法接收Rectangle并设置不同的宽高：

```java
public void resize(Rectangle rect, int width, int height) {
    rect.setWidth(width);
    rect.setHeight(height);
}

// 调用
resize(new Square(), 5, 3);  // 正方形无法同时设置5和3
```

这就是违反里氏替换原则的典型案例。**正方形在数学上是矩形，但在"可变形"这个行为上不是**。正确的做法是不让Square继承Rectangle。

:::important
里氏替换原则提醒我们：继承不是"是"的关系，而是"行为"的关系。子类必须能完全替代父类，且不会破坏程序。
:::

#### 依赖倒置原则（DIP）：针对接口编程

高层模块不应该依赖低层模块，两者都应该依赖抽象。这听起来有点绕，但结合生活例子就很好理解：

"我要搬家，找搬家公司"——我依赖的是"搬家服务"这个抽象，而不是"某某搬家公司"这个具体实现。这样即使这家公司倒闭了，我换一个公司照样能搬家。

```java
// 坏的设计：高层依赖低层
public class UserService {
    private MySQLDatabase database; // 依赖具体实现
}

// 好的设计：两者都依赖抽象
public class UserService {
    private Database database; // 依赖抽象接口
    // MySQLDatabase、RedisDatabase都实现了Database接口
}
```

#### 接口隔离原则（ISP）：保持接口精简

接口隔离原则的核心是：**客户端不应该依赖它不需要的接口**。简单说就是"大接口拆小"。

```java
// 反例：一个大而全的接口
public interface Worker {
    void work();
    void eat();
    void sleep();
    void code();
}

public class Robot implements Worker {
    public void work() { /* 机器人工作 */ }
    public void eat() { }  // 机器人不需要吃东西
    public void sleep() { }  // 机器人不需要睡觉
    public void code() { /* 写代码 */ }
}
```

Robot被迫实现了两个完全不需要的方法。这就是接口设计得太大了。

```java
// 正例：拆成多个小接口
public interface Workable {
    void work();
}

public interface Eatable {
    void eat();
}

public interface Sleepable {
    void sleep();
}

// 人类：需要工作、吃饭、睡觉
public class Human implements Workable, Eatable, Sleepable {
    public void work() { }
    public void eat() { }
    public void sleep() { }
}

// 机器人：只需要工作
public class Robot implements Workable {
    public void work() { }
}
```

:::tip
接口隔离不是说接口越小越好，而是要保持"内聚性"——相关的行为放一起，不相关的行为分开。
:::

#### 迪米特法则（LoD）：只与直接朋友通信

"直接朋友"指的是当前对象直接使用的对象、当前对象的成员变量对象、当前对象创建的对象。如果一个类只是作为局部变量出现在方法中，它不是朋友。

```java
// 违反迪米特法则的例子
public class A {
    private B b;

    public void doSomething() {
        C c = b.getC();  // C是局部变量，不是A的直接朋友
        c.doSomething();  // A间接使用了C，产生了不必要的依赖
    }
}

// 符合迪米特法则的做法
public class A {
    private B b;

    public void doSomething() {
        b.doSomething();  // 只跟直接朋友B通信
    }
}
```

:::caution
违反迪米特法则的典型例子：类A需要类C的数据，但类A不直接持有类C，而是通过类B来获取。这样A和C就产生了间接依赖，增加了耦合。
:::

#### 合成复用原则（CRP）：优先使用组合

合成复用原则建议：**尽量使用对象组合/聚合，而不是继承关系来实现复用**。

为什么？继承虽然简单，但有两大缺点：
1. 继承是静态的，编译时就决定了
2. 子类必须继承父类的全部方法，即使大部分用不到

```java
// 反例：用继承实现复用——违反合成复用原则
public class Dog extends Animal {
    // Dog继承了Animal的所有方法，但可能不需要全部
}

// 正例：用组合实现复用
public class Dog {
    private Animal animal;  // 组合关系

    public Dog(String name) {
        this.animal = new Animal(name);
    }

    // 按需暴露需要的方法
    public String getName() {
        return animal.getName();
    }
}
```

组合的优势在于：**想用什么就组合什么，不用被迫继承不需要的东西**。

### 2.3 原则之间的关系

七大原则不是孤立的，它们相互关联、相互支撑。比如：

- 遵循**单一职责**，类就会更小、更专注，更容易符合**开闭原则**
- 遵循**合成复用**，用组合代替继承，就更容易符合**里氏替换原则**
- **依赖倒置**做得好，**接口隔离**自然就容易做到

这些原则是内功，模式是招式。内功深厚，才能灵活运用招式。

## 第三章：重点模式详解——高频使用的核心套路

这一章是本文的重点。我会深入讲解5种在实际项目中最常用的模式，配上代码示例和类比，确保你学完能用。

### 3.1 单例模式：全局唯一的对象

#### 问题场景

有些对象在整个程序运行期间只需要一个实例，比如配置管理器、数据库连接池、线程池。如果创建多个实例，反而会出问题（连接池创建多个会浪费资源）。

#### 解决方案

单例模式确保一个类只有一个实例，并提供一个全局访问点。

#### 七种写法对比

| 写法        | 线程安全 | 延迟加载 | 性能      | 推荐场景     |
| --------- | ---- | ---- | ------- | -------- |
| 饿汉式       | 安全   | 否    | 高       | 确定需要单例时  |
| 懒汉式（非同步）  | 不安全  | 是    | 高（但不安全） | 禁用       |
| 懒汉式（同步方法） | 安全   | 是    | 低       | 教学意义     |
| 同步代码块     | 不安全  | 是    | 中       | 禁用       |
| **双重检查锁** | 安全   | 是    | 高       | **生产推荐** |
| **静态内部类** | 安全   | 是    | 高       | **最佳推荐** |
| 枚举单例      | 安全   | 否    | 高       | 最安全      |

#### 双重检查锁写法

```java
public class Singleton {
    // volatile很重要：防止指令重排序
    private static volatile Singleton instance;

    private Singleton() {
        // 私有构造函数，防止外部 new
    }

    public static Singleton getInstance() {
        if (instance == null) {  // 第一次检查：避免不必要的同步
            synchronized (Singleton.class) {  // 加锁
                if (instance == null) {  // 第二次检查：确保只创建一次
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

:::important
双重检查锁的关键在于volatile。没有volatile，指令重排序可能导致instance引用已赋值但对象还没构造完成，另一个线程拿到的是"半成品"。
:::

#### 静态内部类写法（最佳）

```java
public class Singleton {
    private Singleton() {}

    // 静态内部类只在被调用时才加载，实现了延迟加载
    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}
```

这种方式利用了类加载机制——静态内部类不会随外部类加载而加载，只有调用getInstance时才会加载，而且类加载过程是线程安全的。

#### 防破坏

单例模式有两大"天敌"：反射和序列化。

```java
// 防反射：在构造函数中抛异常
private Singleton() {
    if (instance != null) {
        throw new RuntimeException("单例对象已存在，禁止通过反射创建！");
    }
}

// 防序列化：添加readResolve方法
private Object readResolve() {
    return instance;
}
```

### 3.2 工厂模式：对象的标准化生产

#### 问题场景

如果对象创建逻辑复杂，或者创建逻辑可能变化，把创建代码散落在各处会导致：代码重复、修改困难、不符合开闭原则。

#### 解决方案

工厂模式把对象创建封装起来，让调用者不需要知道对象是如何创建的。

#### 从简单到抽象的演进

**简单工厂**——一个工厂生产多种产品：

```java
// 违反开闭原则：加新产品要改工厂
public class SimpleFactory {
    public static Product create(String type) {
        if ("A".equals(type)) {
            return new ProductA();
        } else if ("B".equals(type)) {
            return new ProductB();
        }
        throw new IllegalArgumentException("不支持的产品类型");
    }
}

// 调用者
Product product = SimpleFactory.create("A");
```

**工厂方法**——每个产品一个工厂：

```java
// 符合开闭原则：加新产品只需加新工厂类
public interface Factory {
    Product create();
}

public class FactoryA implements Factory {
    public Product create() {
        return new ProductA();
    }
}

public class FactoryB implements Factory {
    public Product create() {
        return new ProductB();
    }
}

// 调用者
Factory factory = new FactoryA();
Product product = factory.create();
```

**抽象工厂**——生产一族产品：

```java
// 抽象工厂：生产一系列相关产品
public interface AbstractFactory {
    ProductA createProductA();
    ProductB createProductB();
}

// 工厂族1
public class Factory1 implements AbstractFactory {
    public ProductA createProductA() { return new ProductA1(); }
    public ProductB createProductB() { return new ProductB1(); }
}

// 工厂族2
public class Factory2 implements AbstractFactory {
    public ProductA createProductA() { return new ProductA2(); }
    public ProductB createProductB() { return new ProductB2(); }
}
```

:::tip
工厂方法的典型应用场景是跨平台UI——WindowsButtonFactory生产Windows风格按钮，MacButtonFactory生产Mac风格按钮，调用者不需要知道具体是哪个工厂。
:::

### 3.3 策略模式：算法的自由切换

#### 问题场景

商场促销活动五花八门：满100减20、打8折、买三送一。这些算法可能会经常变化，如果用if-else写死，修改一个算法可能影响其他算法。

#### 解决方案

策略模式定义一系列算法，把它们一个个封装起来，使它们可以相互替换。

```java
// 策略接口：定义算法的公共行为
public interface Strategy {
    double calculate(double price);
}

// 具体策略1：正常收费
public class NormalStrategy implements Strategy {
    public double calculate(double price) {
        return price;
    }
}

// 具体策略2：打折收费
public class DiscountStrategy implements Strategy {
    private double discount;

    public DiscountStrategy(double discount) {
        this.discount = discount;
    }

    public double calculate(double price) {
        return price * discount;
    }
}

// 具体策略3：返现收费
public class CashbackStrategy implements Strategy {
    private double threshold;
    private double cashback;

    public CashbackStrategy(double threshold, double cashback) {
        this.threshold = threshold;
        this.cashback = cashback;
    }

    public double calculate(double price) {
        if (price >= threshold) {
            return price - cashback;
        }
        return price;
    }
}

// 上下文：持有策略对象，调用者只跟上下文交互
public class Context {
    private Strategy strategy;

    public void setStrategy(Strategy strategy) {
        this.strategy = strategy;
    }

    public double calculate(double price) {
        return strategy.calculate(price);
    }
}

// 调用者：可以运行时切换策略
public class Cashier {
    public static void main(String[] args) {
        Context context = new Context();

        // 场景1：打8折
        context.setStrategy(new DiscountStrategy(0.8));
        System.out.println("打折后：" + context.calculate(100));  // 80

        // 场景2：满100返20
        context.setStrategy(new CashbackStrategy(100, 20));
        System.out.println("返现后：" + context.calculate(100));  // 80
    }
}
```

:::important
策略模式的核心是：**把"可以变化的算法"封装成独立的策略类，客户端可以在运行时切换策略**。这完美符合开闭原则——要加新算法，只需要添加新策略类，不需要修改已有代码。
:::

### 3.4 观察者模式：消息的广播站

#### 问题场景

想象一个场景：老板回来了，前台小妹要通知所有员工。传统做法是小妹挨个打电话。但如果员工数量多、通知逻辑复杂，这种做法就很难维护。

更好的做法是：员工主动订阅"老板回来"这个事件，前台只需要发布事件，所有订阅者自动收到通知。

#### 解决方案

观察者模式定义对象间的一对多依赖关系，当一个对象状态改变时，所有依赖它的对象都得到通知并自动更新。

```java
// 观察者接口：所有订阅者需要实现这个接口
public interface Observer {
    void update(String event);
}

// 具体观察者：员工
public class Employee implements Observer {
    private String name;

    public Employee(String name) {
        this.name = name;
    }

    public void update(String event) {
        System.out.println(name + "收到通知：" + event);
    }
}

// 被观察者接口：发布者需要实现这个接口
public interface Subject {
    void attach(Observer observer);  // 订阅
    void detach(Observer observer);  // 取消订阅
    void notifyAllObservers();      // 通知
}

// 具体被观察者：前台
public class Reception implements Subject {
    private List<Observer> observers = new ArrayList<>();

    public void attach(Observer observer) {
        observers.add(observer);
    }

    public void detach(Observer observer) {
        observers.remove(observer);
    }

    public void notifyAllObservers() {
        for (Observer observer : observers) {
            observer.update("老板回来了！");
        }
    }

    // 前台发布事件的方法
    public void bossComing() {
        System.out.println("前台：老板回来了！");
        notifyAllObservers();
    }
}

// 调用
public class Main {
    public static void main(String[] args) {
        Reception reception = new Reception();

        Employee alex = new Employee("Alex");
        Employee bob = new Employee("Bob");

        reception.attach(alex);  // 订阅
        reception.attach(bob);

        reception.bossComing();
        // 输出：
        // 前台：老板回来了！
        // Alex收到通知：老板回来了！
        // Bob收到通知：老板回来了！
    }
}
```

:::note
Java内置了观察者模式的支持——java.util.Observable和java.util.Observer。不过在JDK 9之后被标记为废弃，推荐使用PropertyChangeSupport或自己实现。
:::

### 3.5 装饰器模式：动态增强对象

#### 问题场景

咖啡店卖咖啡，顾客可以加牛奶、糖、巧克力等配料。如果用继承实现，每种组合都要写一个类：牛奶咖啡、糖咖啡、牛奶糖咖啡...组合爆炸。

更灵活的做法是：把"加配料"变成动态的行为，而不是固定的类。

#### 解决方案

装饰器模式动态地给对象添加一些额外的职责，比继承更灵活。

```java
// 组件接口：定义饮料的基本行为
public interface Drink {
    String getDescription();
    double getPrice();
}

// 具体组件：咖啡
public class Coffee implements Drink {
    public String getDescription() {
        return "咖啡";
    }

    public double getPrice() {
        return 20.0;
    }
}

// 装饰器基类：持有组件引用
public abstract class Decorator implements Drink {
    protected Drink drink;  // 被装饰的对象

    public Decorator(Drink drink) {
        this.drink = drink;
    }
}

// 具体装饰器：牛奶
public class MilkDecorator extends Decorator {
    public MilkDecorator(Drink drink) {
        super(drink);
    }

    public String getDescription() {
        return drink.getDescription() + " + 牛奶";
    }

    public double getPrice() {
        return drink.getPrice() + 5.0;  // 牛奶加5元
    }
}

// 具体装饰器：糖
public class SugarDecorator extends Decorator {
    public SugarDecorator(Drink drink) {
        super(drink);
    }

    public String getDescription() {
        return drink.getDescription() + " + 糖";
    }

    public double getPrice() {
        return drink.getPrice() + 2.0;
    }
}

// 调用：可以任意组合
public class Main {
    public static void main(String[] args) {
        // 一杯咖啡加牛奶加糖
        Drink coffee = new Coffee();
        coffee = new MilkDecorator(coffee);
        coffee = new SugarDecorator(coffee);

        System.out.println(coffee.getDescription());  // 咖啡 + 牛奶 + 糖
        System.out.println(coffee.getPrice());        // 27.0
    }
}
```

:::tip
装饰器模式和代理模式的区别在于意图：装饰器是为了**增强**对象功能，代理是为了**控制**对象访问。但两者结构相似，都是持有被包装对象的引用。
:::

## 第四章：其他模式速查——体系化梳理

除了上面5个重点模式，其余18种模式按照分类整理如下，每个模式用一段话概括核心要点。

:::note
创建型模式共5种，其中**工厂模式**（含简单工厂、工厂方法、抽象工厂三种）和**单例模式**已在第三章详解，本节仅补充剩余的2种。
:::

### 4.1 创建型模式（2种）

**建造者模式**：分步骤构建复杂对象，把"构建过程"和"表示"分离。就像买KFC套餐——主食、配菜、饮料分开点，最后组合成一个完整的套餐。适合对象属性多、创建逻辑复杂的场景。

**原型模式**：通过克隆已有对象来创建新对象，而不是从头开始创建。适合创建成本高、但对象结构相同且可复制的场景。Java中通过实现Cloneable接口实现浅克隆，深克隆需要自定义。

### 4.2 结构型模式（7种）

| 模式        | 核心要点                     | 经典案例                             |
| --------- | ------------------------ | -------------------------------- |
| **代理模式**  | 为对象提供代理，控制对原对象的访问        | 追求者通过闺蜜代理送礼物、延迟加载（图片懒加载）         |
| **适配器模式** | 把不兼容的接口转换成兼容的接口          | 电源适配器（220V转5V）、NBA翻译             |
| **外观模式**  | 为子系统提供统一的高层接口            | 基金投资（一键买入一篮子股票）、电脑开机按钮           |
| **桥接模式**  | 把抽象部分和实现部分分离，使它们可以独立变化   | 手机品牌（华为、小米）× 手机软件（游戏、导航）独立变化     |
| **组合模式**  | 把对象组合成树形结构，统一处理单个对象和组合对象 | 文件系统（文件夹和文件统一处理）、公司组织架构          |
| **享元模式**  | 运用共享技术有效支持大量细粒度对象        | 围棋棋子（颜色只有黑白两种，但位置不同）、文字编辑器（字符复用） |
| **装饰器模式** | 见3.5节重点讲解                | <br />                           |

### 4.3 行为型模式（11种）

| 模式         | 核心要点                     | 经典案例                          |
| ---------- | ------------------------ | ----------------------------- |
| **模板方法模式** | 定义算法骨架，把具体步骤延迟到子类        | 考试答题（题目顺序固定，每题解题方法不同）、冲泡饮料    |
| **状态模式**   | 对象行为随状态变化而变化             | 工作状态机（上班干活、午休吃饭、下班打卡）         |
| **命令模式**   | 把请求封装成对象，支持撤销、重做         | 遥控器按钮、数据库事务                   |
| **职责链模式**  | 让多个对象有机会处理请求，避免发送者和接收者耦合 | 加薪申请审批（组长→经理→总监）、异常处理链        |
| **中介者模式**  | 用中介对象封装一系列对象交互           | 联合国（各国不直接对话）、聊天室（用户通过聊天室转发消息） |
| **迭代器模式**  | 提供顺序访问聚合对象元素的方式          | 遍历ArrayList、遍历LinkedList      |
| **访问者模式**  | 把数据结构和操作分离               | 数据报表（同一个数据结构，不同的报表格式）         |
| **备忘录模式**  | 捕获对象状态，在外部保存并恢复          | 游戏存档、数据库事务回滚                  |
| **解释器模式**  | 定义语法并解释                  | 正则表达式、正则表达式引擎                 |

:::warning
访问者模式和解释器模式是23种模式中最复杂的两种，在实际项目中很少直接使用。如果遇到这类需求，通常会考虑引入专业的解析库（如ANTLR）而不是自己实现。
:::

## 第五章：学习指南与实践建议

### 5.1 学习顺序建议

设计模式不是一天能学完的，建议分三个阶段：

**第一阶段：入门（2-3个模式）**
从单例模式和工厂模式开始。这两个是实际项目中最常见的，理解它们能建立"封装变化"的基本意识。我当初学完这两个，就开始在项目中尝试用了——比如把数据库连接池改成单例，果然清爽了不少。

**第二阶段：进阶（6-8个模式）**
策略、观察者、装饰器、代理、模板方法、适配器。这时候你会开始感受到设计模式的"套路"——核心思想都是"封装变化"。当你能用自己的话解释为什么这个场景适合用这个模式，就说明真的理解了。

**第三阶段：完善（剩余模式）**
根据实际需要学习。做数据库相关项目时学建造者模式，做UI相关项目时学装饰器模式。23种模式不需要全部精通，但至少要知道它们的存在，遇到问题时能想到"这个问题可能有现成的解决方案"。

### 5.2 常见误区

**误区一：为了模式而模式**

这是最常见的问题。我见过有人对着5行的if-else硬要用策略模式重构，结果代码更复杂了。设计模式是解决问题的工具，不是目的。

:::caution
一个简单的if-else能解决问题，就不要硬上策略模式。评估标准是：重构后代码是否更清晰、扩展是否更方便、维护是否更简单。
:::

**误区二：把模式当成死的公式**

UML图是死的，业务场景是活的。照搬书上的代码不如理解模式的意图。比如单例模式，不一定要用"饿汉"或"双重检查锁"——如果有框架支持（如Spring默认就是单例），直接用框架的机制就行。

**误区三：忽略设计原则**

很多人在学模式时只记招式，不记心法。结果换了个场景就不知道怎么用，或者用了反而把代码搞复杂了。记住：**先问"什么会变"，再选择合适的模式**。

### 5.3 实践心得

学设计模式，最终目的是在真实项目中用起来。我的建议是：

1. **从重构开始**：不要一上来就想着用模式写新代码。先从"烂代码"重构入手，当你觉得"这段代码改起来真麻烦"的时候，设计模式可能就是解决方案。
2. **保持简单**：如果你用了模式，代码反而更复杂了，那可能用错了。好的设计应该让人一眼看出意图，而不是需要对照UML图才能理解。
3. **与其他知识形成网络**：设计模式不是孤立的。比如学完JVM后，我知道类加载器可能有单例需求；学完JUC后，我知道线程池内部用到了工厂模式和策略模式。知识串联起来，才算真正掌握。

:::tip
最后一句话与君共勉：**设计模式是前辈们踩坑后总结的最佳实践，但不是银弹。理解它的意图，在合适的场景使用，才能发挥价值。**
:::
