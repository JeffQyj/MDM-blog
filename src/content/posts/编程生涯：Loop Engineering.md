## 第一章：Loop Engineering 是什么

### 1.1 引爆瞬间

2026年6月初，Anthropic工程师、Claude Code创建者Boris Cherny在一次开发者大会上说了一段话，24小时内播放量逼近70万次：

> **「我不再给Claude写提示词了。我有一堆loop在运行，它们自己提示Claude、自己决定下一步该做什么。我的工作是写loop。」**

几乎同时，OpenClaw创始人Peter Steinberger发推，收获830万浏览：

> **「你不应该再给编程Agent写提示词了。你应该设计loop，让loop去提示你的Agent。」**

随后，Google Cloud AI总监Addy Osmani发表了长篇博客，系统性地将这个新范式命名为**Loop Engineering（循环工程）**，并拆解了它的六大组件。

这三个人的核心共识只有一个：**人的角色变了——从「提示词编写者」变成「循环设计师」。**

### 1.2 一句话定义

**Loop Engineering就是设计一套自动运转的循环系统，让AI自己发现任务、执行代码、验证结果、记录状态、决定下一步，直到达成你设定的目标。**

鱼皮在他的两篇深度解读里用了一个精准的比喻——以前开手动挡，每一步自己操作；现在开自动驾驶，你设定目的地就行。

Claude Code团队后来在官方博客中给出了更具体的定义：**循环就是让AI重复执行工作，直到满足某个停止条件。**

### 1.3 循环的三大核心

一个靠谱的Loop需要三个东西：

| 核心             | 说明                 | 反例                    |
| -------------- | ------------------ | --------------------- |
| **明确的目标和停止条件** | 完成标准必须可验证          | 「优化一下代码」不行，「所有测试通过」才行 |
| **反馈闭环**       | 每轮结束后检查结果，决定继续还是停止 | 让AI改完代码就跑，不管对不对       |
| **状态记忆**       | 跨轮次持久化进度，断点续跑      | 把状态存在对话窗口里，关掉就丢       |

### 1.4 四种循环类型

Claude Code官方博客把循环分为四层，从手动到自动逐级递进：

| 类型                   | 你交出什么 | 适合场景          | 对应工具                   |
| -------------------- | ----- | ------------- | ---------------------- |
| **手动循环**（Turn-based） | 验证环节  | 短任务、非固定流程     | 自定义Skills              |
| **目标循环**             | 停止条件  | 有明确完成标准的任务    | `/goal`                |
| **定时循环**             | 触发时机  | 周期性、依赖外部系统的任务 | `/loop`、`/schedule`    |
| **主动循环**（Proactive）  | 整个提示词 | 持续性、流程化的工作    | 以上全部+Dynamic Workflows |

源自Claude Code官方博客[Getting started with loops](https://claude.com/blog/getting-started-with-loops)，鱼皮做了中文深度解读。

### 1.5 范式演进链

Loop Engineering不是凭空冒出来的，它是AI编程范式持续演进的第四阶段：

```text
阶段一（2022-2024）：Prompt Engineering（提示词工程）
  → 核心：怎么写提示词让AI回答更好

阶段二（2025）：Context Engineering（上下文工程）
  → 核心：怎么在对的时候把对的信息喂给AI

阶段三（2026年初）：Harness Engineering（驾驭工程）
  → 核心：怎么给AI搭工具、写测试、设约束

阶段四（2026年中）：Loop Engineering（循环工程）
  → 核心：怎么让AI自己形成工作循环，自动推进
```

前三步是基础，Loop是建立在这个基础之上的「自动循环+反馈闭环」。

:::note
鱼皮也强调过：Loop不是取代提示词的，它是建立在提示词、上下文、Harness这些基础之上的。基础没打好就跑Loop，只会放大问题。
:::

## 第二章：拆开来看——不过是已有概念的重新组合

### 2.1 Addy Osmani 的六大组件

Addy Osmani把完整的Loop拆解为五个构建块加一个贯穿全程的外部记忆层：

| 组件                    | 作用          | 通俗类比     |
| --------------------- | ----------- | -------- |
| **Automations（自动调度）** | 定时/事件触发     | Loop的心跳  |
| **Worktrees（工作隔离）**   | 多Agent并行不冲突 | 每个人的独立工位 |
| **Skills（技能沉淀）**      | 可复用的项目知识    | 新同事的培训手册 |
| **Connectors（工具连接）**  | 打通外部系统      | AI的手和脚   |
| **Sub-agents（子代理互审）** | 写代码和审查分离    | QA和开发分开  |
| **Memory（状态记忆）**      | 跨轮次持久化      | 不能只靠脑子记  |

这个表格列出来，我横竖睡不着，越看越觉得——**这些东西我全都在别处见过。**

### 2.2 逐一回溯前身

**Automations（自动调度）** → cron、CI/CD、GitHub Actions

定时触发、事件驱动、自动执行——这不就是加强版的cron吗？`/loop 5m 检查部署状态`=cron加强版+AI外壳。`/schedule`云端任务=GitHub Actions Scheduled Workflow。

**Worktrees（工作隔离）** → git worktree

给每个Agent分配独立工作目录，互不干扰。当时我只是把它当git技巧在用，现在被包装成Loop Engineering的核心组件之一。

**Skills（技能沉淀）** → SKILL.md / CLAUDE.md

把项目知识和工作流程写成可复用的文档。mattpocock的12个活跃skill这么做，superpowers的14个核心skill也这么做。装在我Trae IDE里那60个skill文件，早在Loop Engineering这个名字出现之前就在跑了。

**Connectors（工具连接）** → MCP协议

MCP（Model Context Protocol）给AI接上文件系统、数据库、浏览器、Slack——Agent框架的标准配置。

**Sub-agents（子代理互审）** → Code Review流程

写代码的Agent和审查的Agent分开——不就是代码审查的工程化吗？我的`/review`命令派发两个并行子代理（standards轴+spec轴），`/fix`命令按审查报告逐条修复。审查者和执行者分离，这个模式在软件工程里存在了几十年。

**Memory（状态记忆）** → PROGRESS.md / 数据库

鱼皮在Cursor实战里用PROGRESS.md记录进度，说「中间断了重启也不会从零开始」。但我更往前追溯的话——[《命令工程之RAG项目实战》](../编程生涯命令工程之rag项目实战/)里，/plan输出的计划文档就是最原始的状态记忆：做完一个commit，划掉一项。

### 2.3 核心结论

> **Loop Engineering的六大组件，没有一个是2026年才发明的。**

那Loop Engineering到底「新」在哪里？

**新在组合方式，不是新在零件本身。**

这就是本章最想表达的观点——当你把一个新概念拆到最底层，你会发现每个零件都是你见过的东西。只是它们被重新命名、重新封装、重新打包了。

:::important
能看穿这一层的人，不会被任何新概念唬住。拆到零件层之后，剩下的问题只有一个：这个组合方式有没有价值？
:::

## 第三章：命令工程的影子——新概念的「似曾相识」

### 3.1 回看命令工程

我在[《命令工程与worktree全实战》](../编程生涯命令工程与worktree全实战/)里正式定义的「命令工程（Command Engineering）」，本质上也是在做同一件事：**把一组有内在逻辑关联的AI技能抽取为带明确意图的「命令」进行统一管理。**

命令工程的6个自定义命令，每一个都是已有概念的组合：

| 命令        | 组合了什么                               |
| --------- | ----------------------------------- |
| `/build`  | worktree隔离 + TDD + Code Review + 验证 |
| `/fix`    | 诊断 → 根因分析 → 修复 → 回归测试               |
| `/idea`   | 脑暴 + 领域建模                           |
| `/prd`    | 上下文抽取 + 用户故事 + 决策记录                 |
| `/review` | standards轴 + spec轴双轴审查              |
| `/ui`     | 设计方向 + 原型验证                         |

**命令工程本身也是「旧概念的组合」**——这个认识我早就写过。

### 3.2 两个工程的对照表

| 维度           | 命令工程                    | Loop Engineering         |
| ------------ | ----------------------- | ------------------------ |
| **核心思想**     | 把skill组合成命令接口           | 把组件组合成自动循环               |
| **组合方式**     | 按用户意图编排                 | 按系统逻辑编排                  |
| **强调什么**     | 简洁、引导、低约束               | 自主、反馈、闭环                 |
| **典型产出**     | /build→/fix→/review 协作链 | /goal→/loop→/schedule 循环 |
| **人扮演什么角色**  | 下游消费者                   | 上游设计者                    |
| **是否依赖前沿模型** | 否，重在组织方式                | 是，需要模型自主判断               |

两者底层逻辑一致——**都是把已有的零件组合成新的工作流。**

区别在于：命令工程面向「用户意图」，强调「我告诉AI做什么」；Loop Engineering面向「系统逻辑」，强调「我设计系统让AI自己决定做什么」。

但就像我在[《命令工程与worktree全实战》](../编程生涯命令工程与worktree全实战/)结尾写过的：**「所有概念都会消散」**——Loop Engineering也不会例外。

### 3.3 一个规律浮现了

当AI Agent的能力到了某个阈值，把已有能力「组合成更大的闭环」就成了一种必然趋势。每个人都会想到这件事，只是名字不一样。Boris Cherny叫它loop，Addy Osmani叫它Loop Engineering，我叫它命令工程。

**名字不一样，本质一样。**

当我说「命令工程 = Loop Engineering = 旧概念的重新组合」时，我不是在否定它们的价值，而是在给你一张**选型地图**：

```text
你追求的是「用户意图清晰、需要人参与的开发」
    → 用命令工程（/idea → /plan → /build → ...）

你追求的是「系统自主运转、减少人工干预」
    → 用 Loop Engineering（/goal → /loop → /schedule）

你想在两种模式之间切换
    → 命令工程做深度控制，Loop Engineering 做自动化闭环
```

选对工具，比用对工具更关键。

## 第四章：从概念到元概念——思维体系才是护城河

### 4.1 每年都有一个「新概念」

复盘我的学习路线：

- 2022年：手敲代码 —— 纯打基础
- 2023年：CV工程师 —— 学会了复制粘贴
- 2024年：Vibe Coding —— AI帮我写，我负责看
- 2025年：SDD（规格驱动开发） —— 先写规格再写代码
- 2026年2月：Harness Engineering —— 给AI搭工装
- 2026年6月：Loop Engineering —— 设计自动循环
- 2026年7月：**命令工程** —— 我自己的版本

每一年都有一个「新概念」出现，每个概念都号称是「终极方案」。但回顾一下就会发现，每个概念都在被下一个概念「兼容」。

**这不是概念的问题，这是概念的本质——所有新概念都是旧概念的重新组合，只不过组合之后发生了化学反应。**

### 4.2 关键能力不是「追新概念」

我在[《AI时代的学习方法论》](../成长碎记ai时代的学习方法论/)里写过一句话：「只要学得慢，那就不用学。」AI时代信息极大丰富，但认知极度稀缺。

放在概念追逐上也是一样的道理——**如果你每个新概念都追着学，你永远只是在学新概念。**

真正需要的能力是：

**不管别人提出什么方法论，你都能用自己的思维去剖析并内化。**

这就是我想强调的核心——**元思维**。

### 4.3 元思维、元概念、元方法论

| 层级       | 定义             | 在本文的体现                         |
| -------- | -------------- | ------------------------------ |
| **元思维**  | 解构任何方法论的能力     | 拆开Loop Engineering六大组件，发现全是旧零件 |
| **元概念**  | 看穿「新概念=旧组合」的规律 | 命令工程也好，Loop Engineering也好，本质相同 |
| **元方法论** | 沉淀属于自己的思维体系    | 用五步法解构一切新概念                    |

我在[《三元思维循环论》](../成长碎记三元思维循环论/)里讲过：洞察力、执行力、反思力构成一个思维闭环。元思维就属于洞察力——看见本质的能力。

而[《元学习的认知》](../成长碎记元学习的认知/)里的认知金字塔进一步揭示了这层关系：

```text
一通百通 ← AI到不了这里
    ↑
举一反三 ← AI能帮你，但需要你主导
    ↑
理解消化 ← AI能加速，但不能替代
    ↑
信息获取 ← AI碾压级优势
```

**元思维就是从「信息获取」往「一通百通」爬的能力。** 每爬上一层，你对外部「新概念」的依赖就少一分。

### 4.4 不要把概念追逐当学习

很多人把「我知道Loop Engineering」当成学习成果。但知道一个概念的名字和能解剖一个概念，是两回事。

「知道」只在信息获取层，搜一搜就能知道。但「解剖」需要在理解消化层——拆开组件、回溯前身、与你已有的认知对照、最后提炼出规律。

每次完成这种「解剖」，你都在往自己的思维体系里加一块砖。积少成多，你的体系越来越完整，新概念对你的冲击力越来越小——**因为你已经能用自己的体系消化它。**

:::important
追逐概念的人永远追不上——因为总有一个更新的概念在等着你。建立体系的人不需要追——因为任何新概念都能被拆解、被内化、被沉淀到自己的体系里。
:::

## 第五章：实战示范——我是怎么解剖 Loop Engineering 的

把我解剖Loop Engineering的全过程拆开给你看，每一步都对应前面讲的「元思维」的具体操作。

### 五步解剖法

| 步骤             | 做什么        | 产出                                         |
| -------------- | ---------- | ------------------------------------------ |
| **第一步：找定义**    | 找出公认的核心定义  | Boris / Peter / Addy 的原话                   |
| **第二步：拆组件**    | 列出功能模块     | 六大组件清单                                     |
| **第三步：回溯前身**   | 每个组件之前在哪见过 | cron、git worktree、SKILL.md、MCP、Code Review |
| **第四步：对照已有认知** | 与命令工程对比    | 本质相同，视角不同                                  |
| **第五步：提炼元规律**  | 从个例到普适规律   | 所有新概念=旧概念的组合                               |

### 第五步是最关键的一步

前四步做完，你只是「理解了一个概念」。但第五步才是质变——**从「理解了Loop Engineering」变成「理解了概念的底层规律」。**

一旦提炼出这个元规律，你会发现它可以套用到几乎所有「新概念」上：

| 新概念                 | 拆开看（旧零件）                                           | 新在哪里 |
| ------------------- | -------------------------------------------------- | ---- |
| Loop Engineering    | cron + git worktree + SKILL.md + MCP + Code Review | 组合方式 |
| 命令工程                | brainstorming + tdd + code-review + worktree       | 组合方式 |
| Harness Engineering | 工具封装 + 沙箱 + 约束规则                                   | 组合方式 |
| MCP协议               | Function Calling + API网关 + 插件系统                    | 组合方式 |

**每个「新概念」都可以用这个五步法解剖。** 解剖完之后，你不再需要「学」它——因为你已经用自己的思维体系消化了它。

:::tip
这就是元思维的力量：不是每个新概念来了都从头学，而是用一个统一的框架去解剖它、理解它的位置、然后决定要不要吸收它。
:::

## 第六章：AI时代的护城河到底是什么

### 6.1 什么不是护城河

我在[《AI时代的协作方法论》](../编程生涯ai时代的协作方法论/)里写过八条法则，其中「计算机基础是杠杆的支点」提到了算法边界、判断力审美、抽象层次。

顺着这个思路往下想——AI时代，什么东西真正不可替代？

- **不是技能数量** —— AI能写代码，能写所有语言的代码
- **不是知识广度** —— AI什么都知道，你能记住的不如它多
- **不是手速效率** —— AI比你快100倍，还不用睡觉

那到底是什么？

### 6.2 三种真正稀缺的能力

**判断力** —— 知道哪些概念值得深究，哪些只是包装。

Loop Engineering用了三个月火遍全网，但有多少人停下来问过：「它解决了什么之前解决不了的问题？它和Harness Engineering到底有什么区别？」

没有判断力的人，会被每一个新概念牵着走。

**解构力** —— 能快速拆解任何新概念，找到本质。

本文做的这件事就是解构力——不把Loop Engineering当成圣经去背诵，而是拆开来看它的每一个零件，回溯每一个零件的出身。

**沉淀力** —— 把每次「看懂一个新概念」都变成自己思维体系的一块砖。

我在[《AI时代的协作方法论》](../编程生涯ai时代的协作方法论/)最后列了八条法则，每条背后都对应具体的操作。后来为什么能快速解剖Loop Engineering？因为命令工程、三元思维循环论、元学习的认知——这些已经被我沉淀到思维体系里的砖，砌在一起刚好能「接住」这个新概念。

### 6.3 让概念追不上你

我发现一个有趣的现象：

2024年学Prompt Engineering的人，2025年在学Context Engineering。
2025年学Context Engineering的人，2026年在学Harness Engineering。
2026年学Harness Engineering的人，现在在学Loop Engineering。

**追概念的永远在追。** 因为总有一个「下一概念」在前面。

但如果你的注意力不在「学概念」，而在「建体系」——

你会发现自己越来越不用「学」了。每次新概念来了，你花10分钟解剖一下，发现又是旧零件的新组合。然后把它放到你的体系里，继续做你的事。

:::warning
追概念是增量竞争——永远有下一个。建体系是存量竞争——每沉淀一次，体系就完整一分。长期来看，存量的复利远大于增量的焦虑。
:::

### 6.4 对抗性审查：别把「组合创新」不当创新

写到这里，我需要对自己做一次对抗性审查。

:::caution
如果因为看到「Loop Engineering的零件都是旧的」，就得出「Loop Engineering没有价值」的结论——那你和那些看到新概念就无脑追捧的人，犯了同样程度的错。一个说「全是新的」，一个说「全是旧的」——两边的判断都过于简单。
:::

Loop Engineering的价值恰恰在于**组合本身**。

cron存在了几十年，git worktree存在了十几年，Code Review存在了更久——但从来没有人把它们和AI Agent串成一个自动循环系统。把已有零件组合成新系统，这是工程创新的经典范式：Unix管道也是组合（每个命令单一职责，管道把它们串起来），Kubernetes也是组合（容器编排=容器+调度+网络）。

**拆开看全是旧的，但组合在一起就是新的。**

Loop Engineering真正的创新不在于发明了新零件，而在于找到了一个让AI持续自主运转的「编排方式」。这一点需要被明确承认。

但这个承认并不影响我的核心结论：**能看穿「新概念=旧组合」的人，在任何新概念面前都有主动权。** 他们不会被唬住，不会盲目追捧，也不会简单否定——他们会解剖、会评估、会决定吸收还是跳过。

## 写在最后：沉淀到自己的思维论里

我在[《命令工程与worktree全实战》](../编程生涯命令工程与worktree全实战/)结尾写过一句话：

> **「AI越来越强，工作流概念越来越轻。也许有一天，连『命令』都不需要。」**

现在我可以把这句话升级一下：

**概念会消散，但沉淀到自己思维体系里的东西不会。**

Loop Engineering也好，命令工程也好，不管明年又冒出来什么Engineering——它们都只是特定时间窗口下，对已有能力的一种特定组合方式。明年会有新的组合，后年会有更新的组合。

这没有错。组合本身就是创新。

但你需要问自己的不是「我该怎么学这个新概念」，而是**「我该如何建立一个不管什么新概念来了都能快速解剖的思维体系」**。

答案就是我在本文反复说的三样东西：

- **元思维** —— 解构一切的方法论
- **元概念** —— 看穿「新概念=旧组合」的规律
- **元方法论** —— 沉淀属于自己的思维体系

AI时代真正的护城河，不在你追赶了多少个新概念，而在你沉淀了多少层自己的思维。
