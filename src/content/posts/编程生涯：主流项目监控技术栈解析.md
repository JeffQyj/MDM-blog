## 一、可观测性：监控的"上位概念"

在动手选型之前，我们得先搞清楚一个根本问题：**可观测性到底是个啥？**

### 1. 基本定义

可观测性（Observability）这个概念最早来自控制论，工程师们用它来描述**通过系统外部输出推断其内部状态的能力**。在软件工程里，它被借用来表达：通过**日志、指标、追踪**这三类数据，全面感知系统运行状况，从而实现问题的提前发现与快速定位。

这里有一个非常重要的辨析：

:::note
**可观测性 ≠ 监控**。监控是可观测性的子集——可观测性覆盖了从数据采集、存储、分析到告警的全链路，更强调对系统内部状态的"深度洞察"；而传统的监控更像是"哨兵"，只负责发现明显异常。
:::

用一句通俗的话来类比：

| 系统       | 类比                 | 关注重点               |
| -------- | ------------------ | ------------------ |
| **监控**   | 体温计                | 告诉你"发烧了"，但不知道为什么   |
| **可观测性** | 体检三件套（血常规+CT+病历追踪） | 不光能发现异常，还能告诉你"为什么" |

### 2. 维度 vs 指标：最容易混淆的一对概念

刚接触监控时，"维度"和"指标"两个词我老是分不清。后来发现，它俩的关系其实就是\*\*"标签"和"数值"\*\*的区别。

| 概念                | 定义           | 关注点   | 示例                                                           |
| ----------------- | ------------ | ----- | ------------------------------------------------------------ |
| **维度（Dimension）** | 描述和分类数据的标签属性 | "是什么" | `user_id=12345`、`app_id=67890`、`model_name=deepseek-chat`    |
| **指标（Metric）**    | 用于量化的数值数据    | "有多少" | `requests_total=100`、`response_time=1.5s`、`tokens_used=2000` |

**核心区别**：维度是可筛选的标签，指标是可计算的数值。这个区别在设计 Grafana 看板时尤其重要——维度决定了你能怎么"切"，指标决定了你能"算"什么。

### 3. 监控数据的四大分类

可观测性体系里，数据通常被分为四大类，每一类解决的问题都不一样：

| 分类                    | 定义            | 示例                           |
| --------------------- | ------------- | ---------------------------- |
| **系统指标**              | 基础设施层面数据      | CPU 使用率、内存占用、磁盘 I/O、网络流量     |
| **应用指标**              | 应用层面性能数据      | 接口响应时间、QPS、错误率、JVM 状态        |
| **业务指标**              | 与业务逻辑强相关的数据   | AI 模型调用次数、Token 消耗量、用户活跃度    |
| **调用链（Trace & Span）** | 分布式系统中请求的流转路径 | Trace = 完整请求，Span = 链中独立操作单元 |

调用链这块要特别说明一下，**Trace 和 Span 是个"父子包含"关系**——一个 Trace 代表一个完整请求的全链路，里面包含若干个 Span；每个 Span 代表调用链中的一个独立操作单元（比如一次 HTTP 调用、一次数据库查询、一次 AI 模型调用）。它的最大价值是：**在微服务架构下，能清晰展示请求在系统中的流转过程，快速定位性能瓶颈和错误节点**。

之前我写过 [ELK 技术栈——日志处理的瑞士军刀](https://blog.madm葚至.top/posts/编程生涯：ELK技术栈——日志处理的瑞士军刀) 那篇文章，ELK 解决的核心是**日志维度**的问题；而本文要重点讲的 Prometheus 和 LGTM 栈，则在**指标**和**调用链**维度上各显神通。它们之间不是替代关系，而是**互补关系**——这也是为什么很多人会把 ELK 和 Prometheus 一起用。

### 4. 百分位数：P50、P90、P99 到底是个啥

聊监控数据时，还有一个绕不开的概念——**百分位数**。它比"平均值"更能真实反映系统性能：

| 百分位          | 含义              |
| ------------ | --------------- |
| **P50（中位数）** | 50% 的请求响应时间低于该值 |
| **P75**      | 75% 的请求响应时间低于该值 |
| **P90**      | 90% 的请求响应时间低于该值 |
| **P99**      | 99% 的请求响应时间低于该值 |

:::note
**为什么 P99 这么重要？** 举个例子：若接口 P99 响应时间为 500ms，意味着 99% 的用户体验良好，但仍有 1% 的用户需要等待超过 500ms。在大流量场景下，这 1% 可能是几千几万人，他们感受到的卡顿往往是开发同学感受不到的。**P99 指标能有效发现系统中的"长尾延迟"问题（偶发的慢请求），这些问题往往是影响用户体验的关键因素。**
:::

平均值是个"骗子"——它会被极端值拉高或拉低，掩盖真实的用户体验。P99 才是真正反映"糟糕体验"的关键指标。

## 二、可观测性体系构建四步法

知道了可观测性是什么，下一个问题就是：**怎么构建一个完整的可观测性体系？**

业界主流的做法是回答四个核心问题：

| 核心问题      | 答案要点                | 常用技术                               |
| --------- | ------------------- | ---------------------------------- |
| **统计什么？** | 通用指标 + 业务特有指标       | ARMS / Prometheus 指标体系             |
| **如何收集？** | 代码埋点、探针技术、日志分析      | Java Agent / Micrometer / Exporter |
| **如何存储？** | 监控数据特点：量大、时序性强、写入频繁 | 时序数据库（Prometheus / Mimir）          |
| **如何展示？** | 直观图表 + 仪表板 + 实时刷新   | Grafana / Kibana                   |

### 1. 统计什么？——指标设计原则

设计监控指标有一个黄金法则：**通用指标 + 业务特有指标**。

- **通用指标**：覆盖系统和应用层面的标准监控项（CPU、内存、QPS、错误率等），这部分是"标配"
- **业务指标**：根据平台特性定制，比如 AI 平台要监控 Token 消耗、模型调用成功率等

:::important
**指标设计的反模式**：堆砌过多指标。监控指标的"贵"在于存储和查询成本，不是定义本身。设计指标时要问自己："这个指标出问题会怎样？我会怎么行动？"如果答不上来，就先不要埋。
:::

### 2. 如何收集？——三种主流方式

数据收集方式主要有三种，各有适用场景：

| 方式       | 侵入性       | 灵活性 | 适用场景      |
| -------- | --------- | --- | --------- |
| **代码埋点** | 高（要改业务代码） | 最高  | 业务特有指标    |
| **探针技术** | 无侵入       | 中等  | 系统 + 应用指标 |
| **日志分析** | 低         | 中等  | 错误、异常链路   |

代码埋点的灵活性最高，可以精准采集业务指标；探针技术（如 Java Agent）则是"无侵入式"采集的典型代表，JVM 启动时自动加载代理，对业务代码零污染。这个稍后讲 ARMS 时会重点展开。

### 3. 如何存储？——为什么不是 MySQL

很多人第一反应是用 MySQL 存监控数据，但这条路是错的——MySQL 不是为监控场景设计的。

| 存储方案              | 优点            | 缺点          |
| ----------------- | ------------- | ----------- |
| **MySQL**         | 简单易用，复杂 SQL 强 | 频繁写入严重影响性能  |
| **Elasticsearch** | 全文检索强         | 存储成本高，时序处理弱 |
| **Prometheus**    | 专为时序数据优化      | 不适合存原始日志    |

**结论**：专业的事交给专业的中间件，监控数据就交给时序数据库。

### 4. 如何展示？——可视化是最后一公里

数据采集、存储做得再好，看不到等于零。展示这一环要解决三个问题：

- **直观**：一眼能看懂趋势和异常
- **实时**：支持自动刷新，及时发现问题
- **可下钻**：能从总览钻到明细（这正是 Grafana 关联可观测性的杀手锏）

:::important
**四步法是顺序关系**：先想清楚要统计什么，再决定怎么收集，存储方式要匹配数据特征，最后用合适的可视化工具呈现。**颠倒顺序（比如先选工具再想指标）会导致返工。**
:::

## 三、四大主流方案横评：选型不再纠结

讲完理论，终于到了激动人心的"选型"环节。当前业界主流的项目监控方案可以归为四大类，每一类都各有特色。

### 1. 方案一：阿里云 ARMS（商业 SaaS）

**ARMS（Application Real-Time Monitoring Service）** 是阿里云提供的应用实时监控服务，核心优势是**无侵入式监控**——采用探针技术（Java Agent），在不修改任何应用代码的情况下，自动收集和分析应用性能数据。

```
ARMS 核心能力一览：
┌──────────────────────────────────────────┐
│  ✓ 系统性能：CPU/内存/线程/GC/连接池状态     │
│  ✓ 应用指标：请求数/错误数/平均耗时         │
│  ✓ 高级能力：调用链追踪/异常诊断/根因定位    │
│  ✓ 告警体系：短信/电话/钉钉/邮件通知        │
└──────────────────────────────────────────┘
```

**适用场景**：

- 企业级项目，需要快速上线的项目
- 不想投入过多运维资源的团队
- 项目初期，先解决"有没有监控"的问题

**核心优势**：5 分钟接入，开箱即用，运维成本为 0

### 2. 方案二：Prometheus + Grafana（开源单点）

这是目前最主流的开源监控组合，特点是"**一个组件解决一个维度**"：

- **Prometheus**：时序数据库，专门存指标
- **Grafana**：可视化平台，把数据变成图表

**适用场景**：

- 需要深度定制业务指标的项目
- 对数据隐私有要求（数据自主可控）
- 技术能力较强的团队
- 与 ARMS 共存：ARMS 负责系统监控，Prometheus 负责业务监控

### 3. 方案三：Grafana LGTM 栈（云原生全栈）

LGTM 是 Grafana Labs 推出的**云原生全栈可观测性套件**，每个组件专注解决一个维度，通过 Grafana 实现统一可视化：

- **Loki**：日志聚合系统
- **Grafana**：统一可视化平台
- **Tempo**：分布式追踪系统
- **Mimir**：可扩展的 Prometheus 兼容时序数据库

这个方案稍后会用独立章节详细讲，因为它代表了"云原生可观测性"的未来方向。

### 4. 方案四：Apache SkyWalking（国产 APM）

**SkyWalking** 是国产开源的应用性能监控(APM)系统，专注于分布式系统的链路追踪和性能分析，是国内微服务领域最受欢迎的开源监控方案之一。

它和 ARMS 类似，基于 **Java Agent 探针技术**实现无侵入式监控，同时支持 Go、Python、Node.js、C# 等多种语言。探针在应用启动时自动加载，自动采集应用的调用链路和性能数据。

**适用场景**：

- 微服务架构（自动发现服务、生成调用拓扑图）
- 国产化要求（中文文档友好）
- 中小规模部署（单节点即可满足需求）

### 5. 全面对比表

为了方便选型，我把这四个方案做成对比表：

| 对比维度      | 阿里云 ARMS         | Prometheus+Grafana | Grafana LGTM 栈 | Apache SkyWalking |
| --------- | ---------------- | ------------------ | -------------- | ----------------- |
| **产品类型**  | 商业 SaaS          | 开源自托管              | 开源自托管          | 开源自托管             |
| **核心优势**  | 开箱即用             | 灵活可定制              | 功能最全           | 国产友好，微服务支持好       |
| **侵入性**   | 无侵入 (Java Agent) | 部分侵入（需埋点）          | 部分侵入（需埋点）      | 无侵入（多语言 Agent）    |
| **覆盖维度**  | 指标+链路+部分日志       | 指标为主               | 指标+日志+链路       | 链路+指标+集成日志        |
| **学习曲线**  | 平缓               | 中等                 | 陡峭             | 中等                |
| **运维成本**  | 极低               | 中等                 | 极高             | 中等                |
| **成本**    | 按量付费，有免费额度       | 免费（仅服务器成本）         | 免费（仅服务器成本）     | 免费（仅服务器成本）        |
| **数据可控性** | 数据存储在阿里云         | 完全自主可控             | 完全自主可控         | 完全自主可控            |
| **官方支持**  | 阿里云技术支持          | 社区支持               | 社区支持           | 社区支持+商业支持         |

### 6. 选型建议

我个人的选型思路是这样的：

| 阶段        | 推荐方案               | 理由                               |
| --------- | ------------------ | -------------------------------- |
| **快速上线**  | 阿里云 ARMS           | 分钟级快速接入，先解决"有没有"的问题              |
| **业务发展**  | Prometheus+Grafana | 监控 AI 平台特有业务指标（Token 消耗、模型调用成功率） |
| **微服务架构** | SkyWalking         | 分布式追踪能力非常有价值                     |
| **大规模部署** | LGTM 栈             | 成本优势和可扩展性凸显                      |

:::tip
**对于大多数非企业级项目**：直接利用数据库和日志进行业务指标统计即可满足需求，**避免过度设计增加成本和复杂度**。监控不是越多越好，而是"刚刚好"最妙。
:::

## 四、Prometheus 核心原理：拉取模式的艺术

四大方案里，Prometheus+Grafana 组合最常被讨论，也是我这次学习的重点。下面我们深入剖析一下 Prometheus 的核心原理。

### 1. Prometheus 是什么

Prometheus 是一个**开源的监控系统和时序数据库**，专门为时序数据的收集、存储和查询而设计。

- 核心理念：将所有监控数据以**时间序列**的形式存储
- 数据模型：每个时间序列由**指标名称**和一组**键值对标签**唯一标识
- 示例：`ai_model_requests_total{model="deepseek-chat", user_id="12345"} 100`
- 优势：能够高效处理时间范围查询，如"过去一小时内各个模型的平均响应时间"

### 2. 核心组件架构

Prometheus 采用模块化架构，各组件职责明确：

```
Prometheus 核心组件：
┌────────────────────────────────────────────────┐
│                                                │
│   ┌──────────────┐    ┌──────────────────┐    │
│   │  Prometheus  │    │   Alertmanager   │    │
│   │    Server    │    │   (告警管理器)    │    │
│   │  (核心)      │    └──────────────────┘    │
│   └──────┬───────┘                             │
│          │ 定期拉取(Pull)                        │
│          ↓                                      │
│   ┌──────────────┐    ┌──────────────────┐    │
│   │  Exporter    │    │  客户端库(SDK)    │    │
│   │  (导出器)    │    │  (代码埋点)       │    │
│   └──────────────┘    └──────────────────┘    │
│                                                │
└────────────────────────────────────────────────┘
```

| 组件                    | 职责                               |
| --------------------- | -------------------------------- |
| **Prometheus Server** | 核心，负责数据收集、存储和查询                  |
| **Exporter**          | "翻译器"，将第三方系统的指标转换为 Prometheus 格式 |
| **Alertmanager**      | 处理告警规则和通知分发                      |
| **客户端库**              | 提供 SDK，方便开发者在应用代码中埋点             |

### 3. 拉取模式：与消息推送的本质区别

Prometheus 最核心的特征是采用\*\*拉取模式（Pull）\*\*收集数据，而不是由应用主动推送（Push）：

```
拉取模式工作流程：
Prometheus Server ──── HTTP GET ────→ 应用 /metrics 端点
                ←─── 指标数据 ─────
                  定期（如 15 秒一次）
```

**拉取模式的优势**：

| 优势          | 说明                               |
| ----------- | -------------------------------- |
| **简单可靠**    | 基于标准 HTTP 协议，无需复杂的消息队列或特殊网络配置    |
| **解耦业务与监控** | 监控数据推送失败不会影响业务逻辑的正常运行            |
| **便于调试**    | 可以直接通过浏览器访问 `/metrics` 端点查看当前指标值 |
| **服务发现灵活**  | 支持服务发现机制自动发现新的监控目标               |

### 4. Jobs 和 Instances

Prometheus 中有两个核心概念：

- **Instance**：一个被监控的目标，通常对应一个应用实例
- **Job**：一组相同类型的 Instances，如"ai-code-platform"

Prometheus 抓取数据时，会自动为每个时间序列添加 `job` 和 `instance` 标签。同时生成两个元指标：

- `up`：目标是否可达（值为 1 表示在线，0 表示离线）
- `scrape_duration_seconds`：抓取耗时

这俩元指标特别有用——`up==0` 直接说明目标挂了，`scrape_duration_seconds` 飙升则说明抓取本身变慢（可能网络有问题）。

### 5. 四种核心指标类型

Prometheus 提供了四种核心指标类型，每种都针对不同的监控场景进行了优化：

| 指标类型               | 特点                         | 适用场景                 | AI 平台示例                 |
| ------------------ | -------------------------- | -------------------- | ----------------------- |
| **Counter（计数器）**   | 累积计数器，只能增加或重置为零            | 统计单调递增的指标            | 模型调用总次数、Token 总消耗量      |
| **Gauge（仪表盘）**     | 数值可以任意上下波动                 | 记录当前状态值              | 当前在线用户数、内存使用量           |
| **Histogram（直方图）** | 统计数据分布，自动生成桶计数、总和和总数       | 观察响应时间等数据的分布         | 模型响应时间分布，计算 P50/P90/P99 |
| **Summary（摘要）**    | 与 Histogram 类似，但客户端预计算百分位数 | 需要精确百分位数且对网络传输有要求的场景 | 极少使用，一般优先用 Histogram    |

**最佳实践**：

- 优先使用 Counter 和 Gauge，存储和查询效率最高
- 响应时间等需要了解分布的指标，使用 Histogram
- 避免滥用 Summary，因为它无法进行聚合计算

### 6. 存储机制

Prometheus 拥有自己的**高性能时序数据库（TSDB）**，单节点就能处理数百万个时间序列：

```
Prometheus 存储机制：
┌─────────────────────────────────────┐
│        内存缓冲区(Head Block)        │ ← 写入
│     ┌────────┐  ┌────────┐          │
│     │ Block1 │  │ Block2 │ ...      │
│     └────────┘  └────────┘          │
└─────────────────────────────────────┘
              ↓ 每 2 小时刷写
┌─────────────────────────────────────┐
│         磁盘(历史 Block)             │ ← 压缩
│     ┌────────┐  ┌────────┐          │
│     │ Block3 │  │ Block4 │ ...      │
│     └────────┘  └────────┘          │
└─────────────────────────────────────┘
```

- **写入流程**：新数据先存内存，每 2 小时批量写入磁盘
- **数据可靠性**：通过预写日志（WAL）确保数据不丢
- **数据压缩**：采用高效压缩算法，节省存储

:::important
**Prometheus 的 TSDB 是为单节点设计的**——它没有原生的集群能力。这也是 Grafana 推出 Mimir 的原因：**Mimir 是 Prometheus 协议的集群版**，解决了水平扩展问题。后面讲 LGTM 栈时会再展开。
:::

## 五、Grafana LGTM 栈：云原生全栈观测

讲完单点的 Prometheus+Grafana，我们必须聊聊业界正在快速演进的 LGTM 栈。它代表了"云原生可观测性"的未来方向。

### 1. LGTM 栈到底是什么

LGTM 是四个组件首字母的缩写，每个组件专注于可观测性的一个特定维度：

| 组件    | 全称      | 负责领域               | 核心定位                    |
| ----- | ------- | ------------------ | ----------------------- |
| **L** | Loki    | 日志(Logs)           | 轻量级、高性价比的日志聚合与查询系统      |
| **G** | Grafana | 可视化(Visualization) | 统一的可观测性仪表板与查询平台         |
| **T** | Tempo   | 链路(Traces)         | 高性能、低成本的分布式追踪系统         |
| **M** | Mimir   | 指标(Metrics)        | 可扩展的 Prometheus 兼容时序数据库 |

> 早期 LGTM 栈中的"M"指的是 **Metrics（即 Prometheus）**。Grafana 的 Prometheus 集群方案最早源于 **Cortex**（2018 年由 Weaveworks 开源），后被 Grafana 收购并迭代，2022 年正式将基于 Cortex 的下一代集群方案命名为 **Mimir**。

### 2. 核心设计哲学：索引最小化

LGTM 栈与传统可观测性方案（如 ELK、Zipkin）的本质区别在于其\*\*"索引最小化"\*\*的设计哲学：

| 组件        | 索引策略                                                            | 传统方案对比                 |
| --------- | --------------------------------------------------------------- | ---------------------- |
| **Loki**  | 只索引日志的**标签(元数据)**，不索引日志内容                                       | ELK 对每字段都建倒排索引         |
| **Tempo** | 索引 **Trace ID** + 少量关键维度（如 `service.name`、`span.name`），其余通过列式扫描 | Jaeger 对 Span 属性全建倒排索引 |
| **Mimir** | 只索引指标的**标签集**，时序数据本身按块存储（与 Prometheus 本地存储索引策略一致，差异在于水平扩展和对象存储） | InfluxDB 早期版本（每字段都建索引） |

这种设计带来了三个革命性的优势：

1. **存储成本极低**：索引体积缩小 10-100 倍，相同硬件可存储更多数据
2. **写入性能极高**：无需复杂的索引构建，写入吞吐量提升数倍
3. **水平扩展能力极强**：所有组件均采用无状态+分片架构，可无限横向扩展

用快递柜的比喻来理解：

:::note
**Loki 就像快递柜的"扫码系统"**——它不记录柜子里放了什么（不索引日志内容），只记录"哪个柜子、什么时候被谁扫过码"（索引标签）。这样存储空间极小，取件时按"柜号"快速定位，再在柜子里翻找具体内容。代价是：内容搜索会慢一些，但**现代对象存储的顺序读取性能非常高，即使扫描大量日志内容，速度也能接受**。
:::

之前我学 ELK 时，深刻体会到全文索引的强大——但也感受到了它的"贵"。Loki 用"标签先过滤、内容后扫描"的策略，把 ELK 的全文索引开销给省下来了，**这正是"用业务理解换技术成本"的经典案例**。

### 3. 完整数据流向

LGTM 栈的完整数据流向非常清晰：

```
LGTM 栈数据流向（自建部署版）：
┌─────────────────────────────────────────────────────┐
│                  应用 / 基础设施                      │
└────────────────────┬────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────────┐
│            采集 Agent (Grafana Alloy)               │
│        (统一采集指标、日志、链路数据)                  │
└────────────────────┬────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────────┐
│     负载均衡 / 反向代理 (Nginx / Envoy / LB)         │
│  (注：商业版 Grafana Cloud 中对应 Grafana Gateway)    │
└────────────────────┬────────────────────────────────┘
                     ↓
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
   ┌────────┐   ┌────────┐   ┌────────┐
   │ Mimir  │   │  Loki  │   │  Tempo │  (独立存储)
   │ (指标) │   │ (日志) │   │ (链路) │
   └────────┘   └────────┘   └────────┘
       └─────────────┼─────────────┘
                     ↓
              ┌──────────────┐
              │   Grafana    │  (统一可视化)
              │  (可视化)    │
              └──────────────┘
```

- **采集层**：Grafana Alloy（原 Grafana Agent）是统一采集器，可同时采集指标、日志、链路数据
- **网关层**：自建部署中通常由 **Nginx / Envoy / 云厂商 LB** 承担统一接收、认证、限流的工作；Grafana Gateway 主要出现在商业版 **Grafana Cloud** 的托管入口中，并非自建场景的标配
- **存储层**：各组件独立存储自己的数据，支持对象存储（S3、OSS、MinIO）作为底层存储
- **查询层**：Grafana 作为统一入口，通过标准 API 查询各组件数据

### 4. Mimir：指标存储的集群版

Mimir 是 Grafana 推出的**开源、可扩展的 Prometheus 兼容时序数据库**，完全兼容 PromQL，解决了原生 Prometheus 无法水平扩展的问题。

#### 核心架构

Mimir 采用**微服务架构**，将不同功能拆分为独立的服务，可单独部署和扩展：

| 服务                      | 职责                       |
| ----------------------- | ------------------------ |
| **Distributor（分发器）**    | 接收指标数据，根据时序标签哈希分片        |
| **Ingester（写入器）**       | 接收数据，在内存中构建时序块，定期刷写到对象存储 |
| **Querier（查询器）**        | 接收 PromQL 查询，并行查询内存和磁盘数据 |
| **Store Gateway（存储网关）** | 查询对象存储中的历史数据，缓存索引        |
| **Compactor（压缩器）**      | 后台合并小数据块，清理过期数据          |

#### 存储结构

Mimir 的存储分为两部分：

```
Mimir 存储结构：
┌────────────────────────────────────────┐
│         元数据存储                       │
│   (Consul / etcd)                       │
│   存储集群拓扑、分片信息                  │
└────────────────────────────────────────┘
┌────────────────────────────────────────┐
│         时序数据存储                     │
│   (对象存储：S3 / OSS / MinIO)          │
│   ┌──────────┐    ┌──────────┐         │
│   │ 数据块   │    │ 索引     │         │
│   │ (Block)  │    │ (Index)  │         │
│   └──────────┘    └──────────┘         │
└────────────────────────────────────────┘
```

### 5. Loki：日志系统的"反传统"设计

Loki 是 Grafana 自研的日志系统，其设计灵感来自 Prometheus，是目前增长最快的开源日志解决方案。

#### 核心设计：标签索引，内容不索引

这是 Loki 与 ELK 最本质的区别：

| 系统       | 索引策略                 | 代价          | 收益     |
| -------- | -------------------- | ----------- | ------ |
| **ELK**  | 对日志的每个字段建立倒排索引       | 存储成本高，写入性能差 | 查询速度极快 |
| **Loki** | 只对**标签**建立索引，日志内容不索引 | 全文搜索需要扫描    | 存储成本极低 |

#### 数据模型与查询语言

Loki 的数据模型与 Prometheus 完全一致：

```
日志流示例：
{app="ai-code-platform", level="error", pod="ai-generate-7f9d8f7d9-2xqzk"}
2025-08-14T19:30:10Z "调用DeepSeek模型失败：超时"
```

Loki 使用 **LogQL** 查询语言，语法与 PromQL 高度相似：

```promql
# 日志过滤查询：先按标签过滤，再搜索内容
{app="ai-code-platform", level="error"} |= "调用模型失败"

# 日志聚合查询：统计每小时的错误次数
sum by (model) (count_over_time({app="ai-code-platform"} |= "调用模型" [1h]))
```

### 6. Tempo：链路追踪的"极致省钱"设计

Tempo 是 Grafana 推出的分布式追踪系统，设计目标是成为"**最便宜、最容易部署的追踪系统**"。

#### 核心设计：索引最小化（不只索引 Trace ID）

Tempo 的设计精髓在于**索引最小化**：它只为 **Trace ID** 和少量关键维度（如 `service.name`、`span.name`）建立索引，而不像传统 APM 那样对 Span 的每个属性（如 `http.status_code`、`db.statement` 等）都建倒排索引。

- **Trace ID 必索引**：作为数据写入分片和查询的主键
- **关键维度索引**：少量常用的可搜索标签（如 `service.name`、`span.name`、`http.method`）作为 dedicated columns，加速按服务/接口的查询
- **大多数 Span 属性不索引**：通过高效的列式扫描（Parquet）完成查询
- **TraceQL 支持**：从 Tempo 2.0 引入 **TraceQL** 以来，已支持类似 PromQL 的标签过滤和聚合查询，无需事先知道 Trace ID

这种"**少量索引 + 列式扫描**"的组合，在保持低成本（存储成本比 Jaeger、Zipkin 低 10 倍以上）的同时，又兼顾了搜索的灵活性——既不会给读者留下"除了 Trace ID 什么都不能查"的错误印象，也精准地传达了 Tempo "极致省钱"的设计哲学。

#### 数据模型

Tempo 完全兼容 OpenTelemetry 的数据模型：

| 概念            | 含义                                       |
| ------------- | ---------------------------------------- |
| **Trace（追踪）** | 代表一个完整的用户请求，由全局唯一的 Trace ID 标识           |
| **Span（跨度）**  | 代表 Trace 中的一个独立操作单元，每个 Span 有自己的 Span ID |
| **Span 属性**   | 包含操作名称、开始时间、结束时间、状态、标签等信息                |

### 7. 关联可观测性：LGTM 栈的杀手锏

虽然 Tempo 本身只能通过 Trace ID 查询，但它通过与 Loki 和 Mimir 的深度集成，实现了强大的**关联可观测性**：

```
关联可观测性工作流：
异常指标点 ──点击──→ 对应 Trace ──点击──→ 对应日志
     ↑                                          ↓
     └────────── 反向跳转 ──────────────────────┘
```

| 跳转方向        | 实现方式                                  | 业务价值     |
| ----------- | ------------------------------------- | -------- |
| **指标 → 链路** | 在 Grafana 中点击异常指标点，跳转到该时间点对应的所有 Trace | 快速定位性能瓶颈 |
| **日志 → 链路** | 如果日志中包含 Trace ID，点击日志直接跳转到对应 Trace    | 错误排查     |
| **链路 → 日志** | 在 Trace 详情中，查看该 Trace 对应的所有日志         | 上下文还原    |

:::important
**这种跨数据源的关联能力，使得排查问题的效率大幅提升**。试想一下：以前发现一个 P99 飙升，要先找日志、再找调用链、再做关联——现在在 Grafana 里点几下就能完成。**这才是"可观测性"区别于"监控"的根本所在**——从"看见问题"到"洞察系统"的能力跃迁。
:::

### 8. LGTM 栈的核心技术优势

总结一下 LGTM 栈的核心优势：

1. **极致的成本效益**：所有组件都支持对象存储作为底层存储，存储成本比传统方案低 90%
2. **无限的水平扩展能力**：所有组件都是无状态的，可通过增加节点实现线性扩展
3. **深度的关联可观测性**：实现了指标、日志、链路三者之间的无缝跳转
4. **云原生友好**：原生支持 Kubernetes 部署，提供官方 Helm Chart
5. **统一的技术栈**：所有组件都采用相同的架构设计和技术栈

## 六、Spring Boot 接入 Prometheus 实战

理论讲了这么多，终于到了"动手"环节。

### 1. 引入依赖

在 `pom.xml` 中添加以下三个核心依赖：

```xml
<!-- 1. 端点提供者：暴露监控端点，是应用与外部监控系统交互的窗口 -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

<!-- 2. 数据收集者：真正的指标收集引擎，提供统一 API 创建自定义指标 -->
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-core</artifactId>
</dependency>

<!-- 3. 格式转换者：将 Micrometer 收集的指标转换为 Prometheus 格式 -->
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

**各组件职责总结**：

| 依赖                               | 职责    | 类比   |
| -------------------------------- | ----- | ---- |
| `spring-boot-starter-actuator`   | 端点提供者 | 开门的人 |
| `micrometer-core`                | 数据收集者 | 干活的  |
| `micrometer-registry-prometheus` | 格式转换者 | 翻译的  |
| `Prometheus`                     | 数据拉取者 | 消费的  |

### 2. 编写配置

在 `application.yml` 中添加 Actuator 配置，暴露必要的监控端点：

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus # 暴露健康检查、信息和 Prometheus 端点
  endpoint:
    health:
      show-details: always # 显示完整的健康检查详情
```

:::caution
**配置坑点**：`include` 默认只暴露 `health` 和 `info` 两个端点。如果不显式配置 `prometheus`，Prometheus 端点不会被暴露。这是新手最常踩的坑之一。
:::

配置完成后，启动应用并访问 `http://localhost:8080/actuator/prometheus`，即可看到 Prometheus 格式的指标数据。如果能看到一堆以 `# HELP` 和 `# TYPE` 开头的文本，说明端点暴露成功。

### 3. 验证基础指标

Spring Boot Actuator + Micrometer 自动收集了大量基础指标，包括：

| 指标                                   | 含义         |
| ------------------------------------ | ---------- |
| `jvm_memory_used_bytes{area="heap"}` | JVM 堆内存使用量 |
| `http_server_requests_seconds_count` | HTTP 请求总数  |
| `http_server_requests_seconds_sum`   | HTTP 请求总耗时 |
| `process_cpu_usage`                  | 进程 CPU 使用率 |

这些"开箱即用"的指标已经能覆盖大部分系统监控需求，但**业务特有指标**还得自己埋点。

## 七、AI 业务指标埋点实战

### 1. 设计监控上下文

由于 LangChain4j 的监听器运行在独立的线程中，无法直接获取业务层的用户 ID 和应用 ID，因此我们需要通过 **ThreadLocal** 来传递监控上下文。

#### 步骤 1：创建监控上下文类

```java
package com.yupi.yuaicodemother.monitor;

import lombok.AllArgsConstructor;
import lombok.Builder;
import lombok.Data;
import lombok.NoArgsConstructor;

import java.io.Serializable;

/**
 * 监控上下文（需要在线程间传递的数据）
 */
@Data
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class MonitorContext implements Serializable {
    private String userId;
    private String appId;
    private static final long serialVersionUID = 1L;
}
```

#### 步骤 2：创建上下文持有者

使用 ThreadLocal 实现线程内的上下文共享：

```java
package com.yupi.yuaicodemother.monitor;

import lombok.extern.slf4j.Slf4j;

/**
 * 监控上下文持有者（线程内共享）
 */
@Slf4j
public class MonitorContextHolder {
    private static final ThreadLocal<MonitorContext> CONTEXT_HOLDER = new ThreadLocal<>();

    /**
     * 设置监控上下文
     */
    public static void setContext(MonitorContext context) {
        CONTEXT_HOLDER.set(context);
    }

    /**
     * 获取当前监控上下文
     */
    public static MonitorContext getContext() {
        return CONTEXT_HOLDER.get();
    }

    /**
     * 清除监控上下文（必须调用，防止内存泄漏）
     */
    public static void clearContext() {
        CONTEXT_HOLDER.remove();
    }
}
```

### 2. 在业务层设置上下文

在调用 AI 模型之前，设置监控上下文，并在请求结束后清除：

```java
public Flux<String> chatToGenCode(Long appId, String message, User loginUser) {
    // ... 参数校验和业务逻辑 ...

    // 6. 设置监控上下文（用户 ID 和应用 ID）
    MonitorContextHolder.setContext(
            MonitorContext.builder()
                    .userId(loginUser.getId().toString())
                    .appId(appId.toString())
                    .build()
    );

    // 7. 调用 AI 生成代码（流式）
    Flux<String> codeStream = aiCodeGeneratorFacade.generateAndSaveCodeStream(message, codeGenTypeEnum, appId);

    // 8. 收集 AI 响应的内容，并在完成后保存记录到对话历史
    return streamHandlerExecutor.doExecute(codeStream, chatHistoryService, appId, loginUser, codeGenTypeEnum)
            .doFinally(signalType -> {
                // 流结束时清理上下文（无论成功/失败/取消）
                MonitorContextHolder.clearContext();
            });
}
```

### 3. 实现 LangChain4j 监控监听器

利用 LangChain4j 的 `ChatModelListener` 机制，在模型调用的各个阶段收集指标：

```java
package com.yupi.yuaicodemother.monitor;

import dev.langchain4j.model.chat.listener.ChatModelErrorContext;
import dev.langchain4j.model.chat.listener.ChatModelListener;
import dev.langchain4j.model.chat.listener.ChatModelRequestContext;
import dev.langchain4j.model.chat.listener.ChatModelResponseContext;
import org.springframework.stereotype.Component;

import javax.annotation.Resource;
import java.time.Instant;
import java.util.Map;

@Component
public class AiModelMonitorListener implements ChatModelListener {
    private static final String REQUEST_START_TIME_KEY = "request_start_time";
    private static final String MONITOR_CONTEXT_KEY = "monitor_context";

    @Resource
    private AiModelMetricsCollector aiModelMetricsCollector;

    @Override
    public void onRequest(ChatModelRequestContext requestContext) {
        // 记录请求开始时间
        requestContext.attributes().put(REQUEST_START_TIME_KEY, Instant.now());

        // 从监控上下文中获取信息
        MonitorContext monitorContext = MonitorContextHolder.getContext();
        String userId = monitorContext.getUserId();
        String appId = monitorContext.getAppId();

        // 将监控上下文存入请求属性，供后续方法使用
        requestContext.attributes().put(MONITOR_CONTEXT_KEY, monitorContext);

        // 获取模型名称
        String modelName = requestContext.chatRequest().modelName();

        // 记录请求开始指标
        aiModelMetricsCollector.recordRequest(userId, appId, modelName, "started");
    }

    @Override
    public void onResponse(ChatModelResponseContext responseContext) {
        // 从属性中获取监控信息
        Map<Object, Object> attributes = responseContext.attributes();
        MonitorContext context = (MonitorContext) attributes.get(MONITOR_CONTEXT_KEY);
        String userId = context.getUserId();
        String appId = context.getAppId();
        String modelName = responseContext.chatResponse().modelName();

        // 记录成功请求
        aiModelMetricsCollector.recordRequest(userId, appId, modelName, "success");

        // 记录响应时间
        recordResponseTime(attributes, userId, appId, modelName);

        // 记录 Token 使用情况
        recordTokenUsage(responseContext, userId, appId, modelName);
    }

    @Override
    public void onError(ChatModelErrorContext errorContext) {
        // 从属性中获取监控信息
        Map<Object, Object> attributes = errorContext.attributes();
        MonitorContext context = (MonitorContext) attributes.get(MONITOR_CONTEXT_KEY);
        String userId = context.getUserId();
        String appId = context.getAppId();
        String modelName = errorContext.chatRequest().modelName();

        // 记录失败请求
        aiModelMetricsCollector.recordRequest(userId, appId, modelName, "error");

        // 记录响应时间
        recordResponseTime(attributes, userId, appId, modelName);
    }

    /**
     * 记录响应时间
     */
    private void recordResponseTime(Map<Object, Object> attributes, String userId, String appId, String modelName) {
        Instant startTime = (Instant) attributes.get(REQUEST_START_TIME_KEY);
        long responseTimeMs = java.time.Duration.between(startTime, Instant.now()).toMillis();
        aiModelMetricsCollector.recordResponseTime(userId, appId, modelName, responseTimeMs);
    }

    /**
     * 记录 Token 使用情况
     */
    private void recordTokenUsage(ChatModelResponseContext responseContext, String userId, String appId, String modelName) {
        var tokenUsage = responseContext.chatResponse().metadata().tokenUsage();
        if (tokenUsage != null) {
            aiModelMetricsCollector.recordTokenUsage(userId, appId, modelName, "input", tokenUsage.inputTokenCount());
            aiModelMetricsCollector.recordTokenUsage(userId, appId, modelName, "output", tokenUsage.outputTokenCount());
            aiModelMetricsCollector.recordTokenUsage(userId, appId, modelName, "total", tokenUsage.totalTokenCount());
        }
    }
}
```

### 5. 错误处理：完整的 onError 实现

为了记录错误信息，需要完善 onError 方法并增加错误计数器：

```java
@Override
public void onError(ChatModelErrorContext errorContext) {
    // 从监控上下文中获取信息
    MonitorContext context = MonitorContextHolder.getContext();
    String userId = context.getUserId();
    String appId = context.getAppId();

    // 获取模型名称和错误类型
    String modelName = errorContext.chatRequest().modelName();
    String errorMessage = errorContext.error().getMessage();

    // 记录失败请求
    aiModelMetricsCollector.recordRequest(userId, appId, modelName, "error");
    // 记录错误详情
    aiModelMetricsCollector.recordError(userId, appId, modelName, errorMessage);

    // 记录响应时间（即使是错误响应）
    Map<Object, Object> attributes = errorContext.attributes();
    recordResponseTime(attributes, userId, appId, modelName);
}
```

### 6. 注册监听器：最容易遗漏的关键步骤

:::warning
**这是最容易遗漏的关键步骤**：必须将自定义的监听器注册到 ChatModel 中，否则监听器不会被触发。

在 `StreamingChatModelConfig` 中，通过 `listeners` 方法注入我们的 `AiModelMonitorListener`：

```java
package com.yupi.yuaicodemother.config;

import dev.langchain4j.model.openai.OpenAiStreamingChatModel;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Scope;

import java.util.List;

public class StreamingChatModelConfig {
    @Value("${openai.api-key}")
    private String apiKey;

    @Value("${openai.base-url}")
    private String baseUrl;

    private String modelName;
    private Integer maxTokens;
    private Double temperature;
    private boolean logRequests;
    private boolean logResponses;

    @Bean
    @Scope("prototype")
    public OpenAiStreamingChatModel streamingChatModelPrototype(AiModelMonitorListener aiModelMonitorListener) {
        return OpenAiStreamingChatModel.builder()
                .apiKey(apiKey)
                .baseUrl(baseUrl)
                .modelName(modelName)
                .maxTokens(maxTokens)
                .temperature(temperature)
                .logRequests(logRequests)
                .logResponses(logResponses)
                // 关键：注册我们的监控监听器
                .listeners(List.of(aiModelMonitorListener))
                .build();
    }
}
```

## 九、踩坑实录

### 坑一：监听器没注册，指标全为空

**问题现象**：代码写完了，Prometheus 也启动了，但查询 `ai_model_requests_total` 始终没有数据。

**根因分析**：监听器没有注册到 ChatModel 中。Spring 的 `@Component` 只是把监听器放进了 IoC 容器，但 LangChain4j 不会自动注入它。

**解决方案**：在 ChatModel 的 `listeners(...)` 方法中显式注册：

```java
.listeners(List.of(aiModelMonitorListener))  // 关键步骤
```

**经验总结**：

:::warning
**框架提供的扩展点 ≠ 自动接入**。无论 LangChain4j 还是 Spring，多数扩展机制都需要显式注册。读官方文档时，要特别留意"如何注册"这部分内容。
:::

### 坑二：ThreadLocal 内存泄漏

**问题现象**：长时间运行后，应用内存持续增长，最终 OOM。

**根因分析**：每次调用都 `setContext(...)`，但没有清理 ThreadLocal。在线程池场景下，线程被复用，旧 context 一直存活，导致内存泄漏。

**解决方案**：使用 `try-finally` 或响应式流的 `doFinally` 确保清理：

```java
.doFinally(signalType -> {
    MonitorContextHolder.clearContext();  // 必须在 doFinally 中调用
});
```

**经验总结**：

| 错误的清理           | 正确的清理                     |
| --------------- | ------------------------- |
| 只在正常返回时清理       | 在 finally / doFinally 中清理 |
| 把清理写在 lambda 内部 | 把清理写在最外层包装                |
| 用完不清理           | 必须 `remove()`             |

**特别强调**：线程池场景下，ThreadLocal 的内存泄漏是"沉默的杀手"——平时看不出来，等到生产环境跑一周就 OOM。

### 坑三：Prometheus 抓不到指标

**问题现象**：Prometheus 控制台显示 `up==0`，所有指标都抓不到。

**根因分析**：可能是以下几个原因之一：

| 原因           | 排查方法                                                        |
| ------------ | ----------------------------------------------------------- |
| 应用未启动        | 检查应用进程是否存在                                                  |
| 端口/路径配错      | 检查 `prometheus.yml` 中的 `targets` 和 `metrics_path`           |
| 防火墙阻挡        | 检查端口是否开放                                                    |
| Actuator 未暴露 | 检查 `application.yml` 中 `include` 是否包含 `prometheus`          |
| 网络不通         | 在 Prometheus 服务器上 `curl http://应用IP:端口/actuator/prometheus` |

**解决方案**：按上述清单逐项排查。

### 坑四：Grafana 图表无数据

**问题现象**：Grafana 图表显示"No data"。

**根因分析**：

1. **数据源没接对**：Grafana 的 Prometheus 数据源 URL 是否正确
2. **PromQL 写错**：语法错误或时序选择器不对
3. **时间范围不对**：图表时间范围不包含有数据的时间段
4. **指标名称不匹配**：Grafana 查的指标名和 Prometheus 实际的不一致

**解决方案**：

```
排查步骤：
1. 在 Prometheus 控制台直接查询，确认指标存在
        ↓
2. 在 Grafana 的 "Explore" 页面验证 PromQL
        ↓
3. 检查数据源配置（URL、访问权限）
        ↓
4. 检查时间范围设置
```

### 坑五：标签基数爆炸

**问题现象**：Prometheus 内存占用飙升，查询越来越慢。

**根因分析**：指标标签的值域太大，比如把 `userId` 直接作为标签（百万级用户），导致时间序列数量爆炸。

**解决方案**：

| 错误做法             | 正确做法                          |
| ---------------- | ----------------------------- |
| 直接用 `userId` 作标签 | 按活跃度分桶（VIP/普通）                |
| 把完整错误信息作标签       | 只保留错误类型（`Timeout`/`AuthFail`） |
| 把 URL 参数作标签      | 只保留 URL 路径                    |

**经验总结**：

:::caution
**标签基数是 Prometheus 性能的"命门"**。一个标签的取值数量决定了时间序列的膨胀速度。**控制标签基数 = 控制 Prometheus 的扩展性**。监控指标设计时，永远问自己："这个标签的取值范围有多大？会无限增长吗？"
:::

### 2. 关键知识点回顾

| 知识点                | 核心要点                                 |
| ------------------ | ------------------------------------ |
| **可观测性 vs 监控**     | 可观测性是上位概念，含数据采集、存储、分析、告警全链路          |
| **维度 vs 指标**       | 维度是标签，指标是数值                          |
| **拉取 vs 推送**       | Prometheus 用拉取，简单可靠、易调试              |
| **四种指标类型**         | Counter/Gauge/Histogram/Summary，按场景选 |
| **LGTM 索引最小化**     | 用"业务理解换技术成本"的经典案例                    |
| **关联可观测性**         | 指标↔日志↔链路跨数据源跳转                       |
| **ThreadLocal 陷阱** | 必须 `remove()`，线程池场景尤甚                |
| **标签基数控制**         | 不让标签取值无限增长                           |
