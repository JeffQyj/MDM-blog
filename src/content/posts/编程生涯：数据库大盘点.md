## 一、先看懂三大阵营：OLTP、OLAP 与 HTAP

在认识具体数据库之前，先理解数据库世界的核心分类——**OLTP**、**OLAP** 和 **HTAP**。

### OLTP：面向业务交易

**OLTP（Online Transaction Processing，在线事务处理）** 对应的是日常业务操作——下单、转账、登录、发帖。这类场景的特点是：

- **高并发**：每秒成千上万的请求打过来
- **低延迟**：用户点一下按钮，期望毫秒级响应
- **高一致性**：转账记录不能多一分也不能少一分
- **数据量级**：单表几百万到几亿行，但单行数据很小

OLTP 数据库通常使用**行式存储**——把同一行的所有字段放在一起，因为业务操作往往是"查一个用户的全部信息"。

### OLAP：面向数据分析

**OLAP（Online Analytical Processing，在线分析处理）** 对应的是数据分析场景——月度营收报表、用户行为漏斗、全网商品销量排行。这类场景的特点是：

- **高吞吐**：要扫描几百 GB 甚至 TB 级别的数据
- **批量计算**：一次查询可能要聚合几亿行记录
- **低并发**：同一时间可能就几十个分析人员在用
- **数据量级**：海量历史数据的聚合分析

OLAP 数据库通常使用**列式存储**——把同一列的所有值放在一起，因为分析操作往往是"统计全量用户的平均消费金额"，只需要读取一个列，不需要读取整行数据。

```text
行式 vs 列式存储对比：

一张订单表有 4 列：订单ID、用户ID、金额、时间

行式存储（适合 OLTP）：
[订单1][用户A][199][2026-07-01] → 读一行，全字段可用
[订单2][用户B][399][2026-07-01]
[订单3][用户A][599][2026-07-02]

列式存储（适合 OLAP）：
订单ID列：[订单1, 订单2, 订单3]
用户ID列：[用户A, 用户B, 用户A]
金额列：  [199, 399, 599]       → 统计"总金额"只用读这一列
时间列：  [2026-07-01, 2026-07-01, 2026-07-02]
```

### HTAP：混合负载——既要又要的第三条路

**HTAP（Hybrid Transactional/Analytical Processing，混合事务/分析处理）** 的出现，打破了 OLTP 和 OLAP 非此即彼的界限。它让一个数据库能同时处理"高频写入"和"快速分析"两类负载，你不再必须在"快写入"和"快分析"之间二选一。

HTAP 的核心能力体现在两个维度：

| 维度           | 说明                                        | 例子                           |
| ------------ | ----------------------------------------- | ---------------------------- |
| **写入时同步分析**  | 业务数据产生的瞬间就能被分析查询，不需要 ETL 搬运到数仓            | 订单产生后实时统计销售额                 |
| **一份数据两种引擎** | 同一份数据同时有行式引擎（支持 OLTP 查询）和列式引擎（支持 OLAP 聚合） | TiDB 的 TiKV（行存）+ TiFlash（列存） |

代表性的 HTAP 数据库包括 **TiDB**（PingCAP）、**OceanBase**（蚂蚁集团），它们都可以用一种存储处理两类负载。

:::tip
HTAP 的"既要又要"是有代价的——纯 OLTP 场景下，HTAP 数据库的单点性能不如 MySQL/PostgreSQL；纯 OLAP 场景下，又不如 Snowflake/ClickHouse。**HTAP 解决的是"运维复杂度"问题，而非"极致性能"问题。** 如果你的团队已经搞定了 ETL 链路，OLTP 和 OLAP 各用专职数据库反而是更成熟的做法。
:::

:::note
这个三大阵营的分类在 [大数据技术栈](../编程生涯大数据技术栈/) 中也有体现——Hadoop 生态的 Hive/Spark 面向 OLAP，HBase 偏向 OLTP 风格，而现代云原生数据库正经历着 HTAP 化的趋势。正如我在那篇文章末尾提到的，**边界正在模糊**。
:::

## 二、交易型数据库（OLTP）全览

交易型数据库是离业务最近的数据库——用户注册、商品下单、支付结算，背后都是 OLTP 数据库在支撑。

### 2.1 国际开源双雄

#### PostgreSQL —— 功能最全的开源"全能王"

PG 被誉为"最先进的开源数据库"，这不是自夸。它原生支持关系型数据、JSON 文档、全文搜索、地理空间、时序数据，通过插件还能实现向量搜索和图数据库功能。对 SQL 标准的支持度极高，扩展性极强。

我在 [数据库天花板——PostgreSQL](../编程生涯数据库天花板postgresql/) 中详细拆解了它的索引体系和架构设计——简而言之，**PG 用一套模块化架构，让你一个数据库搞定原来需要 MySQL + Redis + Elasticsearch + MongoDB 才能解决的场景**。

**什么时候选 PG？**

- 需要处理多种数据模型的复杂业务系统
- 对 SQL 标准兼容性要求高
- 希望减少中间件数量，降低运维复杂度

**需要注意什么？**

- 超高并发写入场景的扩展性不如纯 NoSQL 数据库
- 水平扩展方案（如 pg\_shard 或 Citus）不如分布式原生数据库成熟

#### MySQL —— 互联网时代的开源基石

MySQL 凭借"简单易用、高性能读写"成为 LAMP (Linux（操作系统）、Apache（Web服务器）、MySQL（关系型数据库）、PHP（编程语言）) 技术栈的基石，是全世界装机量最大的开源数据库之一。支撑了无数网站、电商平台和内容管理系统。

```sql
-- MySQL 最擅长的场景：简单的 CRUD + 高并发查询
-- 以电商系统的商品列表为例

-- 建表（简洁明了）
CREATE TABLE products (
    id          INT PRIMARY KEY AUTO_INCREMENT,
    name        VARCHAR(200) NOT NULL COMMENT '商品名',
    price       DECIMAL(10, 2) NOT NULL COMMENT '价格',
    category_id INT NOT NULL COMMENT '品类ID',
    status      TINYINT DEFAULT 1 COMMENT '状态：1上架 0下架',
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='商品表';

-- 高并发分页查询（MySQL 强项）
SELECT id, name, price, created_at
FROM products
WHERE category_id = 100 AND status = 1
ORDER BY created_at DESC
LIMIT 20 OFFSET 0;
```

**什么时候选 MySQL？**

- 读多写少、高并发简单查询的场景
- 团队对 MySQL 运维经验丰富
- 需要丰富的第三方工具和文档支持

**需要注意什么？**

- 复杂查询、窗口函数等高级分析功能不如 PG
- Oracle 收购后开源生态存在不确定性（MariaDB 分支的存在就是证明）

| 对比维度      | PostgreSQL                   | MySQL                 |
| --------- | ---------------------------- | --------------------- |
| SQL 标准兼容性 | 极高，近乎完整的 SQL:2016 支持         | 部分支持，各版本有差异           |
| 索引类型      | B-link、GIN、GIST、BRIN 等十余种    | B+ 树为主，5.7+ 支持全文和空间索引 |
| JSON 支持   | JSONB 原生二进制格式，性能优异           | JSON 文本格式，功能有限        |
| 并发模型      | 多进程（每个连接一个进程）                | 多线程（线程池共享内存）          |
| 扩展性       | 插件生态极其丰富（pgvector、PostGIS 等） | 插槽机制，扩展能力较弱           |
| 运维门槛      | 初期配置参数较多，需一定经验               | 开箱即用，运维成本低            |
| 典型场景      | 复杂业务系统、数据处理枢纽                | 互联网 Web 应用、电商系统       |

:::tip
如果你在纠结 PG 还是 MySQL，我个人的建议是：**新项目优先选 PG，存量项目不要强迁**。PG 的功能深度和前瞻性在不停拉大差距，MySQL 的生态优势和庞大装机量也不是一天能追上的。但更重要的是——两个都值得学，因为它们的底层设计思路完全不同。
:::

### 2.2 国际商业三巨头

如果说 PG 和 MySQL 是开源世界的双雄，那 Oracle、SQL Server、IBM DB2 就是商业数据库的三座大山。

#### Oracle —— 商业数据库的绝对巨头

**Oracle** 是功能强大、稳定、安全的代名词。它拥有 RAC（Real Application Clusters，真正应用集群）等业界最成熟的高可用与性能优化方案，是金融、电信、大型企业的核心标配。

Oracle 的许可费用极高，但它的诊断排障工具非常强大，官方支持也是一流水准。如果你在金融行业干活，大概率绕不开 Oracle。

#### SQL Server —— 微软生态的集大成者

**SQL Server** 与 Windows 生态、.NET、Power BI 深度集成。它不仅是数据库，更是一套完整的数据平台——内置了 Analysis Services（分析服务）、Reporting Services（报表服务）、Integration Services（集成服务）。

管理工具 SSMS（SQL Server Management Studio）对开发者极其友好，是整个数据库行业最好用的管理工具之一。如果你重度使用微软技术栈，SQL Server 是不二之选。

#### IBM DB2 —— 大型机血脉

**DB2** 继承自 IBM 大型机（Mainframe）的血脉，在银行、保险等传统金融领域仍有稳固地位。如今它也能跑在 Linux 和云端，但主要服务于特定的大型企业客户。

:::note
这三大商业数据库的共同特点是：**贵，但值**。贵在许可费用和运维成本，值在极致的稳定性和商业支持。对于预算充足、对数据一致性要求极致的核心交易系统，它们仍然是标杆。但对于大多数互联网创业公司和中小企业，开源的 PG 和 MySQL 已经绰绰有余。
:::

### 2.3 嵌入式之王：SQLite

**SQLite** 不是一个独立的服务器进程，而是一个直接链接到应用程序中的库文件。它可能是世界上部署最广泛的数据库——你的手机里（iOS/Android）、浏览器里、桌面软件里、物联网设备里，到处都有它。

```text
SQLite 的存在感（你可能每天在用但不知道）：
- 手机：微信、支付宝、Chrome 等 App 的本地数据存储
- 浏览器：Cookies、历史记录、书签 —— 都是 SQLite 文件
- 桌面软件：不少软件的配置和状态存储
- 嵌入式设备：路由器、智能家居的本地数据持久化
```

SQLite 最大的优势是**零配置、零管理**。一个单一文件就是整个数据库，可以随意拷贝、移动、甚至通过 Git 管理。不需要安装任何服务，不需要配置任何参数——你的程序里 include 一个库，直接开始用。

**什么时候选 SQLite？** 几乎所有需要简单可靠数据库的客户端环境——移动端、桌面应用、嵌入式设备、中小型网站的本地存储。当你想让应用在本地拥有"数据库能力"时，SQLite 是唯一的标准答案。

:::warning
SQLite 不擅长高并发写入。它只有一个写入者——所有写操作串行执行。所以**绝对不要用 SQLite 做高并发的 Web 服务端核心库**。对于那个场景，请用 PG 或 MySQL。
:::

### 2.4 云原生关系型（存算分离）

传统数据库的计算和存储绑在同一台机器上——想扩容就得上更大的机器，不仅贵，而且有上限。云原生关系型数据库的核心创新是**存算分离**：计算节点和存储节点独立扩缩。

#### Amazon Aurora —— AWS 的云数据库标杆

**Amazon Aurora** 是 AWS 推出的云原生数据库，兼容 MySQL 和 PostgreSQL 协议。它把存储层改造成了类似 HDFS 的分布式存储系统——底层数据自动备份到 S3，跨 3 个可用区存 6 份副本，写入时只写一次但跨区域复制。

相比传统 MySQL，Aurora 的写入吞吐量提升 5 倍，且支持自动扩缩——存储从 10GB 到 128TB 无缝增长，不需要手动分库分表。

#### 国内大厂的云原生数据库

国内三大云厂商都有对标 Aurora 的产品：

| 云厂商     | 产品名                | 兼容协议                        | 核心卖点                 |
| ------- | ------------------ | --------------------------- | -------------------- |
| **阿里云** | PolarDB            | MySQL / PostgreSQL / Oracle | 一写多读，分钟级扩容，国内云数据库顶流  |
| **华为云** | GaussDB(for MySQL) | MySQL                       | 存算分离架构，高可靠性，华为生态深度绑定 |
| **腾讯云** | TDSQL-C            | MySQL                       | 游戏、社交等场景的高并发支持       |

这些云原生数据库的共性：

```text
存算分离架构示意：

         ┌─────┐  ┌─────┐  ┌─────┐        ← 计算节点
         │只读  │  │只读  │  │读写  │          （独立扩缩）
         │节点1 │  │节点2 │  │节点3 │
         └──┬──┘  └──┬──┘  └──┬──┘
            └────────┼────────┘
                     ▼
         ┌─────────────────────┐
         │  共享分布式存储层      │        ← 存储节点
         │  (底层多副本 + 备份)   │          （自动扩缩）
         └─────────────────────┘
```

:::tip
如果你的业务已经部署在云上，云原生数据库通常是最省心的选择——不需要操心备份、容灾、扩缩容，这些都是云厂商帮你兜底的。相比自建 MySQL 集群，**PolarDB 级别的存算分离方案能让运维成本降低 50% 以上**。
:::

### 2.5 分布式数据库（NewSQL）

传统的 PG 和 MySQL 有一个天然瓶颈：单机性能有上限。当业务数据量达到几十 TB、QPS 达到几十万时，单机数据库无论如何优化都扛不住。解法有两个：**分库分表**（如 MyCAT、ShardingSphere），或者直接上**分布式数据库**。

分布式数据库（也叫 NewSQL）在保留关系型数据库的 ACID 事务和 SQL 能力的同时，实现了水平扩展能力。

#### OceanBase —— 蚂蚁集团的分布式王牌

**OceanBase** 是蚂蚁集团自研的分布式数据库，连续多年在 TPC-C（数据库性能的"奥运会"）上刷榜。它原生分布式，金融级高可用，支持 HTAP 混合负载，兼容 MySQL 和 Oracle 两种模式。

OceanBase 内部的核心设计是 **Paxos 协议 + 多副本一致性**——数据在多个副本之间通过 Paxos 协议同步，少数副本挂了不影响业务。这个设计让 OceanBase 能扛住蚂蚁双十一的峰值流量。

#### TiDB —— 开源 NewSQL 的代表

**TiDB**（PingCAP 出品）是开源 NewSQL 的代表项目，兼容 MySQL 协议，采用存储计算分离架构，自带 HTAP 能力。它的开源社区非常活跃，出海极其成功——在日本、东南亚、北美都有大量用户。

TiDB 的核心架构分为三层：

```text
TiDB 三层架构：

┌─────────────────────────┐
│      TiDB Server        │  ← SQL 计算层（无状态，可水平扩展）
│   (MySQL 协议兼容层)     │      接收 SQL，生成执行计划
└────────────┬────────────┘
             │
┌────────────▼────────────┐
│      PD (Placement      │  ← 元数据管理 + 调度
│       Driver)           │      管理 Region 分布、调度
└────────────┬────────────┘
             │
┌────────────▼────────────┐
│      TiKV / TiFlash     │  ← 存储层
│  (行存)      (列存)      │      TiKV：行式存储（OLTP）
│                         │      TiFlash：列式存储（OLAP）
└─────────────────────────┘
```

这种架构的好处是：**计算层和存储层各自独立水平扩展**。业务增长了，加 TiDB Server 节点提升计算能力，加 TiKV 节点扩大存储容量，互不影响。

#### TDSQL —— 腾讯的金融级分布式数据库

**TDSQL** 是腾讯内部锤炼的分布式数据库，支撑微信支付等核心业务。兼容 MySQL 和 PostgreSQL，强在金融级强一致和超大规模实例管理。

#### CockroachDB 和 YugabyteDB —— 国际开源代表

这两者是国际上的分布式数据库开源代表：

- **CockroachDB**：由前 Google 工程师创建，架构受 Google Spanner 启发，强在多区域部署和全球一致性
- **YugabyteDB**：兼容 PostgreSQL 协议的开源分布式数据库，在 Kubernetes 上部署体验极好

| 分布式数据库          | 企业背景           | 兼容协议               | 开源      | HTAP | 核心特点          |
| --------------- | -------------- | ------------------ | ------- | ---- | ------------- |
| **OceanBase**   | 蚂蚁集团           | MySQL + Oracle     | 部分开源    | ✅    | TPC-C 刷榜王，金融级 |
| **TiDB**        | PingCAP        | MySQL              | ✅ 全开源   | ✅    | 开源社区活跃，出海成功   |
| **TDSQL**       | 腾讯             | MySQL + PostgreSQL | 不开放     | ✅    | 微信支付级强一致      |
| **CockroachDB** | Cockroach Labs | PostgreSQL         | ✅ 核心层开源 | ❌    | 全球多区域部署       |
| **YugabyteDB**  | Yugabyte       | PostgreSQL         | ✅ 全开源   | ❌    | K8s 原生体验      |

:::important
选择分布式数据库之前，先问自己一个问题：**你的数据量真的到了必须用分布式的地步吗？** 很多团队在单机 PG/MySQL 能扛住的量级就上了分布式，结果复杂度大幅上升——部署、监控、故障排查都比单机复杂得多。一个务实的建议：单机能扛住就别上分布式，等真的扛不住时再考虑。
:::

## 三、分析型数据库（OLAP）全览

如果说 OLTP 数据库是"让业务跑起来"，那 OLAP 数据库就是"让数据活起来"。它们面向的是海量历史数据的聚合分析场景，支撑报表、大屏、数据挖掘等能力。

### 3.1 云数仓三巨头

这三家分别定义了云原生数据仓库的三种不同路线。

#### Snowflake —— 云原生数仓的定义者

**Snowflake** 是"存算分离"架构的集大成者。它彻底分离了存储和计算——你可以随时创建多个大小不同的计算集群去查询同一份数据，互不干扰，用完即销毁。按查询消耗的资源计费，弹性极致。

Snowflake 还做了一件特别的事：**Data Marketplace（数据市场）**。企业可以把自己的数据上架到 Snowflake 的数据市场中，其他企业可以直接购买并查询——这让 Snowflake 从一个数据仓库变成了一个"数据流通平台"。

#### BigQuery —— Google 的无服务器分析巨兽

**BigQuery** 的核心特点是：**真·无服务器**。你不需要管理任何服务器或集群，直接提交 SQL 查询，它背后是 Google 全球网络和 Dremel 技术，能在数秒内扫描 PB 级数据。

BigQuery 的定价是按**查询扫描的数据量**计费，而非按集群运行时间。这意味着如果你只跑了一个 100MB 的查询，就只付 100MB 的钱——这对于小查询来说极省钱。

#### Redshift —— AWS 的数据仓库脊梁

**Redshift** 是 AWS 生态的核心分析组件，基于 MPP（Massively Parallel Processing，大规模并行处理）架构。早期基于 PostgreSQL 改造，现在通过 RA3 节点实现了存算分离。

通过分布键和排序键的合理设计，Redshift 在预定义结构的星型/雪花模型上能发挥巨大性能。它还提供了 **Redshift Spectrum**，可以直接查询 S3 数据湖中的文件，无需先加载到 Redshift 表中。

| 对比维度    | Snowflake           | BigQuery              | Redshift              |
| ------- | ------------------- | --------------------- | --------------------- |
| 架构特点    | 存算分离经典              | 无服务器 + 自动扩缩           | MPP + 手动调优            |
| 弹性      | 极强，计算集群独立扩缩         | 极致，自动扩缩用户无感           | 较强，但需预先规划             |
| 定价模式    | 按计算资源使用时长           | 按扫描数据量                | 按集群规格固定费用             |
| SQL 兼容性 | 自定义 SQL（类 PG 风格）    | 自定义 SQL               | 基于 PostgreSQL         |
| 半结构化数据  | 原生支持 VARIANT 类型     | 原生支持 JSON             | 通过 SUPER 类型支持         |
| 数据共享    | Data Marketplace 生态 | 有限（通过 BigQuery 数据集共享） | 通过 Redshift Datashare |

:::caution
三大云数仓都有一个共同的"坑"：**离开自家云生态，体验打折扣**。Snowflake 虽然跨云（AWS/Azure/GCP 都能跑），但最佳体验仍在 AWS 上。BigQuery 离开 GCP 就没法用。Redshift 和 AWS 生态的绑定就更不用说了。在选云数仓之前，先锁死你的云厂商。
:::

#### 国内云数仓

国内三大云厂商也都有自己的全托管数仓产品：

| 云厂商     | 产品名             | 核心特点                                |
| ------- | --------------- | ----------------------------------- |
| **阿里云** | AnalyticDB（ADB） | 兼容 MySQL/PG，内置向量化引擎和机器学习，千亿级数据亚秒级响应 |
| **华为云** | GaussDB(DWS)    | 源于 Greenplum，PB 级全托管，融合 AI 和政企场景    |
| **腾讯云** | TCHouse         | 整合 ClickHouse、Doris 等引擎的云数仓品牌       |

### 3.2 实时交互式分析

如果说云数仓三巨头是"重型分析武器"，那 ClickHouse、Doris、StarRocks 这些就是"轻量级突击步枪"——部署简单、性能极致、场景聚焦。

#### ClickHouse —— 性能极致的实时分析引擎

**ClickHouse** 由俄罗斯搜索引擎公司 Yandex 开源，它的特点是：**快，快得离谱**。为了极致压缩和向量化查询，ClickHouse 不惜牺牲 OLTP 的特性（如单条更新、事务）。

```sql
-- ClickHouse 擅长的场景：海量日志分析
-- 统计过去 24 小时内每个 API 端点的调用次数、P99 延迟

SELECT
    endpoint,
    count(*) AS call_count,
    quantile(0.99)(latency_ms) AS p99_latency  -- P99 延迟：最慢的 1% 请求的延迟
FROM api_logs
WHERE event_time >= now() - INTERVAL 24 HOUR
GROUP BY endpoint
ORDER BY call_count DESC;
```

**适用场景**：日志分析、用户行为漏斗、监控大屏、时序数据聚合——**场景非常聚焦，但在这个场景里无可匹敌**。

#### Apache Doris —— 百度开源的明星项目

**Apache Doris** 是百度贡献给 Apache 基金会的分析型数据库，也是近年来国内最火的开源分析项目之一。它的核心优势是**极致易用**：高并发下秒级多表 JOIN 查询，适合报表分析和实时看板。

Doris 的商业版叫 **SelectDB**，由原百度 Doris 团队核心成员创立，提供了云原生版本和更完善的企业级功能。

#### StarRocks —— 极速向量化分析

**StarRocks** 与 Doris 同源但走向独立演进。它的向量化引擎性能更极致，分析物化视图极强，服务了京东、小红书等头部互联网公司。商业公司为镜舟科技。

| 对比维度    | ClickHouse       | Apache Doris | StarRocks    |
| ------- | ---------------- | ------------ | ------------ |
| 开源组织    | Yandex           | Apache 基金会   | Linux 基金会    |
| 核心亮点    | 极致单表查询性能         | 高并发多表 JOIN   | 向量化引擎 + 物化视图 |
| SQL 兼容性 | 自定义 SQL（类 MySQL） | 兼容 MySQL 协议  | 兼容 MySQL 协议  |
| 多表 JOIN | 弱（不推荐频繁 JOIN）    | 强（秒级多表关联）    | 强（物化视图加速）    |
| 更新/删除   | 弱（不擅长单条更新）       | 支持 Upsert    | 支持 Upsert    |
| 典型场景    | 日志分析、监控大屏        | 报表分析、实时看板    | 极速数据分析、多维分析  |

#### Hologres —— 阿里云的 HSAP 利器

**Hologres** 是阿里云与实时计算 Flink 深度集成的 HSAP（Hybrid Serving/Analytical Processing，服务与分析一体化）产品。它的核心亮点是：支持对**实时写入**的数据进行**毫秒级分析**。阿里双十一的实时大屏就是基于 Hologres 构建的。

### 3.3 嵌入式分析：DuckDB

**DuckDB** 立志成为分析界的 SQLite——进程内嵌入式 OLAP 数据库。你不需要安装任何服务，直接在 Python、R、Node.js 中 `import duckdb`，就能用 SQL 快速分析本地的 CSV、Parquet、JSON 文件。

```python
# DuckDB 的简单使用：直接查 CSV 文件
import duckdb

# 查询本地 CSV 文件，不需要建表
result = duckdb.sql("""
    SELECT
        category,
        SUM(amount) AS total_sales,
        AVG(amount) AS avg_sales,
        COUNT(*) AS order_count
    FROM 'orders_2026.csv'
    WHERE order_date >= '2026-07-01'
    GROUP BY category
    ORDER BY total_sales DESC
    LIMIT 10
""")

print(result)
```

**适用场景**：数据科学家和分析师在本地处理几十 GB 级数据集，代替 Pandas 做复杂分析；构建轻量级数据处理管道。它不是用来做服务器端多用户访问的，而是提升单机分析生产力的超级工具。

如果要从头选一个实时 OLAP，可以参考这个简单规则：

```text
你要分析的是"日志"→ ClickHouse
你要分析的是"报表"→ Doris / StarRocks
你在阿里云上跑    → Hologres（跟 Flink 深度集成）
你要单机分析 CSV  → DuckDB
```

## 四、NoSQL 多模型数据库

用关系型数据库处理一切，就像用一把瑞士军刀做所有事——它能行，但遇到专业场景还是有点别扭。NoSQL 数据库就是为了这些"专业场景"而生的。

我在 [NoSQL数据库理论入门——Redis与MongoDB](../编程生涯nosql数据库理论入门redis与mongodb/) 中详细学过 Redis 和 MongoDB 的原理与用法，这里不再重复深度内容，而是把它们放在全局版图中定位。

### 4.1 键值（KV）缓存：Redis 与 Tair

**Redis** 是内存数据库的绝对霸主，用来做缓存、队列、计数器、排行榜。它的五种数据类型（String、Hash、List、Set、Zset）覆盖了绝大多数缓存场景。

**Tair** 是阿里云兼容 Redis 协议的 KV 产品，增加了**内存 + SSD 混合存储**——热数据在内存中毫秒级访问，冷数据下沉到 SSD 降低成本。当你的 Redis 存储成本失控时，Tair 的混合存储方案能省不少钱。

### 4.2 文档数据库：MongoDB

**MongoDB** 使用 JSON 文档模型，数据存为 BSON（Binary JSON）格式。相比关系型的固定表结构，MongoDB 的 Schema-less 让开发者可以快速迭代数据结构——新增字段直接写文档就行，不需要 `ALTER TABLE`。

适合场景：内容管理、用户画像、日志存储、产品目录等灵活数据结构需求。

### 4.3 列族数据库：HBase 与 Cassandra

**Apache HBase** 运行在 HDFS 之上，专门为海量数据的随机读写设计。我在 [大数据技术栈](../编程生涯大数据技术栈/) 中详细分析过它的角色——PB 级别的订单流水、用户画像、监控指标，HBase 都能毫秒级定位。

**Apache Cassandra** 则是另一种列族数据库的设计哲学——去中心化、无单点故障、最终一致性。每个节点地位平等，没有 Master 节点，非常适合多数据中心部署。

### 4.4 图数据库：Neo4j

**Neo4j** 是图数据库的事实标准。它以"节点 + 关系"的形式存储数据，天然适合社交关系、反欺诈、知识图谱等场景。

```text
图数据库的直观理解：

传统的"好友关系"在 MySQL 中：
  users 表 + friends 表（userId, friendId）→ 查"好友的好友"需要多次 JOIN

在 Neo4j 中：
  (张三)-[:朋友]->(李四)
  (李四)-[:朋友]->(王五)
  (王五)-[:朋友]->(张三)

查"张三的朋友的朋友" → 沿着 [:朋友] 关系走两步就行
```

国内云厂商也提供了兼容的图数据库服务：阿里云 GDB、腾讯云 TGDB。

### 4.5 时序数据库：InfluxDB 与 TDengine

**InfluxDB** 是 IoT 和监控场景的经典时序数据库选型。它针对时间戳、标签、字段值的写操作做了极致优化。

**TDengine**（涛思数据）是国产自研的高性能时序数据库，超级压缩率（通常 10-20 倍），SQL 支持极好，适合工业物联网场景。

### 4.6 搜索引擎：Elasticsearch

**Elasticsearch** 已经不只是搜索工具了——它是日志分析、APM（Application Performance Monitoring，应用性能监控）、SIEM（Security Information and Event Management，安全信息和事件管理）平台的底层核心。

我在 [ELK技术栈——日志处理的瑞士军刀](../编程生涯elk技术栈/) 中详细拆解过它的倒排索引原理和分布式架构。简而言之：**它用倒排索引把全表扫描变成了关键词查找**。

:::note
Elasticsearch 和 PG 的 GIN 索引的核心原理是一样的——都是倒排索引。区别在于 ES 是"专职"搜索引擎，在分布式分片、实时聚合分析上比 PG 要专业得多。**中小规模的全文搜索用 PG + GIN 完全够用，但大规模日志分析和搜索聚合，ES 仍然是王者。**
:::

## 五、新兴数据库赛道

这两年，数据库世界出现了两个崛起最快的新赛道——向量数据库和湖仓一体。

### 5.1 向量数据库（AI 时代的基石）

大模型的爆发催生了向量数据库——用 Embedding 向量来表示文本、图像、音视频的语义，然后通过向量相似度搜索来实现语义检索。

这跟传统的关键词搜索完全不同：传统搜索要"包含某个词"，向量搜索找的是"意思相近的内容"。

```text
关键词搜索 vs 向量搜索：

搜索"番茄炒蛋"：

传统搜索引擎（ES）：
  "番茄炒蛋" → 找包含"番茄"或"炒蛋"的文档
  → 可能找到"番茄炒牛肉"、"炒蛋攻略"——关键词匹配，语义有限

向量搜索引擎（Milvus/Pinecone）：
  "番茄炒蛋" → 转为 Embedding 向量 → 找语义最相似的文档
  → 可能找到"西红柿鸡蛋做法"、"番茄蛋花汤"——语义匹配，意思相近
```

**主流产品：**

- **Milvus**（Zilliz 出品）：开源向量数据库标杆，社区活跃度极高
- **Pinecone**：SaaS 模式的全托管向量库，上手最简单
- **Chroma**：轻量级嵌入式向量库，适合 AI 原型开发
- **pgvector**：PostgreSQL 的向量检索插件——如果你的 PG 已经在用了，直接用 pgvector 扩展就行了

:::tip
向量数据库的选型有一条简单规则：**你在哪个数据库生态里，先用它的向量能力**。用 PG 就上 pgvector，用 ES 就上 dense\_vector，用 Redis 就上 RediSearch。只有这些方案都扛不住了，才考虑单独的 Milvus 或 Pinecone。
:::

### 5.2 湖仓一体：打破数据湖与数仓的墙

传统架构中，数据湖（存原始数据，用 Spark/Hive 分析）和数据仓库（存结构化数据，用 SQL 分析）是分开的。这就导致了"数据湖里的数据导不到数仓里，数仓里分析不了原始数据"的尴尬局面。

**湖仓一体（Lakehouse）** 的核心思路是：底层用廉价的对象存储（像数据湖一样），上层用开放表格式（如 Apache Iceberg）提供 ACID 事务、时间旅行、模式演进等数据仓库级别的能力。计算引擎（Spark、Flink、Trino）可以直接读取同一份数据，互不干扰。

```text
湖仓一体架构的核心：

┌──────────────────────────────────────┐
│  多种计算引擎                          │
│  Spark / Flink / Trino / ...         │  ← 解耦，各引擎直接读数据
├──────────────────────────────────────┤
│  开放表格式                            │
│  Apache Iceberg / Delta Lake / Hudi  │  ← ACID 事务 + 时间旅行
├──────────────────────────────────────┤
│  廉价对象存储                          │
│  AWS S3 / 阿里云 OSS / MinIO          │  ← 无限容量 + 低成本
└──────────────────────────────────────┘
```

**Databricks** 是湖仓一体概念的提出者和最主要的推动者。它提供了围绕 Delta Lake 格式的整套分析平台，在数据分析师和数据科学家群体中口碑极好。

开源表格式三巨头：

- **Apache Iceberg**：最活跃的开源表格式，Netflix 贡献，社区生态最广
- **Delta Lake**：Databricks 贡献，与 Spark 集成最紧密
- **Apache Hudi**：Uber 贡献，擅长增量写入和 upsert 场景

## 六、全场景选型指南

前面梳理了六大赛道、几十种数据库，现在是时候把这些知识点转化成**可执行的选择决策了**。

### 按场景速查

| 场景                 | 首选方案                    | 备选方案                         | 一句话理由                  |
| ------------------ | ----------------------- | ---------------------------- | ---------------------- |
| **核心业务交易（TB 级以内）** | PostgreSQL / MySQL      | PolarDB / TDSQL-C            | 简单、成熟、社区强大             |
| **海量并发交易（需水平扩展）**  | TiDB / OceanBase        | CockroachDB / YugabyteDB     | 保留 SQL 体验 + 分布式弹性      |
| **云上简化运维**         | Amazon Aurora / PolarDB | GaussDB / TDSQL-C            | 存算分离，自动扩缩容             |
| **海量数据离线报表、BI 分析** | Snowflake / BigQuery    | AnalyticDB / GaussDB(DWS)    | 云原生弹性，零运维              |
| **实时日志 / 事件分析**    | ClickHouse              | Apache Doris / StarRocks     | 速度优先，场景聚焦              |
| **灵活文档存储**         | MongoDB                 | PostgreSQL + JSONB           | Schema-less，快速迭代       |
| **缓存加速 / 高并发访问**   | Redis                   | Tair / 自建 in-memory          | 微秒级响应，生态最成熟            |
| **全文搜索**           | Elasticsearch           | PostgreSQL + GIN 索引          | 小规模用 PG，大规模用 ES        |
| **图关系 / 知识图谱**     | Neo4j                   | PostgreSQL + AGE / 阿里云 GDB   | 专职图库性能更优               |
| **时序数据 / IoT 监控**  | TDengine                | InfluxDB / TimescaleDB       | 国产时序库性能与压缩率领先          |
| **AI 向量检索 / RAG**  | Milvus                  | Chroma / pgvector / Pinecone | 开源首选 Milvus，轻量用 Chroma |
| **本地 / 单机数据分析**    | DuckDB                  | SQLite + 聚合查询                | 分析界的 SQLite，瞬间上手       |
| **移动端 / 嵌入式本地存储**  | SQLite                  | Realm / RocksDB              | 零配置，一个文件即数据库           |
| **湖仓融合架构**         | Databricks + Iceberg    | 华为 / 阿里云湖仓一体方案               | 多种引擎同时分析同一份数据          |

### 几个选型核心原则

1. **不要为了"时髦"而选型**。Kubernetes 集群上跑个 PostgreSQL 比什么"NewSQL"都稳定——90% 的互联网创业公司的数据量，PG 或 MySQL 都扛得住。
2. **NoSQL 不是 SQL 的替代品，而是互补品**。用 Redis 做缓存是为了缓解 MySQL 的压力，用 MongoDB 存灵活文档是因为关系型做这事真的很痛苦——它们不是非此即彼的关系。
3. **云原生数据库是趋势**。如果你的业务在云上，一定要用云厂商的托管服务。自己搭建集群的运维成本，远超那一点托管费用。
4. **HTAP 虽好，不要贪杯**。一个数据库想同时做好 OLTP 和 OLAP，必然在某个维度上做了妥协。先用专职数据库跑起来，等运维成本真的成了瓶颈时，再考虑 HTAP。
