## 从「设备连上」到「设备管好」

「设备连上」**和**「设备管好」**之间的鸿沟是一条天堑。原始数据是散的，只有把它加工成指标，才能串联起管理和决策。**

### 三个核心问题

生产管理对设备的核心关切，可以归结为三个问题：

| 问题       | 指标                 | 一句话解释                        |
| -------- | ------------------ | ---------------------------- |
| 设备开得好不好？ | **OEE（设备综合效率）**    | 一个数字告诉你设备「时间 × 速度 × 质量」的综合表现 |
| 设备稳不稳？   | **MTBF（平均故障间隔时间）** | 设备平均多久坏一次                    |
| 修得快不快？   | **MTTR（平均修复时间）**   | 设备坏了平均多久修好                   |

这三者构成了设备管理的「黄金三角」——**OEE 看效果，MTBF 看可靠性，MTTR 看可维护性**。接下来逐个拆解。

## 一、OEE——衡量设备「好不好」的黄金标准

### 1.1 OEE 是什么

**OEE（Overall Equipment Effectiveness，设备综合效率）** 是精益生产中最核心的设备效率衡量指标，由日本丰田体系推广而来。它的精妙之处在于：**用一个数字，同时回答三个问题——时间利用率、速度表现、质量水平。**

OEE 的公式看似简单：

```
OEE = 可用率 × 性能开动率 × 良品率
```

但拆开来看，里面藏着一整套时间管理哲学。

### 1.2 时间链条拆解

理解 OEE 必须先理解「时间」的层级划分。如果你直接把「设备工作了多久」当作效率的衡量标准，很可能会得出完全错误的结论。

:::important
**时间链条的精髓在于「层层扣除」**：每一层扣除的都是不同维度的损失，对应不同的管理责任。
:::

```text
时间层级拆解（以一天 24 小时为例）：
┌─────────────────────────────────────────────────┐
│  ① 日历总时间 = 24 小时                           │  理论最大可用时间
├─────────────────────────────────────────────────┤
│  ② 计划生产时间（负荷时间）= 日历总时间 — 计划内停机   │  排程表上的"计划开工时间"
│                          = 24h — 8h(休息+保养)   │
│                          = 16h                  │
├─────────────────────────────────────────────────┤
│  ③ 稼动时间 = 计划生产时间 — 非计划停机              │  设备真正"赚钱"的时间
│             = 16h — 2h(故障+换型+待料)            │
│             = 14h                               │
├─────────────────────────────────────────────────┤
│  ④ 净稼动时间 = 稼动时间 × 速度效率                  │  扣除速度损失后的时间
├─────────────────────────────────────────────────┤
│  ⑤ 价值稼动时间 = 净稼动时间 × 良品率                │  真正创造价值的时间
└─────────────────────────────────────────────────┘
```

每一层的时间，对应 OEE 的三个分项：

| OEE 分项                 | 计算公式                      | 对应的时间维度  | 反映的问题          |
| ---------------------- | ------------------------- | -------- | -------------- |
| **可用率（Availability）**  | 稼动时间 ÷ 计划生产时间 × 100%      | ③ ÷ ②    | 设备停了多久？（时间损失）  |
| **性能开动率（Performance）** | 理论节拍 × 实际产量 ÷ 稼动时间 × 100% | 产量倒推 ÷ ③ | 设备跑得快不快？（速度损失） |
| **良品率（Quality）**       | 合格品数量 ÷ 实际产量 × 100%       | ⑤ ÷ ④    | 设备做得好不好？（质量损失） |

### 1.3 「稼动」这个词为什么这么叫？

「稼动」为什么不叫「机动」或者「运转」等更好从字面意思去理解的词语？

:::note
**「稼动」源自日语「稼働」（Kadō）**。日语中「稼ぐ」（Kasegu）是「赚钱」的意思。所以「稼動」的字面直译是 **「为了赚钱而运转」**——只有生产合格品、创造价值的那部分时间，才配叫稼动时间。设备空转、试加工、调试都不算。
:::

这个命名自带一种「成本意识」。它提醒管理者：设备一转就是在花钱（折旧、电费、人工），只有「稼」着转才能把钱赚回来。

### 1.4 性能开动率的灵魂：理论节拍时间

理论节拍时间（Theoretical Cycle Time，简称理论 CT）是计算性能开动率的核心参数。

**理论节拍**是指设备在理想状态下，没有任何停顿和减速，连续生产一个合格产品所需的最短时间。它由设备制造商的硬件极限决定——马达转速、机械行程、电气响应速度，这些都是物理上限。

这里有一个非常容易混淆的概念群：

| 术语                  | 定义           | 由谁决定  | 管理含义                    |
| ------------------- | ------------ | ----- | ----------------------- |
| **理论节拍**            | 设备设计的极限速度    | 设备制造商 | 追求的终极目标，但永远不能突破         |
| **实际节拍**            | 今天实测的平均生产速度  | 现场统计  | 需要无限逼近理论节拍              |
| **需求节拍（Takt Time）** | 为满足订单必须多久出一个 | 市场和销售 | 如果需求节拍慢于理论节拍，降速生产不算速度损失 |

:::caution
**一个常见的误算**：当需求节拍慢于理论节拍时，如果直接用「理论节拍 × 产量 ÷ 稼动时间」计算性能开动率，会得出小于 100% 的「损失」——但这不是速度损失，而是「计划性低速」。严谨的做法是：当需求节拍 < 理论节拍时，用**需求节拍**替代理论节拍作为计算的基准。
:::

### 1.5 一个完整的 OEE 计算示例

假设一条产线的数据如下：

- 计划生产时间：8 小时（480 分钟）
- 设备故障停机：30 分钟
- 换型调整：20 分钟
- 待料停机：10 分钟
- 理论节拍：1 分钟/个
- 实际产量：380 个
- 合格品数：360 个

**第一步：计算可用率**

```text
稼动时间 = 480 - 30 - 20 - 10 = 420 分钟
可用率 = 420 ÷ 480 = 87.5%
```

**第二步：计算性能开动率**

```text
性能开动率 = (1 分钟 × 380 个) ÷ 420 分钟 = 90.5%
```

**第三步：计算良品率**

```text
良品率 = 360 ÷ 380 = 94.7%
```

**第四步：计算 OEE**

```text
OEE = 87.5% × 90.5% × 94.7% = 75.0%
```

:::important
**世界级制造标准**：OEE > 85% 属于世界级水平；60%-85% 属于正常水平；< 60% 说明有较大的改善空间。这个数字在各行业略有不同，但大致范围一致。
:::

## 二、MTBF 与 MTTR——可靠性与可维护性的两把尺

OEE 衡量的是「综合表现」，但要深入回答「设备为什么表现不好」，还需要 MTBF 和 MTTR 这两个指标。

### 2.1 MTBF——设备稳不稳

**MTBF（Mean Time Between Failures，平均故障间隔时间）** 衡量设备的可靠性——平均来说，设备正常运行多久会出一次故障。

```
MTBF = 总正常运行时长 ÷ 故障发生次数
```

比如，一台设备在一个月内运行了 700 小时，发生了 5 次故障，那么 MTBF = 700 ÷ 5 = 140 小时。

:::tip
**MTBF 越大越好**。它反映了设备的「本质可靠性」——设计水平、制造质量、维护保养的综合体现。
:::

### 2.2 MTTR——修得快不快

**MTTR（Mean Time To Repair，平均修复时间）** 衡量设备的可维护性——从故障发生到修复完成，平均花了多长时间。

```
MTTR = 总故障维修时长 ÷ 故障发生次数
```

如果 5 次故障的总维修时长为 10 小时，那么 MTTR = 10 ÷ 5 = 2 小时。

:::tip
**MTTR 越小越好**。它反映的是维修团队的响应速度、备件库存管理和故障诊断能力。
:::

### 2.3 最容易被忽略的区分：故障停机 vs 非故障停机

在计算 MTBF 和 MTTR 时，有一个**最容易被踩的坑**：

| 停机类型     | 举例              | 是否计入 MTBF/MTTR |
| -------- | --------------- | -------------- |
| **故障停机** | 电机烧毁、传感器故障、机械卡死 | ✅ 计入           |
| **换型调整** | 切换产品型号时的模具更换    | ❌ 不计入          |
| **待料停机** | 等待上游物料到达        | ❌ 不计入          |
| **计划停机** | 定期保养、节假日        | ❌ 不计入          |

:::warning
**停机分类混淆是数据治理中最常见的问题**。如果 MES 系统中把「换型停机」也被标记为「故障」，MTBF 会被严重低估——因为非故障事件被错误地计入了故障次数。这会导致维修团队被「冤枉」，管理者做出错误的决策。

解决方案很简单但必须严格执行：在数采阶段就做到**停机原因标准化分类**，在源头上保证数据质量。
:::

### 2.4 MTBF 和 MTTR 的协同意义

| MTBF | MTTR | 含义                          |
| ---- | ---- | --------------------------- |
| 高    | 低    | **理想状态**：设备很少坏，坏了也能快速修好     |
| 高    | 高    | 设备本身可靠，但维修效率低（备件不到位、技术能力不足） |
| 低    | 低    | 设备不太可靠，但维修团队响应很快（适合备机充足的场景） |
| 低    | 高    | **最差状态**：设备经常坏，修得还慢（需要重点关注） |

## 三、数采指标的数据模型设计

理论讲完了，接下来是最核心的问题：**原始数据长什么样？怎么把它加工成指标？**

### 3.1 必须采集的原始字段全景

根据OEE 和 MTBF/MTTR 的计算公式，我们可以整理出数采系统必须采集的核心字段：

#### OEE 字段清单

| 字段         | 说明           | 来源          | 计算用途        |
| ---------- | ------------ | ----------- | ----------- |
| 计划生产开始时间   | 班次计划开工时间     | MES / 排程系统  | 计算计划生产时长    |
| 计划生产结束时间   | 班次计划完工时间     | MES / 排程系统  | 计算计划生产时长    |
| 设备实际稼动开始时间 | 设备真正开始干活的时间  | SCADA / PLC | 计算稼动时长      |
| 设备实际稼动结束时间 | 设备停止干活的时间    | SCADA / PLC | 计算稼动时长      |
| 理论节拍       | 设备设计速度       | 设备台账（固定值）   | 计算性能开动率     |
| 实际总产量      | 本班次实际产出总数    | MES / 现场录入  | 计算性能开动率和良品率 |
| 合格品数量      | 检验通过的产品数     | MES / 质检系统  | 计算良品率       |
| 停机明细       | 每次停机的起止时间和原因 | SCADA + MES | 核算稼动时间      |

#### MTBF/MTTR 字段清单

| 字段     | 说明                    | 来源             | 计算用途     |
| ------ | --------------------- | -------------- | -------- |
| 故障触发时间 | 故障发生的时间点              | SCADA / PLC 报警 | 确定故障起点   |
| 维修到达时间 | 维修人员开始响应的时间           | MES 报修系统       | 评估响应速度   |
| 维修完成时间 | 维修完成、设备恢复运行的时间        | MES 报修系统       | 计算维修时长   |
| 故障原因分类 | 标准化故障代码（机械/电气/软件/操作等） | 维修工单           | 统计分析     |
| 停机原因标签 | 故障 vs 非故障（关键区分字段）     | MES / 现场录入     | 保证指标口径正确 |

#### 公共基础字段

| 字段     | 说明                |
| ------ | ----------------- |
| 设备唯一编号 | 设备台账 ID，按单台设备分别核算 |
| 设备名称   | 便于阅读的显示名称         |
| 产线/车间  | 组织维度，用于聚合分析       |
| 班次     | 早/中/晚班，用于班次效率分析   |
| 时间戳    | 所有事件的标准时间记录，精度到秒  |

### 3.2 从原始数据到指标的 ETL 流程

采集到的原始数据不是直接拿来算指标的，需要经过一个标准的处理流水线：

```text
原始数据 → 清洗 → 聚合 → 计算 → 存储 → 展示

① 采集层：PLC/SCADA 定时上报设备状态、产量、报警事件
② 清洗层：剔除异常值（传感器抖动）、补全缺失时间戳、统一停机分类
③ 聚合层：按设备 × 班次 × 日期聚合原始事件，计算中间变量
④ 计算层：代入 OEE / MTBF / MTTR 公式，产出最终指标
⑤ 存储层：写入时序数据库（如 InfluxDB）或关系库（如 MySQL）
⑥ 展示层：BI 看板、Grafana 仪表盘、日报推送
```

## 四、指标在 IoT 平台中的落地实战

有了数据模型和 ETL 流程，接下来就是怎么让指标「用起来」。

### 4.1 指标看板设计

指标看板是指标建设的「最后一公里」——再好的指标，如果不能被一线管理和决策者直观看到，就没有价值。

参考[数据可视化之BI](../编程生涯数据可视化之bi/)中讲到的看板设计原则，设备指标看板应该分为三个层级：

#### 第一层：总览层（面向管理层）

```text
┌─────────────────────────────────────────────────────┐
│                 设备效率总览                          │
├──────────────┬──────────────┬──────────────┬────────┤
│  OEE 75.0%   │  可用率 87.5% │ 性能率 90.5%  │ 良品率  │
│  ▲ 2.1%      │  ▼ 1.3%      │  ▲ 0.5%      │ 94.7%  │
│  (环比昨日)   │               │              │ ▲ 0.3% │
├──────────────┼──────────────┼──────────────┼─────────┤
│  MTBF        │  MTTR        │  重点关注设备  │         │
│  140h        │  2h          │  3号线B设备   │         │
│  ▼ 5%        │  ▲ 10%       │  OEE < 60%   │         │
└──────────────┴──────────────┴──────────────┴─────────┘
```

#### 第二层：趋势层（面向工程师）

- OEE 7 日趋势线图（可下钻到 24 小时）
- MTBF/MTTR 月度趋势对比
- 各设备 OEE 横向排名

#### 第三层：明细层（面向维修/生产人员）

- 当班设备运行状态（绿/黄/红）
- 当前故障报警列表
- 故障历史查询

### 4.2 告警策略：基于 MTBF/MTTR 的动态阈值

传统的固定阈值告警（比如「温度 > 80°C 就报警」）在设备管理中远远不够。更好的做法是**基于历史 MTBF 数据设定动态基线**：

| 告警级别 | 触发条件                  | 通知方式           | 响应要求       |
| ---- | --------------------- | -------------- | ---------- |
| 信息   | 单台设备 OEE < 60% 超过 1 天 | 邮件             | 关注         |
| 警告   | 当月 MTBF 低于历史基线 20%    | 邮件 + 企业微信      | 24 小时内分析原因 |
| 严重   | 关键设备停机超过 MTTR + 30 分钟 | 电话 + 短信        | 30 分钟内响应   |
| 紧急   | P1 级设备故障，产线全面停线       | 电话 + 短信 + 值班经理 | 5 分钟内响应    |

### 4.3 联动 BI 系统

指标数据不应该只停留在「监控看板」——它可以和 BI 系统联动，形成完整的决策闭环：

```text
设备运行数据
    ↓
数采平台 → 清洗 → 聚合 → 指标计算
    ↓
写入数据仓库（MySQL / ClickHouse / 时序库）
    ↓
BI 系统接入
    ├── OEE 日报：每天自动推送给生产经理
    ├── 设备健康度月报：管理层决策参考
    └── 故障归因分析：关联停机原因分类，找出共性故障
```

在前面学过的[数据可视化之BI](../编程生涯数据可视化之bi/)中，BI 系统擅长处理和展示「加工后的指标数据」——把计算结果推送到 BI，再用 Quick BI 或 DataEase 做仪表盘，是性价比很高的方案。

## 五、总结与展望

### 从「数采」到「指标」，再到「智能运维」

回顾一下整条链路：

1. **数采层**：PLC/SCADA 采集原始数据（状态、产量、报警）
2. **清洗聚合层**：ETL 处理，剔除异常，按设备和班次聚合
3. **指标计算层**：代入 OEE/MTBF/MTTR 公式，算出核心指标
4. **可视化层**：看板展示 + BI 分析 + 告警推送

这只是第一阶段。当积累了足够的历史数据后，就可以做更有价值的事情：

| 阶段                | 能力              | 技术手段      |
| ----------------- | --------------- | --------- |
| **描述性分析（发生了什么）**  | OEE 日报、MTBF 月报  | SQL + 报表  |
| **诊断性分析（为什么发生）**  | 故障归因、对比分析       | BI 下钻联动   |
| **预测性分析（将要发生什么）** | 设备剩余寿命预测、故障预警   | ML + 时序预测 |
| **指导性分析（应该怎么做）**  | 维护计划自动排程、备件智能推荐 | AI + 优化算法 |

### 对集成工程师而言

**把原始信号加工成能回答业务问题的信息是必备的能力**。

理解 OEE、MTBF、MTTR 这些指标，不只是学会了三个公式，更是理解了**制造业管理者的语言**。

当能用这些指标跟生产经理对话时，就已经从一个「写接口的工程师」变成了「懂业务的集成顾问」。
