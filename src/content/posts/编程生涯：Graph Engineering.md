## 一、九词引爆

2026年7月18日 00:34 UTC，OpenClaw 创始人 Peter Steinberger 在 X 上敲下九个词：

> **"Are we still talking loops or did we shift to graphs yet?"**

260 万次观看。72 小时内，这条推文像一根火柴扔进了火药桶。

四个半小时后，Hamel Husain（以 AI Eval 闻名的开发者）发了一篇 X 文章，标题叫《Loop Engineering Is Dead. Enter Graph Engineering.》。他是在开玩笑——但没人当真玩笑。Santiago Valdarrama 当天跟了句 "Loop Engineering is dead. Long live Graph Engineering!"，Rhys Sullivan 直接预言第二天就会有一篇万字长文阐述 Graph Engineering。

预言成真了。而且不止一篇。

:::note
2026 年 2 月 Harness Engineering、6 月 Loop Engineering、7 月 Graph Engineering——AI 工程化的命名周期已经从"半年一更"加速到"月更"了。
:::

### 为什么是现在？

Graph 编排本身一点都不新。LangGraph 做了三年，月下载量 6500 万+。AutoGen、Google ADK 都比这个词早了至少一年。所以 7 月到底变了什么？

变了的是「布线的成本」。

在此之前，编排多个 Agent 意味着你要专门学一套框架，在代码里手写节点、边和状态机。到了 2026 年 7 月，情况变了：你可以在 prompt 里描述一个目标，模型自己写出编排脚本，然后并发地 spawn 出一批子 Agent 去执行。中间结果活在脚本的变量里，而不是你的上下文窗口里——协调不烧 token，因为它是代码在跑，不是模型在想。

Claude Code 的 workflow 功能就是一段自动拆任务、派 subagent、等结果、处理分支的调度脚本，你只需要在对话框里描述目标，模型自己会写出这段脚本。执行中随时输 `/workflows` 就能看到后台的进度树——哪个节点正跑、哪些已完成、消耗了多少 token。

## 二、三分天下

Graph Engineering 分裂为三种互不兼容的定义。每一派有各自的理论框架、工具生态和拥护者。

### 第一派：编排图谱（Orchestration Graphs）

**核心主张：多 Agent 系统的拓扑结构本身是一个可编程、可版本化的工程制品。**

将系统建模为异构节点（Agent、确定性函数、路由器、Join 点、工具、人工检查点）和有向边（通信、委托、路由），共享状态沿边流动。拓扑不再是一个偶然产物，而是被显式设计、版本控制、运行时监控的对象。

这一派的工具已经存在多年：

| 工具                              | 特点                       | 定位            |
| ------------------------------- | ------------------------ | ------------- |
| **LangGraph**（LangChain）        | 三年前开始做，月下载量 6500 万+      | 最成熟的图编排框架     |
| **Microsoft AutoGen GraphFlow** | 图驱动多 Agent 编排，支持 DiGraph | 企业级多 Agent 协作 |
| **Google ADK**                  | 图工作流 + A2A 跨系统委托         | 云端原生编排        |
| **Temporal**                    | 工作流引擎，也能用于 Agent 编排      | 通用工作流         |

### 第二派：循环之图（Graphs of Loops）

**核心主张：单个反馈循环是基本单元，Graph Engineering 设计的是这些循环之间的监督、馈入、否决关系。**

一个循环有四个部件：关注的变量、目标值、衡量差距的方式、缩小差距的动作。循环重复运行。Graph Engineering 是做在循环之上的元设计——定义哪个循环监控哪个、哪个有否决权、数据以什么节奏在这些循环之间流动。

这是三派中最抽象的一个，也最缺乏可操作的工程实践。它提出了一个真实问题：当你有几十个自治循环同时运行时，怎么保证它们不会互相抵消？但回答还停留在概念层面。

:::caution
循环之派虽然最"新"、听起来最深刻，但恰恰因为它缺乏工程落地，最容易成为"PPT 架构"——说出去好听，跑起来无从下手。如果你想实操 Graph Engineering，建议从第一派（编排图谱）开始。
:::

### 第三派：图谱知识与记忆（Graph-Structured Knowledge and Memory）

**核心主张：Agent 的知识存量应被建模为带类型的节点和边的图谱，Agent 在这些节点间遍历推理，而不是在扁平文本块中做语义搜索。**

代表项目：

- **Microsoft GraphRAG / LightRAG** — 从文本语料自动提取知识图谱。GraphRAG 的公开数据显示：准确率比纯文档检索高 18%，token 成本降低 85%，单次查询成本约 $0.004
- **Graphiti / Zep** — 时间感知的 Agent 记忆图谱，增量吸收每轮对话
- **Neo4j** — 三层记忆模型（短期会话 / 长期类型化实体 / 推理轨迹）
- **mcp-neo4j-agent-memory** — 10 个专用工具的知识图谱 Agent 记忆

### 对照总表

| 维度       | 编排图谱               | 循环之图     | 图谱知识            |
| -------- | ------------------ | -------- | --------------- |
| **核心问题** | 如何编排多个 Agent       | 如何协调多个循环 | 如何组织知识          |
| **成熟度**  | 高                  | 低        | 中               |
| **工具代表** | LangGraph, AutoGen | 尚无成熟工具   | GraphRAG, Neo4j |
| **适合谁**  | 想做多 Agent 系统的开发者   | 研究控制论的学者 | 做 RAG 增强的应用开发者  |

:::tip
这三派不是互斥的。一个成熟的生产系统完全可以同时采用三种视角：用编排图谱管理 Agent 拓扑，用循环之图的思维设计反馈回路，用图谱知识支撑 Agent 的长时记忆。
:::

## 三、拆开就三样东西

三派分立听起来很热闹，但绕开名字的包装，底层是同一套东西。一张 graph，拆开就三样：**节点（Node）**、**边（Edge）**、**状态（State）**。

### Node：干活的那个

一个节点可以是一个跑着完整思考循环的 Agent，也可以是一段按照固定规则运行的普通代码，或者一次数据库查询。甚至，人也行——审批环节就是一个典型的人类节点：前面的任务流进来，你做出决定，后面的任务再继续往下走。

好节点的标准特别朴素：

- 它只干一件事
- 单独就能测
- 哪天想换掉它，别的节点不受牵连

**一个节点要是身兼五职，那它就不是节点了——它就是又一个大 Loop。**

### Edge：走哪条路

设计一条边，其实是在回答两个问题：下一个节点由什么决定？是否要根据结果选择不同分支？

**由什么决定下一个节点？**

| 边类型                           | 谁来决策    | 例子                    |
| ----------------------------- | ------- | --------------------- |
| **确定性边**（Deterministic Edge）  | 写死的代码逻辑 | 测试全部通过 → 进入部署，不需要模型掺和 |
| **模型决策边**（Model-decided Edge） | 模型判断    | 工单进来，该派给退款节点还是投诉节点    |

**设计的功夫就在分清哪条边该写死、哪条该交给模型。** 能写死的尽量写死，把模型的判断能力留给少数确实需要理解语义的分支。

**流程是否固定？**

- **固定边**：总是进入同一个节点
- **条件边**（Conditional Edge）：根据上一步的结果分叉——测试通过 → 下一个节点，测试失败 → 返工节点

条件边和前面两种不是并列关系。一条条件边既可以由代码判断（"测试通过就审批"），也可以由模型判断（"根据工单内容分到退款或投诉"）。

### State：任务的存档点

任务按照 graph 定义的顺序依次经过各个节点，执行到哪、每一步产出了什么、消耗了多少 token——这些信息总得有个地方存着。这个地方就是状态。

你可以把它理解成一张字段固定的任务进度表：

```json
{
  "plan": { "status": "done", "artifact": "spec-v2.md" },
  "backend": { "status": "done", "artifact": "api/export.js" },
  "frontend": { "status": "running" },
  "tests": { "status": "pending" },
  "tokens_used": 12000
}
```

谁要看进度，读这个对象就行，不用再钻进一大段聊天记录里翻。

有了存档，流程中断就完全不是一回事了。以前中断叫「这一趟白跑了」，现在中断叫「读档，重试那一个节点」。**就像玩游戏——没有存档点的游戏，死一次回出生点，谁受得了？**

### 三个核心动作

三样东西凑齐，几个关键操作就自然浮现了：

```text
分支并行（fan-out）
    一个节点同时分出多条边，启动多个节点并行执行

汇合（fan-in）
    多个节点全部完成后，汇聚到一个节点继续

条件跳转
    根据上一步结果，走不同的分支路径
```

### 那 Loop 去哪了？

这是整篇文章最需要厘清的一个问题。

**Loop 没有死。恰恰相反，Loop 是 Graph 的最小单元。**

你可以把一个 Loop 理解成一张最小的 Graph——只有一个节点（Node），一条边（Edge），而且这条边指回自己。Graph 上每个 Agent 节点的内部，跑的仍然是那个熟悉的思考循环：接收输入 → 调用工具 → 验证结果 → 决定下一步。

```text
Loop（单个 Agent 内部）
  输入 → 思考 → 工具调用 → 验证 → 再思考 → ...
  ↑______________________________________|

Graph（多个节点的编排）
  [规划节点] ─→ [后端节点] ─→ [集成节点] ─→ [审批节点]
                → [前端节点] ─↑
                → [测试节点] ─↑
                     ↑ 每个节点内部仍然是一个 Loop
```

所以，**Loop Engineering 管的是节点内部，Graph Engineering 管的是节点之间。** 两者根本不是一个层面的东西，不存在谁取代谁。

## 四、那个没人敢提的陷阱

Graph Engineering 最锋利的一句警告来自 towards\_AI：

> **"Without anchors, a graph is a larger hallucination with better project management."**

翻译过来就是：「没有现实锚点，图不过是一场被项目管理包装得更大型的幻觉。」

你可以画出一张无比精美的 DAG，节点整齐、依赖清晰、并行也漂亮——但要是每个节点的产出都没有经过现实验证，整张图就是一台「自动化地生产错误」的机器。

### 什么时候不该用 Graph？

| 场景          | 用 Graph 的效果  | 建议             |
| ----------- | ------------ | -------------- |
| 写个脚本、修个 Bug | 杀鸡用牛刀        | 直接串行，一个人干完     |
| 简单调研、单步任务   | 无意义增加复杂度     | 一个 Agent 就够了   |
| 节点本身不可靠     | 放大错误         | 先确保每个节点稳定，再谈编排 |
| 缺乏度量标准      | 无法判断好坏       | 先建立验证机制        |
| 团队只有一个人     | 编排的收益 < 沟通成本 | 手动流程更高效        |

### Reality Anchor 怎么做？

1. **每个节点必须有可验证的产出标准**——不是一个"感觉对了"的评审，而是一个程序能判断的 pass/fail
2. **图里至少有一个节点是"现实锚点"**——比如人工审批、外部 API 数据校验、物理传感器的读数
3. **长期运行的图必须有审计日志**——每个节点执行前后的状态快照，出了事能回溯

:::important
画图之前，先回答一个问题：这张图里哪个节点负责"戳破幻觉"？如果你的答案是没有——那你正在搭建的不是编排系统，而是一个幻觉放大器。
:::

## 五、从 Loop 到 Graph，再到什么？

### 范式演进链补完

在[《Loop Engineering》](../编程生涯loop-engineering/)里，我列出了到 2026 年中的四阶段演进：

```text
阶段一（2022-2024）：Prompt Engineering（提示词工程）
  → 核心：怎么写提示词让 AI 回答更好

阶段二（2025）：Context Engineering（上下文工程）
  → 核心：怎么在对的时候把对的信息喂给 AI

阶段三（2026年初）：Harness Engineering（驾驭工程）
  → 核心：怎么给 AI 搭工具、写测试、设约束

阶段四（2026年中）：Loop Engineering（循环工程）
  → 核心：怎么让 AI 自己形成工作循环，自动推进
```

现在可以加上第五阶段了：

```text
阶段五（2026年7月）：Graph Engineering（图工程）
  → 核心：怎么把多个循环编排成一张可执行的图
```

但注意——**这不是一条"替换"链，而是一条"嵌套"链**。每一层都建立在下一层之上，而不是取代下一层。

```text
Graph Engineering
    ↑ 编排多个循环
Loop Engineering
    ↑ 让 Agent 自主迭代
Harness Engineering
    ↑ 给 Agent 搭工装
Context Engineering
    ↑ 喂对的信息
Prompt Engineering
    ↑ 问对的问题
```

就像网络协议栈的分层模型——每一层解决一个层面的问题，依赖下层提供的服务，但不会让下层"过时"。

### 名字会变，但核心不会

Graph Engineering 这个名字能火多久？我觉得不会太久。

但概念的消失，底层的 **Node、Edge、State 这三个东西不会消失。** 就像 Loop Engineering 背后的 cron、worktree、MCP 不会消失，就像命令工程背后的 brainstorming、TDD、code review 不会消失一样。

我在[《Loop Engineering》](../编程生涯loop-engineering/)里用过一张表，现在可以更新它：

| 新概念               | 拆开看（旧零件）                                           | 新在哪里 |
| ----------------- | -------------------------------------------------- | ---- |
| Loop Engineering  | cron + git worktree + SKILL.md + MCP + Code Review | 组合方式 |
| Graph Engineering | Node + Edge + State + Fan-out/Fan-in               | 组合方式 |
| 命令工程              | brainstorming + tdd + code-review + worktree       | 组合方式 |

**每个「新概念」都是旧零件的重新组合。**
