## 一、大数据来了——传统数据库的「滑铁卢」

### 一个经典的场景

假设你做了一个电商网站，生意火爆，每天产生上千万条用户行为和订单数据。老板让你分析一下这些数据：

> 「统计过去一个月所有用户的性别、消费金额、购买品类分布，还要按省份、按年龄段交叉分析。」

如果用 MySQL 去搞，大概率直接卡死——几亿行数据在一个表里做 `GROUP BY` + `JOIN`，查询跑个半小时都不见得能出结果。

**这不是 MySQL 不行，而是场景不对。** MySQL 这类关系型数据库，处理几百 G 数据就是极限了。当数据量到达 **TB、PB** 级别——一个订单表就有几十亿行——传统数据库从架构层面就无法胜任。

### 大数据的「三 V」特征

大数据之所以「大」，不只是体量大。业界常说的 **3V** 特征更准确地刻画了它：

| 特征      | 英文       | 通俗理解       | 举例                       |
| ------- | -------- | ---------- | ------------------------ |
| **体量大** | Volume   | 一台机器的硬盘装不下 | 单日日志量几十 TB               |
| **速度快** | Velocity | 数据产生的速度极快  | 每秒数万条用户点击                |
| **多样性** | Variety  | 数据的格式五花八门  | 结构化 JSON、非结构化图片、文本日志混在一起 |

这三个维度叠加在一起，传统工具自然扛不住。那怎么办？

### 核心思路：一个「切」字

大数据的解决思路说穿了就一个字——**切**。

一个文件太大，一台服务器存不下？切成小份，用多台服务器来存。一批数据太大，一台服务器算不动？切成小份，分给多台服务器并行算。

> 大数据处理的本质，就是把「大」切成「小」，用一群廉价机器的合力，干翻一台超级计算机。

这个思路听起来简单，但实现起来有一堆问题需要解决：谁来切？谁管这些切成块的数据？切完之后怎么查？怎么保证某台机器坏了数据不丢？——**Hadoop 就是为解决这些问题而生的。**

## 二、HDFS——给数据造一座「超大仓库」

### 存储困境：单机装不下

先解决第一个问题：**数据怎么存？**

假设你有 1PB 的数据，单个服务器最多挂几十块硬盘，根本装不下。就算强行装下，读写速度也是瓶颈——单块硬盘的顺序读写速度大约 200MB/s，1PB 的数据光读一遍就要花两个月。

解法很直接：**用多台服务器的硬盘拼在一起。**

HDFS（Hadoop Distributed File System）就是做这件事的——它把一个大文件切成固定大小的数据块（默认 **128MB**），分散存储到集群中多台服务器上。

### 架构拆解：NameNode + DataNode

```
HDFS 架构：
                    ┌─────────────┐
                    │  NameNode   │  ← 管理文件系统的「目录」
                    │ (元数据服务) │     记录每个文件被切成哪些块、存在哪台机器上
                    └──────┬──────┘
                           │
         ┌─────────────────┼─────────────────┐
         │           │            │          │
     ┌───┴───┐   ┌───┴───┐    ┌───┴───┐  ┌───┴───┐
     │DataNode│  │DataNode│   │DataNode│ │DataNode│
     │ 节点1  │   │ 节点2  │    │ 节点3  │ │ 节点4  │
     │块0 块3 │   │块1 块0'│    │块2 块1'│ │块0''块3'│  ← 每个块默认3副本
     └───────┘   └───────┘     └───────┘ └───────┘
```

| 组件             | 职责                  | 类比                        |
| -------------- | ------------------- | ------------------------- |
| **NameNode**   | 管理文件系统的目录树和元数据      | 超市中央仓库的「总账本」，记录每个货架上有哪些商品 |
| **DataNode**   | 实际存储数据块，响应读写请求      | 超市的「货架」，商品（数据块）真正放在上面     |
| **Block（数据块）** | 默认 128MB，文件被切成等大小的块 | 标准化的「快递箱」，每个箱子大小一样        |

### 副本机制：数据不丢的秘密

HDFS 的每个数据块默认存 **3 个副本**，分布在不同机器上。即使某台 DataNode 宕机了，从其他机器上也能读到数据。

```bash
# 查看 HDFS 文件信息
hdfs fs -ls /user/data/orders/
# 输出：-rw-r--r--   3  ...  /user/data/orders/2026-07-15.csv

# 查看文件的块分布
hdfs fsck /user/data/orders/2026-07-15.csv -files -blocks -locations

# 输出结果会显示：
# 该文件被切成 N 个 128MB 的块
# 每个块分别存在哪几台 DataNode 上
# 副本数是否满足配置要求
```

### 通俗比喻

HDFS 像连锁超市的 **中央仓库体系**：

- **NameNode** = 仓库管理员手里的「库存台账」，记录了每个商品（文件）放在哪个货架（DataNode）的哪个位置（Block）
- **DataNode** = 一个个实体货架，商品真正放在上面
- **副本机制** = 每个商品不只放一个货架，同一件商品在 3 个不同货架上各放一份——万一某个货架倒了，从其他货架也能拿到

### HDFS 的局限

HDFS 解决了海量数据存储的问题，但它有两个明显的短板：

- **NameNode 单点故障**：如果 NameNode 挂了，整个文件系统就不可用了（虽然 HDFS HA 方案可以解决，但运维复杂）
- **不适合存小文件**：每个文件的元数据都保存在 NameNode 内存中，大量小文件会撑爆 NameNode

:::tip
HDFS 的设计哲学是「**面向大文件、顺序读写、一次写入多次读取**」。它不适合频繁修改数据、也不适合大量随机读写——那些场景需要其他组件来补位，比如后面要讲的 HBase。
:::

## 三、MapReduce——把计算任务「拆」给多台机器

### 计算困境：单机算不动

数据存好了，接下来是第二个问题：**怎么算？**

假设我们要统计电商网站所有用户的消费总额。所有订单数据共 1.28TB，存在 HDFS 上。如果想把数据全部加载到一台服务器的内存里做计算——没有一台服务器有那么大内存。

解法跟存储一样：**计算也是「切」**。

把数据分成多份（split），分配给多台服务器并行计算，每台服务器只算自己那一份，最后汇总结果。这个思路就是 **MapReduce**。

### Map & Reduce：两个函数搞定的分布式计算

MapReduce 把整个计算过程抽象为两个阶段：

```
MapReduce 计算流程：

原始数据（1280GB 订单数据）
    │
    ▼
  [切分成 10 个 Split，每个 128GB]
    │
    ├─ Split 1  ─→ Map 任务 1  ─→ 中间结果 1  ─┐
    ├─ Split 2  ─→ Map 任务 2  ─→ 中间结果 2  ─┤
    ├─ Split 3  ─→ Map 任务 3  ─→ 中间结果 3  ─┤     Shuffle   ┌────────────┐
    ├─ Split 4  ─→ Map 任务 4  ─→ 中间结果 4  ─┤  (排序与分组)  │ Reduce 任务 │                                               → 最终结果
    ├─ Split 5  ─→ Map 任务 5  ─→ 中间结果 5  ─┤               │ (汇总计算)  │
    ├─ Split 6  ─→ Map 任务 6  ─→ 中间结果 6  ─┤               └────────────┘
    ├─ Split 7  ─→ Map 任务 7  ─→ 中间结果 7  ─┤
    ├─ Split 8  ─→ Map 任务 8  ─→ 中间结果 8  ─┤
    ├─ Split 9  ─→ Map 任务 9  ─→ 中间结果 9  ─┤
    └─ Split 10 ─→ Map 任务 10 ─→ 中间结果 10 ─┘
```

用户只需要自定义两个函数：

```java
// Map 阶段：处理每个分片中的「一行」数据
// 输入：(行号, 订单记录文本)
// 输出：(性别, 消费金额) 键值对
public class OrderMapper extends Mapper<LongWritable, Text, Text, FloatWritable> {

    @Override
    protected void map(LongWritable key,           // 行号
                       Text value,                 // 一行订单数据
                       Context context)            // 上下文，用于输出中间结果
                       throws IOException, InterruptedException {

        String line = value.toString();
        String[] fields = line.split(",");

        // 假设 CSV 格式：订单ID,用户ID,性别,消费金额,品类
        String gender = fields[2];        // 性别
        float amount = Float.parseFloat(fields[3]);  // 消费金额

        // 输出：(性别, 金额) —— 框架会自动按键分组
        context.write(new Text(gender), new FloatWritable(amount));
    }
}

// Reduce 阶段：汇总同一组的数据
// 输入：(性别, [金额1, 金额2, 金额3, ...])
// 输出：(性别, 总金额)
public class OrderReducer extends Reducer<Text, FloatWritable, Text, FloatWritable> {

    @Override
    protected void reduce(Text key,                  // 性别（男/女）
                          Iterable<FloatWritable> values,  // 该性别的所有消费金额
                          Context context)
                          throws IOException, InterruptedException {

        float sum = 0;
        for (FloatWritable val : values) {
            sum += val.get();  // 累加所有金额
        }

        // 输出：(性别, 总金额)
        context.write(key, new FloatWritable(sum));
    }
}
```

这个过程的精妙之处在于：**用户只需要关心业务逻辑（Map 怎么处理一行数据、Reduce 怎么汇总结果），而不需要关心数据怎么分发、任务怎么调度、失败怎么重试**——这些都交给 MapReduce 框架去处理。

### 通俗比喻

MapReduce 像公司年会的 **「分小组讨论 + 汇总汇报」** 流程：

- **Map** = 老板说「每个小组讨论一下自己组的年度总结」，各小组长（Map 任务）分别整理本组数据
- **Shuffle** = 各小组长把同类型的内容整理到同一摞（比如所有小组的「技术部」总结归到一起）
- **Reduce** = 老板把各小组汇总上来的同一主题内容合并，得出最终结论

:::note
你可能注意到 MapReduce 的代码量不小——一个简单的统计逻辑就要写几十行 Java。这正是后面要讲的 **Hive** 站出来解决的问题：用 SQL 代替手写 MapReduce。
:::

### MapReduce 的致命短板

MapReduce 虽然设计巧妙，但有 **一个硬伤**：

**每个计算阶段的中间结果都要写入磁盘。**

这意味着：即使只做两步运算（Map → Reduce），中间结果也得落盘一次。如果是一个复杂的多阶段计算（Map → Reduce → Map → Reduce），磁盘 IO 的次数会成倍增长——**磁盘读写是内存读写的几十倍慢**。

解决这个问题的方案，就是后来大杀四方的 **Spark**。

## 四、YARN——给计算任务当「管家」

### 资源管理问题

MapReduce 解决了「怎么算」的问题，但随之而来的新问题是：**谁来管这些计算任务的资源？**

一个 MapReduce 作业可能会产生成百上千个 Map 任务和 Reduce 任务，每个任务都需要 CPU 和内存。集群里有几十台服务器，哪台服务器分给哪个任务？任务排队时怎么分配优先级？——这就是 **YARN（Yet Another Resource Negotiator）** 的职责。

### 核心概念：Container

YARN 把计算资源抽象为 **Container（容器）**——一个 Container 就是一组受限的 CPU 和内存资源的组合。

```
YARN 资源调度流程：

用户提交计算任务
    │
    ▼
┌─────────────────────────────────────────┐
│              ResourceManager            │  ← 全局资源调度器
│  负责：接收任务、分配 Container、监控状态    │
└────────────┬────────────────────────────┘
             │
    ┌────────┴────────┐
    │    NodeManager  │  ← 每台服务器上都有一个
    │  (服务器节点1)    │     负责管理本机的 Container
    │  ┌────────────┐  │
    │  │ Container 1│  │  ← CPU 2核 + 内存 4GB
    │  │ (Map 任务)  │  │
    │  ├────────────┤  │
    │  │ Container 2│  │  ← CPU 1核 + 内存 2GB
    │  │ (Reduce 任务)│ │
    │  └────────────┘  │
    └──────────────────┘
```

### YARN 与 K8s 的关系

学到这里，如果你之前学过 [容器编排的艺术——Kubernetes](../编程生涯容器编排的艺术——kubernetes/)，一定会觉得 YARN 和 K8s 做的事情有点像——都是资源调度和管理。

| 维度       | YARN                | Kubernetes   |
| -------- | ------------------- | ------------ |
| **定位**   | 大数据计算框架的资源管理器       | 通用容器编排平台     |
| **资源抽象** | Container（CPU + 内存） | Pod（可包含多个容器） |
| **调度粒度** | 作业级别                | 应用级别         |
| **适用场景** | Spark、Flink 等计算框架   | 任意微服务、有状态应用  |
| **当前地位** | 存量场景仍广泛使用           | 云原生时代的事实标准   |

:::important
2026 年的趋势是：**YARN 逐渐被 Kubernetes 取代。** 越来越多的数据平台把 Spark 和 Flink 作业以容器方式提交到 K8s 集群运行。YARN 的设计初衷是为批处理优化的，而 K8s 能统一调度批处理作业、流处理作业、应用服务——运维复杂度大幅降低。但现实中，银行、电信等传统行业的大量 Hadoop 集群仍在使用 YARN，这一过渡还会持续很多年。
:::

## 五、Hive——用 SQL 撬动大数据

### 痛点：数据分析师不会写 MapReduce

MapReduce 虽然强大，但它的编程门槛实在太高了——写一个简单的统计逻辑就要好几十行 Java 代码。

在 MySQL 时代，一个数据分析师只要会写 SQL 就能做数据分析。到了大数据时代，竟然要逼着产品经理和运营人员学写 MapReduce？这显然不现实。（当然，到了AI时代，这些问题也都不是问题了）

**Hive** 就是来解决这个问题的。

### Hive = SQL → MapReduce 的翻译器

Hive 的定位很简单：**把用户写的 SQL 语句，自动翻译成 MapReduce 任务去执行。**

```sql
-- 用 Hive SQL 统计男女消费总额
-- 这段代码背后会被翻译成一个 MapReduce 作业
SELECT gender, SUM(amount) AS total_amount
FROM orders
WHERE order_date >= '2026-06-01'
GROUP BY gender;

-- 翻译后等价于：
-- Map 阶段：读取 orders 表每行数据，输出 (gender, amount)
-- Reduce 阶段：按 gender 分组，SUM 汇总 amount
-- 整个过程用户不用写一行 Java 代码
```

这个 idea 的精妙之处在于：**SQL 是数据分析领域最通用的语言，Hive 让它无缝衔接到了大数据世界。**

### Hive 表结构

Hive 里的表和 MySQL 的表有一个本质区别：

| 维度       | MySQL 表       | Hive 表               |
| -------- | ------------- | -------------------- |
| **存储介质** | 本地磁盘文件        | HDFS 上的文件            |
| **数据格式** | InnoDB 引擎的页结构 | 文本/Parquet/ORC 等文件格式 |
| **执行引擎** | MySQL 自研      | MapReduce/Tez/Spark  |
| **更新删除** | 支持事务，实时更新     | 不支持（或通过 ACID 表有限支持）  |
| **适用场景** | 在线事务处理（OLTP）  | 离线数据分析（OLAP）         |

```sql
-- 建表示例：创建一个 Hive 表
CREATE TABLE orders (
    order_id    STRING,
    user_id     INT,
    gender      STRING,
    amount      FLOAT,
    category    STRING,
    order_date  STRING
)
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ','        -- 指定 CSV 格式
STORED AS TEXTFILE;              -- 以文本文件格式存储

-- 加载数据到 Hive 表
LOAD DATA INPATH '/user/data/orders/2026-07-15.csv'
INTO TABLE orders;

-- 执行查询（自动转换为 MapReduce 任务）
SELECT category, COUNT(*) AS order_count, AVG(amount) AS avg_amount
FROM orders
GROUP BY category
ORDER BY order_count DESC;
```

### 通俗比喻

Hive 像一个 **「跨语言翻译官」**——你只需要说中文（SQL），它会自动翻译成机器能懂的指令（MapReduce 任务），然后去执行并返回结果。

:::caution
Hive 的查询延迟通常在数十秒到分钟级别，**不适合实时查询场景**。每个 Hive SQL 背后都是一个或多个 MapReduce 任务，任务的启动、调度、计算都需要时间。如果你需要一个能在海量数据中毫秒级查出某一条记录的数据库，Hive 做不到——那是后面要讲的 **HBase** 的领域。
:::

## 六、Spark——把磁盘「搬」进内存里

### 问题：MapReduce 太慢了

MapReduce 的一个核心瓶颈：**每个阶段的计算结果都要写入磁盘**。

考虑一个简单的两步计算：

1. 从订单表中统计每个品类的销售额（一轮 MapReduce）
2. 对上一步结果排序取前 10 名（又一轮 MapReduce）

每一步的中间结果都要写磁盘。磁盘 IO 的速度比内存慢几十倍到上百倍，这就是 MapReduce 慢的根本原因。

### Spark 的创新：RDD + 内存计算

Spark 的核心创新就一句话：**把尽可能多的中间结果放在内存里**。

它的核心数据结构叫做 **RDD（Resilient Distributed Dataset，弹性分布式数据集）**——可以理解为 Spark 内部的数据「载体」，数据以分区（Partition）的形式分布在集群各节点的内存中。

```
MapReduce vs Spark 执行对比：

MapReduce 执行方式（每次落盘）：
  HDFS 读取 → Map 写磁盘 → Shuffle 写磁盘 → Reduce 写磁盘 → 输出到 HDFS
              ↓               ↓               ↓
          磁盘 IO        磁盘 IO         磁盘 IO

Spark 执行方式（尽可能内存）：
  HDFS 读取 → Map(内存) → Shuffle(内存) → Reduce(内存) → 输出到 HDFS
              ↓               ↓               ↓
          不落盘          不落盘           不落盘
         (除非内存放不下)
```

Spark 的性能优势非常明显——同一计算任务，Spark 通常比 MapReduce **快 10 到 100 倍**。

### Spark 生态：不只是快那么简单

Spark 不只是 MapReduce 的替代品，它长出了一个完整的生态圈：

```text
Spark 生态系统：
                    ┌─────────────┐
                    │   Spark     │
                    │  Core 引擎   │  ← 底层执行引擎，RDD + DAG 调度
                    └──────┬──────┘
          ┌────────────────┼────────────────┐
          │                │                │
    ┌─────┴─────┐    ┌─────┴─────┐    ┌─────┴─────┐
    │ Spark SQL │    │Spark MLlib │   │ Spark     │
    │ (结构化查询)│    │ (机器学习)  │   │ Streaming │
    └───────────┘     └───────────┘   │ (流处理)   │
                                      └───────────┘
```

| 组件                  | 功能                            | 类比            |
| ------------------- | ----------------------------- | ------------- |
| **Spark Core**      | 底层执行引擎，RDD + DAG 调度           | 发动机，提供动力      |
| **Spark SQL**       | 用 SQL 或 DataFrame API 操作结构化数据 | 方向盘，让操作更简单    |
| **Spark MLlib**     | 分布式机器学习算法库                    | 工具箱，提供各种算法    |
| **Spark Streaming** | 微批处理模式的流计算引擎                  | 传送带，按批次处理实时数据 |

```python
# PySpark 示例：用 DataFrame API 做统计分析
from pyspark.sql import SparkSession
from pyspark.sql.functions import sum, avg, count, col

# 初始化 Spark 会话
spark = SparkSession.builder \
    .appName("order_analysis") \
    .config("spark.sql.adaptive.enabled", "true") \  # 开启自适应查询优化
    .getOrCreate()

# 读取 HDFS 上的订单数据
orders_df = spark.read \
    .option("header", "true") \
    .csv("hdfs://cluster/user/data/orders/*.csv")

# 链式操作：筛选 → 分组 → 聚合 → 排序
result = orders_df \
    .filter(col("order_date") >= "2026-06-01") \     # 筛选近一个月数据
    .groupBy("gender", "category") \                  # 按性别+品类分组
    .agg(
        sum("amount").alias("total_amount"),           # 总消费额
        count("*").alias("order_count"),               # 订单数量
        avg("amount").alias("avg_amount")              # 平均消费额
    ) \
    .orderBy(col("total_amount").desc())              # 按总消费额降序排列

result.show(10)
```

这段代码的可读性和简洁度，和前面几十行 Java 的 MapReduce 版本形成了鲜明对比——**Spark 的 DataFrame API 让大数据分析的开发效率提升了一个数量级。**

### 通俗比喻

Spark 像把工厂的 **传送带升级成了「空中轨道」**：

- MapReduce 的传送带是地面传送带——每个加工站之间要先把零件卸到地面（磁盘），再搬到下一个工位
- Spark 的空中轨道——零件在加工站之间通过空中传输（内存），不用落地，加工速度成倍提升

## 七、Flink——让数据「流」起来

### Spark 的局限：再快也是「批」

尽管 Spark 已经把 MapReduce 甩开几条街，但 Spark Streaming 的底层仍然是 **微批处理（Micro-batch）**：

```
Spark Streaming 的微批模式：
  数据流：|---数据1---|---数据2---|---数据3---|---数据4---|---
          ↓           ↓           ↓           ↓
         [攒成一批]   [攒成一批]   [攒成一批]   [攒成一批]
          ↓           ↓           ↓           ↓
         ┌─────┐    ┌─────┐    ┌─────┐    ┌─────┐
         │ 批1 │     │ 批2 │    │ 批3 │    │ 批4 │
         └─────┘    └─────┘    └─────┘    └─────┘
          ↓           ↓           ↓           ↓
                    Spark Core 逐批处理
```

每一批数据之间有间隔（从几秒到几十秒不等），这意味着延迟是「批大小」级别的——**不是真正的实时**。

### Flink 的革新：来一条算一条

**Apache Flink** 走的是另一条路：**真正的流计算（True Streaming）**。数据来一条，就处理一条，没有「攒批」的过程。

```
Flink 的流模式：
  数据流：|--数据1--|--数据2--|--数据3--|--数据4--|
          ↓         ↓         ↓         ↓
        ┌─┴─┐     ┌─┴─┐     ┌─┴─┐     ┌─┴─┐
        │处理│     │处理│     │处理│     │处理│  ← 每条数据独立处理
        └───┘     └───┘     └───┘     └───┘
          ↓         ↓         ↓         ↓
                   实时结果输出
```

```java
// Flink 流处理示例：实时统计每分钟的订单金额
public class OrderStreamAnalysis {

    public static void main(String[] args) throws Exception {
        // 创建流执行环境
        StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();

        // 从 Kafka 读取实时订单数据（数据流源头）
        DataStream<String> orderStream = env
            .addSource(new FlinkKafkaConsumer<>("orders", new SimpleStringSchema(), properties));

        // 解析、分组、窗口计算
        orderStream
            .map(line -> {
                String[] fields = line.split(",");
                return Tuple2.of(fields[2], Double.parseDouble(fields[3]));
                // 解析为 (性别, 金额) 格式
            })
            .keyBy(value -> value.f0)                       // 按性别分组
            .window(TumblingProcessingTimeWindows.of(Time.minutes(1)))  // 1 分钟滚动窗口
            .sum(1)                                          // 求和
            .print();                                        // 输出结果

        env.execute("Real-time Order Analysis");
    }
}
```

### 事件时间 vs 处理时间

Flink 相比 Spark Streaming 的另一个关键优势，是它对 **事件时间（Event Time）** 的原生支持：

| 时间概念     | 含义                    | 举例                    |
| -------- | --------------------- | --------------------- |
| **事件时间** | 数据实际产生的时间             | 用户点击「下单」按钮的那一刻        |
| **处理时间** | 数据到达 Flink 系统的时间      | Flink 服务器收到这条点击数据的那一刻 |
| **摄入时间** | 数据进入 Flink Source 的时间 | Kafka 消费者拉取到数据的那一刻    |

如果没有事件时间机制，当网络延迟导致数据晚到几分钟时，这些数据会被归到错误的窗口里。Flink 通过 **Watermark（水位线）** 机制解决了这个问题——在乱序数据流中也能准确计算事件时间窗口。

### Spark vs Flink：怎么选？

| 维度               | Spark Streaming   | Flink                 |
| ---------------- | ----------------- | --------------------- |
| **处理模型**         | 微批处理（Micro-batch） | 真正流处理（True Streaming） |
| **延迟**           | 秒级到分钟级            | 毫秒级                   |
| **事件时间**         | 支持但有限             | 原生支持，Watermark 机制成熟   |
| **状态管理**         | 依赖外部存储            | 内置状态后端（RocksDB、内存）    |
| **Exactly-Once** | 支持                | 原生支持                  |
| **适用场景**         | 准实时 ETL、批流混合作业    | 实时数仓、实时风控、实时监控        |
| **2026 年地位**     | 批处理标配引擎           | 实时流处理领域绝对霸主           |

:::note= [数据可视化之BI](../编程生涯数据可视化之bi/) 中，提到了阿里云大数据体系中的 Flink 版产品。**Flink 的流原生设计是从架构层面为低延迟而生的**。
:::

## 八、HBase——在海量数据里「秒查」一条记录

### 新痛点：存量数据里取一条还是慢

HDFS 解决了海量存储，Hive/Spark 解决了海量计算，Flink 解决了实时处理——但这套组合在遇到一个看似简单的需求时，仍然很尴尬：

> 「把用户 10086 最近 10 条订单详情查出来。」

用 Hive 查？提交一个 SQL 任务，等 MapReduce/Spark 启动、调度、扫描数据……**分钟级别**。Flink 虽然实时性强，但它是针对 **数据流处理** 设计的，不是做 **在线查询** 的。

### HBase 的定位：分布式数据库

HBase 是一个 **运行在 HDFS 之上的分布式列式数据库**，专门为海量数据的高并发随机读写场景设计。

```
HBase 架构：
┌──────────────────────────────────────────────┐
│              HBase Master                     │  ← 管理 Region 分配
└──────────────────────────────────────────────┘
                      │
    ┌─────────────────┼─────────────────┐
    │                 │                 │
┌───┴────┐      ┌───┴────┐       ┌───┴────┐
│Region  │      │Region  │       │Region  │
│Server 1 │      │Server 2│       │Server 3│
│(行键A-F)│      │(行键G-M)│       │(行键N-Z)│
└────────┘      └────────┘       └────────┘
    ↓               ↓               ↓
┌──────────────────────────────────────────────┐
│                   HDFS                        │  ← 底层数据持久化
└──────────────────────────────────────────────┘
```

HBase 通过 **RowKey（行键）** 实现快速定位。只要你设计好 RowKey，HBase 能在毫秒级别定位到具体的数据行——**不需要全表扫描**。

```java
// HBase 查询示例：根据 RowKey 查询用户订单
public class OrderQuery {

    public void getOrdersByUserId(String userId) throws IOException {
        // 获取 HBase 表引用
        Table table = connection.getTable(TableName.valueOf("user_orders"));

        // 构造 Get 请求：RowKey = 用户ID倒序 + 时间戳
        // 设计思路：user_id 按字典序查找，时间戳倒序保证最新的在前面
        String startRow = userId + "#2026-07-15";
        String endRow = userId + "#2026-07-01";

        Scan scan = new Scan();
        scan.withStartRow(Bytes.toBytes(startRow));  // 扫描起始行
        scan.withStopRow(Bytes.toBytes(endRow));      // 扫描终止行
        scan.setLimit(10);                             // 只取 10 条

        ResultScanner results = table.getScanner(scan);
        for (Result result : results) {
            // 解析结果
            String orderId = Bytes.toString(
                result.getValue(Bytes.toBytes("info"), Bytes.toBytes("order_id")));
            String amount = Bytes.toString(
                result.getValue(Bytes.toBytes("info"), Bytes.toBytes("amount")));
            System.out.printf("订单ID: %s, 金额: %s\n", orderId, amount);
        }

        table.close();
    }
}
```

### HBase、Redis、MongoDB 的定位差异

我之前在 [NoSQL数据库理论入门——Redis与MongoDB](../编程生涯nosql数据库理论入门redis与mongodb/) 中学过 Redis 和 MongoDB，加上 HBase，正好可以做一个三者的横向对比：

| 维度       | Redis          | MongoDB      | HBase             |
| -------- | -------------- | ------------ | ----------------- |
| **定位**   | 缓存/高速存取        | 通用文档数据库      | 海量数据随机读写          |
| **数据量级** | KB\~MB（内存有限）   | GB\~TB（磁盘存储） | PB 级别             |
| **读写模式** | 全内存，微秒级        | 内存+磁盘，毫秒级    | 毫秒级随机读写           |
| **数据结构** | 五种基本类型         | 灵活的 BSON 文档  | 稀疏的列式存储           |
| **适用场景** | 缓存、排行榜、Session | 内容管理、日志、实时分析 | 订单流水、用户画像、监控指标    |
| **底层依赖** | 自身内存 + 持久化文件   | 本地文件系统       | **必须运行在 HDFS 之上** |

### 通俗比喻

HBase 像一个大型图书馆的 **索引柜系统**：

- 图书馆有几百万本书（海量数据），但你想找某一本的时候，不需要去书架上一排排找
- 索引柜按 **RowKey（索书号）** 分类：A 区放 A-F 开头的索引卡，B 区放 G-M 的……
- 你告诉管理员索书号，管理员在对应的索引柜（Region Server）里一翻，**秒级**找到书的位置

:::important
HBase 的性能极度依赖 **RowKey 的设计**。如果 RowKey 设计不合理（比如直接用自增 ID），数据会全部写入同一个 Region，导致「热点写」问题——集群里一台机器忙死，其他机器闲着。RowKey 设计的好不好，直接决定了 HBase 能不能发挥它的真实能力。
:::

## 十、现代大数据技术栈俯瞰——Hadoop 之后的世界

2026 年的今天，我们回过头看 Hadoop 生态，会发现一个有意思的格局：**Hadoop 的「设计思想」没有过时，但它的「实现方式」已经被翻新了很多轮。**

### 经典组件的现代替代

| 经典组件          | 当前地位                        | 现代替代方案                        |
| ------------- | --------------------------- | ----------------------------- |
| **HDFS**      | 存量场景仍广泛使用，新建平台很少选           | 对象存储（AWS S3、阿里云 OSS、MinIO）    |
| **MapReduce** | **基本退出主流**                  | Spark（离线）+ Flink（实时）          |
| **YARN**      | 银行/电信等传统行业仍普遍               | Kubernetes                    |
| **Hive**      | Hive Metastore 作为元数据中心仍不可替代 | Hive SQL 引擎 → Trino、Spark SQL |
| **HBase**     | 部分场景仍在使用                    | TiDB、Cassandra、ClickHouse     |
| **Spark**     | **离线批处理的事实标准**              | 自身持续迭代（Spark 4.x）             |
| **Flink**     | **实时流处理领域绝对霸主**             | 自身持续迭代（Flink 2.x）             |

### 不容忽视的「新势力」

除了上述替代关系，2026 年的大数据技术栈还涌现了一批经典 Hadoop 生态中没有的新角色：

```
2026 年大数据技术栈全景：

┌──────────────┐
│   数据源层     │  ← 业务数据库、日志文件、埋点数据、IoT 设备
└──────┬───────┘
       ↓
┌──────────────┐
│   数据管道     │  ← Kafka / Pulsar（消息队列，数据高速公路）
└──────┬───────┘
       ↓
┌──────────────────────────────────────────────┐
│                 存储层                        │
│  对象存储（S3/OSS/MinIO）+ 开放表格式            │
│  (Iceberg / Delta Lake / Hudi)               │  ← 新一代湖仓一体底座
└──────────────────┬───────────────────────────┘
                   ↓
┌──────────────────────────────────────────────┐
│              计算引擎层                       │
│  Spark（离线批处理） Flink（实时流处理） Trino（联邦查询）│
└──────────────────┬───────────────────────────┘
                   ↓
┌──────────────────────────────────────────────┐
│              OLAP / 查询层                    │
│  ClickHouse / Doris / StarRocks / TiDB       │  ← 新一代分析型数据库
└──────────────────────────────────────────────┘
```

### 湖仓一体：数据湖和数据仓库的融合

以前大家争论「数据湖」和「数据仓库」谁更好。2026 年的答案是：**都不选了，全都要——湖仓一体（Lakehouse）**。

湖仓一体的核心思路很简单：底层用廉价的对象存储（像数据湖一样），上层用开放表格式（如 Apache Iceberg）提供 ACID 事务、时间旅行、模式演进等数据仓库级别的能力。计算引擎（Spark、Flink、Trino）可以直接读取同一份数据，互不干扰。

```text
湖仓一体架构的精髓：
┌─────────────────────────────────────────────────┐
│  Spark / Flink / Trino / ... 多种计算引擎         │  ← 解耦
├─────────────────────────────────────────────────┤
│  Iceberg / Delta Lake 开放表格式                  │  ← ACID + 时间旅行
├─────────────────────────────────────────────────┤
│  对象存储（S3 / OSS / MinIO）                     │  ← 廉价 + 无限容量
└─────────────────────────────────────────────────┘
```

:::warning
不要把 Hadoop 和「大数据」划等号。Hadoop 是大数据时代的「开荒者」，但不是「终结者」。2026 年的大数据技术栈已经进化到湖仓一体 + 云原生的阶段，**如果你现在开始学大数据，建议直接从 Spark + Flink + 对象存储 + 开放表格式入手**，而非从 Hadoop 的完整部署开始。
:::

## 学习心得

从 Hadoop 到 Flink，从 HDFS 到对象存储，从 YARN 到 Kubernetes——这趟大数据技术栈的学习之旅，让我真正理解了「分而治之」这四个字的技术分量。

每一代技术都在解决上一代留下的痛点：

| 时代             | 解决的问题        | 遗留的痛点              |
| -------------- | ------------ | ------------------ |
| **HDFS**       | 单机存不下海量数据    | 不适合小文件，NameNode 单点 |
| **MapReduce**  | 单机算不动海量数据    | 磁盘 IO 瓶颈，编程门槛高     |
| **YARN**       | 资源管理需要统一调度   | 专为批处理设计，通用性差       |
| **Hive**       | SQL 降低编程门槛   | 延迟高，不适合实时场景        |
| **Spark**      | 内存加速计算       | 微批处理，延迟不够低         |
| **Flink**      | 真正的实时流处理     | 状态管理复杂，运维门槛高       |
| **K8s + 对象存储** | 存算分离 + 云原生弹性 | 网络延迟损耗             |

每一层新技术的出现，不是要推翻前人，而是把前人解决不了的痛点再往前走一步。这也是技术演进的底层逻辑：**没有银弹，只有不断逼近极限。**

回头看我之前学的 [数据可视化之BI](../编程生涯数据可视化之bi/)，其中提到的阿里云 MaxCompute（离线数仓）和 Flink 版产品，本质就是 Hadoop 生态思想的云原生实践。BI 是数据「可视化出口」，而大数据技术栈是整个链路的「数据引擎」——没有引擎，再漂亮的仪表盘也是空壳。
